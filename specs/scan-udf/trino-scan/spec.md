# Feature: trino_scan

States how the scan reaches a Trino source, how the credential travels in the driver's own credential options, and which transport carries it.

## Background

- This is the mechanism `scan-udf/arrow-scan`'s framework invariant is satisfied by for Trino. That feature requires the credential to be resolved from the named Exasol `CONNECTION` object at scan time and never persisted. This feature states only where it goes from there.
- The ADBC Trino driver accepts `username` and `password` as database options distinct from `uri`, so the scan sets three options and no credential enters the connection value. This is the separate-option shape `scan-udf/mysql-scan` uses rather than the single-option shape `scan-udf/postgresql-scan` is forced into. Gate 2.1 measured it against driver `0.5.3`: the library's option table carries `uri`, `username`, `password`, `passwordSet`, `SSL`, `SSLCert`, and `SSLCertPath`, and setting `password` as bytes rather than as a string returns `NotImplemented: [Trino] Unknown database option 'password'`, which shows the driver keeps an option registry and registers `password` as a string option.
- The `uri` option stays mandatory. Omitting it returns `InvalidArguments: [Trino] failed to create database: missing required option uri`. Its value is the address's own `trino://` URI, naming the host, the port, the catalog, the schema, and every query parameter the address carries.
- The `uri` option's value carries no userinfo component. A user and password written into the address are not the credential, because Exasol resolves that beside the address. Gate 2.1 measured that the separate options override a userinfo the URI carries, field by field, so keeping one would change no authentication result and would only add a place a secret can surface.
- Nothing about the credential is percent-encoded, because the credential reaches no URI. No option value the driver parses as a URI or as a connection string holds the password, so no password byte needs escaping and no password character can change where the URI's authority ends. The guarantee is structural rather than a property of an encoding, which is the same guarantee `scan-udf/mysql-scan` states. Gate 2.1 measured a password holding `@`, `/`, `:`, `?`, `#`, `&`, `%`, or a space authenticating through the separate options.
- Trino 483 authenticates no password holding a character outside the ASCII range through the separate options, and this feature attempts no workaround. Two facts together produce that limit, and gate 2.1 measured both against the server's own REST endpoint: the server decodes an HTTP Basic credential as ISO-8859-1, which is RFC 7617's default charset, and the driver sends the option value's UTF-8 bytes. The credential's UTF-8 bytes answer HTTP 401 and its ISO-8859-1 bytes answer HTTP 200. The same gate measured an ISO-8859-1 spelling reaching the server through the URI userinfo the driver percent-decodes, which covers U+0000 to U+00FF alone and no character above it. Decision `[17]` removes that route deliberately rather than by oversight, because a credential in the URI is the disclosure surface the separate options exist to close. So for U+0080 to U+00FF the closed door is this feature's own design choice; above U+00FF it is the server's charset and no client does better. The scan passes the resolved bytes unchanged and transcodes nothing either way.
- A `CONNECTION` carrying a password reaches Trino over HTTPS or not at all, and the server is what enforces that. The driver reads the transport from the address. It uses HTTPS by default, including on port 8080, and it sends plain HTTP only when the address carries `SSL=false`. Trino then refuses the credential with `403 Forbidden: "Error 403 Forbidden: Authentication over HTTP is not enabled"`, because its own `http-server.authentication.allow-insecure-over-http` default is `false`. Gate 2.1 measured both answers. The adapter surfaces that refusal rather than stripping the password to make the connection succeed. The server refuses the request only once a statement executes, exactly as it checks the credential only once a statement executes, so that refusal surfaces through the scan's execute-time diagnostic rather than through the connection-open path. A live `make test-e2e-trino` run measured the message, ``discovering source metadata: executing `SELECT table_name FROM "memory".information_schema.tables WHERE table_schema = 'adbc_vs' AND table_type IN ('BASE TABLE', 'VIEW') ORDER BY table_name`: IO: [Trino] failed to create record reader: failed to execute query: trino: query failed (403 Forbidden): "Error 403 Forbidden: Authentication over HTTP is not enabled"``. The catalog survives inside the statement's qualified table reference and the schema survives as a predicate literal. The host appears nowhere. So this refusal names no host, for the same reason and under the same narrowing the wrong-password bullet below states, and every Trino-server-level rejection reached only through query execution falls under it. A refusal the driver itself raises while the connection opens does not: an address naming the plain-HTTP port without `SSL=false` fails the driver's own TLS handshake before any statement runs, so it reaches the credential-free failure subject the connection-open path names and names the host.
- A Trino server serving a certificate the driver cannot verify is reached by the address's own certificate-verification parameter, which the adapter carries across like every other parameter and neither adds nor removes. Whether to disable verification is the operator's decision, recorded in the `CONNECTION` object rather than in a property or a compiled-in setting, so the adapter has no verification policy of its own for the source. This is separate from the registry client's policy, which `driver-provisioning/driver-self-install` fixes at always verifying.
- Every invariant about persistence and disclosure holds, and each is asserted rather than assumed. The option values carrying the credential are built at the moment of connecting and discarded with the connection attempt. The credential reaches no scan specification, no `adapterNotes`, no SQL text, no `EXPLAIN VIRTUAL` output, and no log line or error message.
- The password takes one spelling inside the process, its verbatim bytes, and the adapter strips that one spelling from every message it surfaces. The adapter strips it at the boundary it controls rather than trusting the driver, as defense in depth. Gate 2.1 measured the one driver message that quotes a value it was handed: a malformed `uri` is rejected with `InvalidArguments: [Trino] failed to create database: invalid Trino URI format`, which quotes the URI. That message can disclose no credential here, because the URI holds none.
- The failure subject the adapter names is the credential-free value handed to the `uri` option. It names the host, the port, the catalog, and the schema, and it carries no userinfo, so naming it discloses nothing.
- The Trino driver checks no credential while the connection opens, so a wrong password is refused only once a statement executes. Gate 2.1 measured the open path deferring both the transport and the credential to the first execute, and gate 2.1d measured the driver's own `401` quoting neither the URI nor the credential. The failure subject the bullet above builds is therefore never reached for a wrong password. That failure surfaces through the scan's execute-time diagnostic instead, which names the statement: the catalog and the schema survive inside the statement's qualified table reference, and the host appears nowhere. Group E measured the message, ``executing `SELECT name AS c1 FROM memory.adbc_vs.orders`: ADBC status IO: [Trino] failed to create record reader: failed to execute query: trino: query failed (401 Unauthorized): "Access Denied: Invalid credentials"``. So `scan-udf/trino-scan` is the one feature of the three that cannot name the host on an authentication failure, and the catalog and the schema are what keep that one failure diagnosable. This is a decision rather than an oversight: an eager probe query at connect time would restore the host and was rejected, because it adds a round trip to every connection open to fill one field of one failure mode's message. `scan-udf/mysql-scan` and `scan-udf/postgresql-scan` name the host eagerly because their own drivers authenticate inside the connection handshake, which is those drivers' protocol behavior rather than anything this adapter built, and which this feature reaches for Trino only by adding that probe. The narrowing covers every failure Trino itself raises only once a statement executes, which is the wrong password and the plain-HTTP refusal the transport bullet above states, and nothing else. An unreachable host fails at the transport before any statement runs, a malformed `uri` fails at database creation, and a plain-HTTP-port address carrying no `SSL=false` fails the driver's own TLS handshake, and each still names the host.
- The connection-open path is shared, so the redaction binds every caller rather than the scan alone. The adapter opens the source connection through the same path for `createVirtualSchema`, `refresh`, and `setProperties`.
- The driver's own Arrow representations are what the coercion receives. It returns a `varchar` as a string, a `date` as a 32-bit day value, a `double` as a double, a `bigint` as a 64-bit integer, and a `boolean` as an Arrow boolean. It returns a `decimal` at the narrowest Arrow width its declared precision admits: `Decimal32` up to precision 9, `Decimal64` from precision 10 to 18, and `Decimal128` from precision 19 up. It returns a `timestamp(p)` at the Arrow unit that precision implies, seconds at precision 0, milliseconds up to 3, microseconds up to 6, and nanoseconds above that. Gate 2.4 measured every one of those widths and units against real batches. A nanosecond timestamp, a `Decimal32`, and a `Decimal64` are representations this driver reaches and the other two do not. `scan-udf/arrow-scan` owns the normalization of every one into the declared Exasol type.

## Scenarios

### Scenario: The credential travels in the driver's own username and password options

* *GIVEN* an Exasol `CONNECTION` whose address is `trino://host:8443/memory/adbc_vs?SSLVerification=NONE` and whose password contains `@`, `/`, `:`, `?`, `#`, `&`, `%`, and a space
* *WHEN* the scan builds the Trino connection target
* *THEN* the scan MUST set the resolved user as the driver's `username` database option and the resolved password as its `password` database option, rather than writing either into the connection value
* *AND* each of those two option values MUST equal the resolved field byte for byte, with no percent-encoding, escaping, or transcoding applied by the scan, because the driver sends the bytes it is given and Trino 483 authenticates no password holding a character outside the ASCII range
* *AND* the `uri` option's value MUST equal the address with its userinfo component removed and nothing else changed, so no credential reaches a value the driver parses and no query parameter and no path element the operator set is dropped or re-derived
* *AND* the connection MUST authenticate against a Trino server whose configured password holds each of those characters, proven by executing a statement rather than by opening the connection alone, because the driver defers both the transport and the credential to the first execution

### Scenario: A userinfo component in the address is dropped rather than carried

* *GIVEN* an Exasol `CONNECTION` whose address carries a user and a password in its own userinfo component, and whose user and password fields hold different values
* *WHEN* the scan builds the Trino connection target
* *THEN* the `uri` option's value MUST carry no userinfo component
* *AND* the `username` and `password` options MUST carry the values the `CONNECTION` object's own fields hold
* *AND* the host the `uri` option addresses MUST be the address's own host rather than any part of the discarded userinfo component
* *AND* the failure subject the scan names MUST be built from the `uri` option's value, so neither the discarded userinfo nor the resolved credential can reach it

### Scenario: Credential never appears in any surfaced text

* *GIVEN* a scan against a Trino source, and a second scan whose `CONNECTION` object holds a wrong password
* *WHEN* the first scan's generated SQL, scan specification, and `adapterNotes` are read back, and the second scan's error is surfaced
* *THEN* none of the generated SQL, the scan specification, or `adapterNotes` MUST contain the password or the user
* *AND* the error the failing scan surfaces MUST NOT contain the password, including within any text the driver produced, at the database-creation step as well as the connect and execute steps, because gate 2.1 measured database creation to be the one step whose message quotes a value it was handed
* *AND* the second scan's error MUST still name the catalog and the schema it tried to reach, so a wrong credential stays diagnosable, and it MAY omit the host, because the driver checks the credential only once a statement executes and the execute-time diagnostic names the statement rather than the address
* *AND* the redaction MUST be applied by the scan rather than relied on from the driver, because nothing upstream binds the driver to omit a value it received as an option

### Scenario: Adapter-side source error surfaces no credential

* *GIVEN* an Exasol `CONNECTION` addressing a Trino server, whose password field holds a value
* *WHEN* `createVirtualSchema`, `refresh`, or `setProperties` fails against that source, once with a wrong password and once against a host and port nothing listens on
* *THEN* every error surfaced to the querying session MUST NOT contain the source password, in any encoding or escaping
* *AND* the wrong-password failure MUST still name the catalog and the schema it addressed, so it stays diagnosable, and it MAY omit the host, because the driver checks the credential only once a statement executes
* *AND* the unreachable-host failure MUST still name the host, the catalog, and the schema it addressed, because a transport failure happens before any statement executes and the driver's own message quotes the address it dialled
* *AND* the redaction MUST apply to the subject the adapter names as well as to text the driver produced, and MUST hold for every caller of the shared connection-open path rather than for the scan alone

### Scenario: A password over an unencrypted transport fails rather than being sent or dropped

* *GIVEN* an Exasol `CONNECTION` whose address carries `SSL=false` and whose password field holds a value
* *WHEN* the scan opens the Trino connection
* *THEN* the attempt MUST fail with the Trino server's own refusal, `403 Forbidden: "Error 403 Forbidden: Authentication over HTTP is not enabled"`, because the server's `http-server.authentication.allow-insecure-over-http` default is `false`
* *AND* an address naming the plain-HTTP port without that parameter MUST fail inside the driver instead and MUST name the host, because the driver uses HTTPS by default on every port and refuses that address while the connection opens, before any statement executes, so the failure subject the connection-open path names is reached
* *AND* the adapter MUST NOT strip the password, downgrade the request, or rewrite the address to make the connection succeed, because any of those would send a credential the operator asked to protect or silently connect as a different principal
* *AND* the surfaced error MUST NOT contain the password, and the server's own refusal MUST still name the catalog and the schema it tried to reach, so the refusal stays diagnosable, and it MAY omit the host, because the server refuses the request only once a statement executes, which is past the point the connection-open path names its failure subject

### Scenario: Every timestamp precision and decimal width this driver returns coerces to its declared type

* *GIVEN* Trino `timestamp(p)` columns at precisions the driver returns as seconds, milliseconds, microseconds, and nanoseconds, and `decimal(p,s)` columns the driver returns as `Decimal32`, `Decimal64`, and `Decimal128`, each declared in Exasol as `TIMESTAMP` or as `DECIMAL`
* *WHEN* the scan coerces those batches
* *THEN* every value MUST be emitted as its declared Exasol type
* *AND* the nanosecond unit MUST be handled rather than rejected, because this driver reaches a unit the other two do not
* *AND* the `Decimal32` and `Decimal64` widths MUST be handled rather than rejected, because this driver returns the narrowest width a declared precision admits where the other two return one width
* *AND* a value whose sub-millisecond digits Exasol cannot hold MUST be handled by the same rule `scan-udf/arrow-scan` states for every driver rather than by a rule of this feature's own
