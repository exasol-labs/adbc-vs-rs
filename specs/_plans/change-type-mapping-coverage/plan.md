# Plan: change-type-mapping-coverage

## Summary

PostgreSQL and MySQL map every column type the Exasol JDBC Virtual Schemas map, with `CHAR` and `TIMESTAMP(p)` joining the mapped set, timestamps keeping their source precision, and no source session setting. Each mapped column records its source type, so the dialect reads a converted type as the value the scan emits, and `docs/type-mapping.md` and `specs/exasol-types.md` state the mapping, the remaining differences from Exasol's comparison, and Exasol's own type limits.

## Context

- Issue exasol-labs/adbc-vs-rs#17: PostgreSQL maps seven types and omits every other column, so a 19-column ticket table kept two columns. Issue #18: PostgreSQL timestamps lose their microseconds, because every timestamp declares Exasol's default precision of 3.
- The PR conversation comment asks to align both mappings with the JDBC Virtual Schemas checked out at `~/code/exa-postgresql-virtual-schema` and `~/code/exa-mysql-virtual-schema`, to maximize coverage, and to record a known difference from Exasol's comparison instead of omitting the type. It overrides the interview rules "map only types with safe predicates" and "no per-column mechanism" (decision-log `[pr-feedback]`).
- JDBC PostgreSQL (`BaseColumnMetadataReader.java:321-449`, `PostgreSQLColumnMetadataReader.java:36-59`): `numeric` of any precision, `uuid`, `json`, `jsonb`, `xml`, `interval`, `inet`, geometric, enum, and unknown types map to `VARCHAR(2000000)`; `money` and `real` to `DOUBLE`; `bit` of any width to `BOOLEAN`; `character(n)` to `CHAR(n)` up to 2000; `time` types to `VARCHAR(100)`; `bytea` returns a constant text; arrays are left out. The dialect casts these types in the select list only (`PostgresSQLSqlGenerationVisitor.java:49-54, 181-198`), keyed on the type name it records in column `adapterNotes`.
- JDBC MySQL (`MySQLColumnMetadataReader.java:36-86`): integers map to `DECIMAL` of the width's digits, `TINYINT(1)` and `BIT` of any width to `BOOLEAN`, `TEXT` to `VARCHAR(65535)`, `MEDIUMTEXT`, `LONGTEXT`, and `JSON` to `VARCHAR(2000000)`, `ENUM` and `SET` to `CHAR`, `TIME` to a `TIMESTAMP` on 1970-01-01, `YEAR` to `DATE`, every character set to `UTF8`; binary, blob, and spatial types are left out. The dialect renders no type-specific conversion.
- Neither JDBC Virtual Schema sets a session time zone or a JDBC time-zone property. Both declare `TIMESTAMP(p)` from the source precision on Exasol 8.32 and later. adbc-vs supports Exasol 2025.1 and later, and `TIMESTAMP(6)` holds microseconds on the test Exasol 2025.1.11 (measured), so the mapping needs no version check.
- Whether the UDF SDK carries an Arrow microsecond timestamp into an `EMITS` column declared `TIMESTAMP(6)` without truncation is not measured. The SDK hands Arrow IPC bytes to the Script Language Container (`exasol-udf-sdk` `context.rs:251-269`), so no code read settles it. Exasol changelog 13409 states that a Script Language Container can emit 9 fractional digits. Task 2.1 measures it directly after task 1.1 and gates every later task.
- Exasol 2025.1.11, measured with literal queries: a `CHAR(5)` holding `ab` equals `'ab'`, is unequal to a `VARCHAR` holding `ab`, and does not match `LIKE 'ab'`. Exasol's type limits, aliases, and defaults are in `reference/exasol-types.md` in this directory, which task 5.3 copies to `specs/exasol-types.md`.
- `specs/` holds product behavior only (`AGENTS.md`). `specs/exasol-types.md` is classed as reference material for type mappers, not a feature spec: it holds no scenarios, and `speq` reads no file outside `specs/<domain>/<feature>/`, which a scratch copy of `specs/` with the file added confirmed (`speq feature validate` and `speq plan validate` pass). Task 5.4 states the class in `AGENTS.md`.
- Exasol never re-applies a delegated fragment and negotiates per capability, not per column. The query model already resolves each column reference's declared type from `involvedTables` (`pushdown_query.rs:135-137`, `:480-495`), and `create_schema.rs::column_json` (`:790-796`) writes no column `adapterNotes` yet.
- A `column` entry in predicate position fails today (`pushdown_query.rs:760-762`), and so does a predicate as a comparison operand. PostgreSQL defines no `min` or `max` over `boolean`.
- Two request shapes are unmeasured: whether Exasol sends `WHERE FLAG` over a `BOOLEAN` column as a bare `column` entry, which task 1.6 accepts, or as a comparison with a `literal_bool`, which no dialect advertises; and how many fractional digits a `literal_timestamp` carries for `TIMESTAMP '2024-01-01 12:00:00.123456'` compared with a `TIMESTAMP(6)` column, which `pushdown_query.rs:872` passes through as text. Task 2.2 measures both and records them here.
- MySQL matches a select-list expression against a `GROUP BY` expression only whole and rejects any other expression over a grouped column with error 1055 (ADR `fail-select-list-predicate-over-grouped-character-key`). A key grouped by its read expression therefore needs `ANY_VALUE` in the select list (decision-log `[plan-review]`). PostgreSQL accepts a select-list expression over a grouped sub-expression.
- Departures from the PR request's JDBC alignment, for the PR reviewer to confirm: constrained PostgreSQL `numeric(p,s)` with p at most 36 maps to `DECIMAL(p,s)`, where JDBC maps every `numeric` to `VARCHAR(2000000)` (decision-log [9]); `bytea` maps to its hex text, where JDBC returns a constant text; a PostgreSQL `character(n)` wider than 2000 is read without its trailing blanks; every reference to a converted column reads through its read expression, where the JDBC PostgreSQL dialect converts in the select list only ([6]); and `TINYINT(1)` maps to `DECIMAL(3,0)`, as the request says, where JDBC maps it to `BOOLEAN`. PostgreSQL arrays and MySQL binary, blob, and spatial columns stay omitted as JDBC omits them, although issue #17 lists arrays ([10]). The user confirmed in this session that every bit width maps to `BOOLEAN`, that MySQL `CHAR(n)` maps to `CHAR(n)`, and that a non-finite `DOUBLE` reaches Exasol unchanged (decision-log `[pr-feedback]`).
- The fixture tables `items`, `all_unmapped`, and `numeric_specials` (`docker/postgres/init.sql:64-174`) and `mixed_types`, `unmapped_only`, the `latin1` `items.region` column, and the `CHAR(8)` `code` columns (`tests/common/mysql.rs:90-135`, `docker/mysql/init.sql:15`) hold columns this plan maps or retypes. Existing MySQL assertions expect `code` as `VARCHAR(8) UTF8` (`e2e_mysql_test.rs:785`, `:1307-1308`, `tests/common/mirror.rs:58-59`, `:134-135`).
- The architecture delta (`architecture.md` in this directory) adds the column `adapterNotes`, the read expression, `TIMESTAMP(p)`, and the absence of a session setting to § Components, § Data Flow, § Interfaces, and § Constraints.

## Impact

- After `ALTER VIRTUAL SCHEMA ... REFRESH`, a PostgreSQL virtual table exposes every column except arrays, and a MySQL virtual table every column except binary, blob, and spatial ones. A `SELECT *` returns more columns, and tables whose columns were all unmapped appear.
- Breaking for refreshed schemas: column types change. A PostgreSQL or MySQL timestamp declares its source precision, so `TIMESTAMP(6)` replaces `TIMESTAMP` for a default PostgreSQL `timestamp`. A MySQL `CHAR(n)` column declares `CHAR(n)` instead of `VARCHAR(n)`, so Exasol pads its values and compares them with a `VARCHAR` operand as a `CHAR`. A MySQL `latin1` column now maps instead of being omitted. A view or `CREATE TABLE AS` over a virtual table picks up the new types.
- An existing virtual schema keeps its tables, columns, and generated statements until it is refreshed, including `VARCHAR(n)` for its MySQL `CHAR` columns. Its columns carry no column `adapterNotes`, so they render bare, as today.
- Downgrading adbc-vs after a `REFRESH` under this release fails queries over `TIMESTAMP(p)` columns with p other than 3 and over converted columns until the schema is refreshed under the older release.
- Generated statements change for converted types: a PostgreSQL `uuid`, `json`, unconstrained `numeric`, or similar column renders as `CAST(<column> AS TEXT)`, `money` as a double conversion, `bit` as `(position(B'1' IN <column>) > 0)`, and MySQL `TIME`, `YEAR`, `BIT`, and `JSON` columns as their read expressions, inside `ANY_VALUE` in the select list of a MySQL grouped query. A delegated filter, join key, grouping key, or `MIN` or `MAX` operand on such a column cannot use a source index on it. The main cost case is a PostgreSQL `uuid` key, and `docs/type-mapping.md` names the expression-index remedy.
- Known differences from Exasol's comparison, which `docs/type-mapping.md` lists: a `CHAR` column compared with a `VARCHAR` operand or matched by `LIKE` without a trailing wildcard follows the source's blank-padding rule; a `bit` or `BIT` column wider than one bit reads as `true` when any bit is set, so two different source values read as one `true`; a PostgreSQL `timestamp with time zone` compared with a timestamp or date follows the source session `TimeZone`, so a non-UTC session shifts the selected rows; a MySQL `TIMESTAMP` reads in the session `time_zone` and repeats one wall-clock value in a daylight-saving fall-back hour; a delegated comparison of a MySQL `latin1` column with a literal outside `latin1` fails with MySQL's collation error.
- A query reading a text longer than 2000000 characters from a newly mapped column fails rather than returning a truncated value.

The scenarios copied unmarked into the `pushdown-join`, `pushdown-aggregation`, and `postgresql-collation` deltas are unchanged.
- The existing `vs-adapter/postgresql-collation` E2E tests show that a `character varying` column still renders bare and keeps its collation.
- Each differential E2E test checks a delegated fragment twice, per `AGENTS.md`: `EXPLAIN VIRTUAL` shows the fragment in the source statement, and the rows equal those of the same query over the local Exasol mirror table.
- `docker-compose.yml` (`:27-60`) sets no time zone for the test PostgreSQL and MySQL containers, so their sessions are expected to run in UTC. The E2E tests of a time-zone-aware timestamp first assert that the session zone is UTC (PostgreSQL `SHOW TimeZone`, MySQL `TIMEDIFF(NOW(), UTC_TIMESTAMP())` equal to zero) and fail naming the zone otherwise, then assert agreement with the mirror. The non-UTC behavior is a stated limitation and has no E2E test.
