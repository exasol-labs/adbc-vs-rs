# Plan: add-default-bucketfs-connection

## Summary

Make `BUCKETFS_CONNECTION` optional: a statement naming none resolves the reserved connection `ADBC_VS_BUCKETFS`, and both explicit properties are unchanged. A version-free default driver location answers when that connection does not resolve, or when the driver registry cannot be reached through it.

## Design

### Context

`createVirtualSchema` requires `BUCKETFS_CONNECTION` whenever `DRIVER_PATH` is absent, so every virtual schema on a cluster restates the same BucketFS write credential. Issue #4 asks for a conventional default plus a soft landing when neither route is configured.

Two forces shape the answer, and they pull against each other.

The first is release 0.3's own record. `driver-provisioning/driver-path-override` was introduced precisely to *remove* an informal "place the library at a fixed compiled-in path" fallback, and ADR 003 rejected keeping it on two grounds: the path was not a supported input, and it stopped being fixed once the install path carried a resolved version. Issue #4's point 3 asks for that fallback back. It is grantable only if both grounds are answered — the location must be a stated interface, and it must be version-independent by construction.

The second is why the install path carries a version at all. `provisioning.rs` states it: an unversioned path "would have made it answer for whichever version arrived first, so a range would resolve once per cluster and never again." Any location the presence check consults *before* the index read reintroduces exactly that defect.

Both are answered by keeping the two locations disjoint and never consulting the new one before an install would have been attempted. Self-install keeps its versioned tree and its index-first presence check, untouched. The pre-placed location is a separate, version-free path, reached only when self-install through the reserved connection could not run at all.

Two failures mean it could not run, and the maintainer's answer to round-1's intent question settles that both count. The reserved connection does not resolve, so no write credential exists. Or it resolves and the registry answers nothing, so no version can be resolved to install. The second is the case issue #4's "Why" names: a cluster that followed the deployment instructions holds `ADBC_VS_BUCKETFS`, and an air-gapped one has no HTTPS egress. Serving only the first would deliver the soft landing to a cluster that deleted the connection the same plan tells it to keep.

The version-first defect survives that widening because the fallback happens *after* a failed index read rather than before a successful one. Nothing was resolved and nothing was installed, so the next statement reads the index again: a pre-placed library shadows self-install for exactly as long as the registry stays unreachable, and not one statement longer.

That argument holds only for the index request's own transport failure, so the trigger is narrowed to exactly that. Today one `ProvisioningError` variant covers four failures. Either request can reach no host, and either body can stop arriving after its status did. Three of the four mean the registry answered, so nothing about the cluster's egress was learned. Two of those three also run after a version was resolved and a presence check ran, a second ground that excludes the package leg. Task 2.2 splits the variant along both axes before the fallback predicate is written.

- **Goals**
  - A `CREATE VIRTUAL SCHEMA` that needs no `BUCKETFS_CONNECTION` on the common cluster.
  - A stated, version-independent location an air-gapped operator can pre-place a library at without setting `DRIVER_PATH`, reachable on a cluster that holds the reserved connection.
  - Both explicit properties unchanged, including their refusal to fall back on any failure.
- **Non-Goals** — no change to version resolution's own answers, to the versioned presence check, or to what self-install downloads and writes. No new property. No configurable default-connection name and no configurable mount. Both are conventions, and a property for either would be a decision the adapter declined to make. No fallback before an index read, and none on a registry that answered anything at all. No fallback on a package request that reached no host, on either leg's interrupted transfer, or on either explicit route.

### Decision

One precedence chain, four levels, each reached only by the absence of the one above it. The last two levels are new, and the last one is reached by either of two cluster-level failures.

#### Architecture

```
CREATE VIRTUAL SCHEMA / refresh / setProperties
        │
        ▼
create_schema::driver_source(&properties)          ← pure, no I/O, unchanged shape
        │
        ├── DRIVER_PATH set ─────────────▶ Supplied(path)
        ├── BUCKETFS_CONNECTION set ─────▶ SelfInstall(name)
        └── neither ─────────────────────▶ DefaultBucketFs                        (NEW)
        │
        ▼
create_schema::open_driver_library(ctx, mount, source, driver)                    (mount NEW)
        │
   Supplied ─────────▶ provisioning::supplied_driver(path)     exact path, readable only
        │
   SelfInstall(name) ─▶ resolve_connection(name) ─▶ ensure_driver
        │                 every failure of either step surfaces: never falls back
        │
   DefaultBucketFs ───▶ resolve_connection("ADBC_VS_BUCKETFS")
                          ├── Err(cause) ────────────────────── ConnectionUnresolved(cause) ─┐
                          └── Ok ─▶ ensure_driver(registry, bucket)                          │
                                     ├── Ok(installed) ──────▶ provisioned                   │
                                     └── Err(e) ─▶ e.registry_unreachable()                  │
                                            Some((url, cause)) ▶ RegistryUnreachable{..} ────┤
                                            None ─────────────▶ SchemaError::Provisioning(e) │
                                                                                             ▼
                                     create_schema::default_location_library(mount, driver, cause)
                                       provisioning::readable_library(default_driver_path(..))
                                         Ok  ─▶ DriverLibrary::supplied(path), no version
                                         Err ─▶ SchemaError::NoDriverRoute

provisioning error taxonomy, split so one variant means one failure:            (NEW)
  RegistryUnreachable  index request reached no host             fallback fires
  PackageUnreachable   package request reached no host           statement fails
  TransferInterrupted  either leg's body stopped mid-arrival     statement fails

BucketFS mount, two disjoint trees:
  adbc-drivers/<driver>/<version>/<library>   adapter-owned, written by self-install
  adbc-drivers/<driver>/supplied/<library>    operator-owned, never written by the adapter   (NEW)
```

#### Patterns

| Pattern | Where | Why |
|---------|-------|-----|
| Route selection stays a pure function of properties | `create_schema::driver_source` | It runs before any `CONNECTION` is resolved, which is what keeps a statement that could never provision refusable without reaching outside the process. Probing the default connection and the default location is I/O, so both live in `open_driver_library` where `ctx` already is |
| Sentinel path segment rather than a version | `adbc-drivers/<driver>/supplied/<library>` | The install path's third segment is always a parsed `semver::Version`, and no version parses as `supplied`, so the operator-owned and adapter-owned trees are provably disjoint rather than disjoint by convention |
| One definition of "readable driver library" | `provisioning::readable_library`, called by both routes | Two callers deciding independently what counts as readable is back-door leakage; each route phrases its own error over one shared answer |
| The last resort has one entry point and two causes | `create_schema::default_location_library` | Both triggers reach the same file at the same path and produce the same notes. One function taking why it was reached keeps the location's layout, its readability test, and its error phrased once |
| Only an index request that reached no host falls back | `provisioning::ProvisioningError::registry_unreachable` | The accessor lives with the taxonomy that answers it, so `create_schema` asks the question in its own vocabulary and learns no variant name. It returns the index URL and the transport cause rather than a bool, so the caller composes its own message from facts instead of quoting another route's remedy. Widening it to any provisioning failure would pin a cluster to a pre-placed library on a transient CDN outage |
| One variant per failure, split before the accessor is written | `PackageUnreachable`, `TransferInterrupted` beside `RegistryUnreachable` | One variant covering four failures made the accessor unable to tell an air gap from a reset mid-download. The three it now sheds all mean the registry answered, so none of them says anything about the cluster's egress. Two of the three carry a second ground: the package leg runs after a version was resolved and the presence check ran |
| The route rule is one testable function every self-install failure passes through | `create_schema::self_install_fallback` | "Only the reserved route falls back, and only on a registry reached not at all" is one rule. Both credential routes hand their `ensure_driver` error to this function, so the route argument holds a real value at run time and one test covers both answers. An arm the code never calls would test nothing |
| Explicit values never fall back | `SelfInstall`, `Supplied` | Already the `DRIVER_PATH` rule; extending it to an explicit `BUCKETFS_CONNECTION`, for a failed resolution and an unreachable registry alike, keeps one rule rather than three |
| The mount is injected, never read inside the decision | `open_driver_library`'s new `mount` parameter | `BUCKETFS_MOUNT` is ambient host state, and a branch chosen by whether a path outside the workspace exists is not assertable below the E2E tier. `open` passes the constant at the entry point, so both branches are unit-testable against a temp directory |

#### Key Interfaces

| Interface | Owner | Contract |
|-----------|-------|----------|
| `pub const DEFAULT_BUCKETFS_CONNECTION: &str` | `create_schema` | The reserved `CONNECTION` name. Lives beside `BUCKETFS_CONNECTION_PROPERTY` because `create_schema` owns every connection-name decision; `provisioning` is handed credentials and resolves nothing |
| `pub fn default_driver_path(mount: &Path, driver: Driver) -> PathBuf` | `provisioning` | The operator-owned location's layout. Takes the mount as an argument, exactly as `Bucket::new` does, so `provisioning` owns the layout and `create_schema` owns which mount is real |
| `pub fn readable_library(path: &Path) -> Result<(), String>` | `provisioning` | Whether a path is a driver library the adapter will use. `Err` carries the cause each route's own error message quotes |
| `pub fn ProvisioningError::registry_unreachable(&self) -> Option<(&str, &str)>` | `provisioning` | `Some((index URL, transport cause))` only for an index request that reached no host. Every registry that answered, every unusable index, every package failure — the package request reaching no host included — and every BucketFS failure is `None`, so a caller cannot mistake a CDN outage, a reset download, or a bad package for an air gap. Returns the two facts rather than a bool so the caller composes its own message and never re-renders this module's |
| `enum FallbackCause { ConnectionUnresolved(String), RegistryUnreachable { url: String, cause: String } }` | `create_schema` | Why self-install through the reserved connection did not run. Two variants rather than two `Option` fields, so the error cannot be built naming both causes or neither. The `RegistryUnreachable` arm carries the accessor's two facts, never a rendered `ProvisioningError` |
| `fn self_install_fallback(&DriverSource, &ProvisioningError) -> Option<FallbackCause>` | `create_schema` | The route rule: `Some` for `DefaultBucketFs` and an index request that reached no host, `None` for every other pairing. Every `ensure_driver` failure on both credential routes passes through it, so `SelfInstall` reaches `None` through the same call `DefaultBucketFs` reaches `Some` through |
| `fn default_location_library(mount: &Path, driver: Driver, cause: FallbackCause) -> Result<DriverLibrary, SchemaError>` | `create_schema` | The last-resort step both triggers reach. Returns a supplied library with no version, or `NoDriverRoute` |
| `SchemaError::NoDriverRoute { driver, path, fallback: FallbackCause }` | `create_schema` | The error replacing today's missing-property error. Three fields, not five: `Display` names `DEFAULT_BUCKETFS_CONNECTION`, `BUCKETFS_CONNECTION_PROPERTY`, and `DRIVER_PATH_PROPERTY` from the constants, so the reserved connection is context on both arms and the reported failure on the `ConnectionUnresolved` arm alone. The `RegistryUnreachable` arm composes the index URL and the transport cause into its own sentence |

Reviewed against `/speq:design-philosophy`'s Quick Diagnostic. No new module and no new boundary: five functions, one small enum, and one error variant join modules that already own the decisions behind them. `default_driver_path` sits beside `driver_install_path`, so BucketFS layout keeps its single owner; `DEFAULT_BUCKETFS_CONNECTION` sits beside the property constants, so connection naming keeps its single owner; `registry_unreachable` sits with the error taxonomy it reads, so no caller matches a variant and no caller re-renders this module's prose. `readable_library` exists to stop a second owner appearing for a decision `supplied_driver` already made. Dependencies stay inward: `provisioning` gains no knowledge of properties, connections, or the UDF context, and `create_schema` gains no knowledge of the path layout beyond calling for it. `driver_source` stays pure, so the boundary between "which route the properties chose" and "what that route does" is unmoved. The mount arrives as an argument on both branches of `open_driver_library`, so `open` is the module's only reader of `BUCKETFS_MOUNT` and the two paths the disjointness test compares are computed under one mount value.

### Consequences

| Decision | Alternatives Considered | Rationale |
|----------|------------------------|-----------|
| Reserve `ADBC_VS_BUCKETFS` as the default connection name | `ADBC_VS_BUCKETFS_CONNECTION`; a new `DEFAULT_BUCKETFS_CONNECTION` property naming it | The README, both E2E harnesses, and `tests/common/schema.rs` already use exactly this name, so the convention is the one already documented and a cluster that followed the README needs no change at all. A `..._CONNECTION` suffix restates the object's kind; a property naming the default is a default that is not one |
| Give the pre-placed route its own version-free location, `adbc-drivers/<driver>/supplied/<library>` | Reuse the versioned install path; add a `default` segment; put it under `adbc-drivers/supplied/<driver>/` | The versioned path cannot be pre-placed without resolving a version, which is what an air-gapped cluster cannot do — ADR 003's second ground for rejecting the old fallback. `default` reads as a version and the mount already ends `bfsdefault/default`. `supplied` names the owner, matches `supplied_driver`, and can never be mistaken for a version |
| Reach the default location on both cluster-level failures: the reserved connection does not resolve, or the index request reaches no host | Only the no-connection case, which round 1 flagged as intent drift; any provisioning failure | The no-connection-only trigger fires only on a cluster that deleted the connection the README tells it to create, so the soft landing issue #4 asked for would never reach the cluster that needs it. Falling back on any failure would pin a cluster to a stale pre-placed library on a transient CDN outage or a bad package |
| Split `RegistryUnreachable` into three variants before the fallback predicate is written | Keep one variant and document the boundary; test the predicate over variants only | One variant covered four failures: either request reaching no host, and either body stopping after its status arrived. Three of them mean the registry answered, so none is evidence of an air gap, and the fallback would have fired on a reset 46 MB download and on a truncated index alike. A boundary a variant cannot express is a boundary no test can hold |
| Hand `create_schema` the index URL and the transport cause, not a rendered `ProvisioningError` | Keep the bool predicate and embed `error.to_string()` in the last-resort error | The rendered text names `DRIVER_PATH` as the remedy, which is the explicit route's answer rather than this one's. It also denied that any pre-load location exists — a claim task 2.2 deletes from every variant that carried it. Returning two facts lets each route phrase its own remedy over one shared answer, which is the rule `readable_library` already follows |
| Delete the "no path on the mount to pre-load it at" clause from every provisioning message | Reword it on `RegistryRejected` alone, and keep the explicit route's copy; special-case the derived route at render time | The clause is false of the product once `adbc-drivers/<driver>/supplied/` exists and task 4.1 documents it. `RegistryRejected` is reachable on the derived route, so the clause had to go there. `RegistryUnreachable` keeps it only on the explicit route, where it would tell an operator that the location `README.md` names does not exist. One true sentence costs less than two routes' messages kept apart. **Human-directed** |
| Give `NoDriverRoute` three fields and read the property names from constants | Five fields, carrying the connection name and a second cause beside `fallback` | A `cause` field beside a `fallback` field reintroduces the "built naming both causes or neither" pairing that `FallbackCause`'s two variants exist to rule out. The three names the message states are compile-time constants of this module, so a field for any of them is a value that can only ever hold one thing |
| Consult the default location only after an install would have been attempted | Check it first as a cheap short-circuit before the index read | Checking first restores the "answers for whichever version arrived first" defect the versioned path removed. Falling back after a failed index read does not: nothing resolved, nothing installed, and the next statement reads the index again |
| Fall through only on the reserved-connection route, for a failed resolution and an unreachable registry alike; never on either explicit route | Fail on any resolution failure; distinguish not-found from no-access; let an explicit `BUCKETFS_CONNECTION` fall back too | `UdfError` exposes no structured variant, so not-found and no-access cannot be told apart. Falling through is safe on the derived route: Exasol enforces `CONNECTION` access at resolution, the source `CONNECTION` is resolved first, and the notes record which route answered. An explicit property is an instruction, so its failures surface unchanged |
| Extend `driver-provisioning/driver-path-override` rather than add a fourth feature | A new `driver-preplaced-default` feature | Both routes reach the same three obligations — exact file, readability only, no fallback — and differ only in where the path came from. Two features would have to be kept in agreement about a decision neither owns alone |
| Scope `driver-provisioning/driver-version-resolution`'s unreachable-registry error to the explicit route | Leave the feature untouched, as round 1 found it left; extend the error to name the default location on every route | Two of the three routes no longer reach that error: `DRIVER_PATH` reads no index, and the reserved-connection route answers an unreachable registry from the default location. Leaving the scenario unscoped left a recorded spec that the new route contradicts. Naming the default location inside that error would offer the pre-placed remedy on the one route that refuses it |

## Impact

`BUCKETFS_CONNECTION` becomes optional. The README has always named the BucketFS connection `ADBC_VS_BUCKETFS`. A `CREATE VIRTUAL SCHEMA` on such a cluster needs `DRIVER` and `CONNECTION_NAME` only. Every statement that works today keeps working unchanged, including both explicit routes and their refusal to fall back on any failure.

No breaking change. One behavior change lands on the derived route. A statement omitting both `BUCKETFS_CONNECTION` and `DRIVER_PATH` used to fail naming the missing property. It now resolves the reserved connection and self-installs through it. It falls to the default driver location on two failures: that connection does not resolve, or the index request reaches no host. It still fails when no library is there. That error names the location it looked at, both properties, and whichever failure blocked self-install.

A session that can create a virtual schema and can resolve `ADBC_VS_BUCKETFS` can now trigger a driver download and a BucketFS write. It no longer has to name that connection. Exasol still enforces access to the connection object, so this grants no credential the session did not already hold.

`adbc-drivers/<driver>/supplied/` becomes a reserved location on the BucketFS mount. Any holder of the BucketFS write credential can place a native library there. Self-install never overwrites or removes what is there. The adapter loads it with no statement naming the path, where `DRIVER_PATH` required a statement. Two conditions bound it. The loading statement must name neither property. Either the reserved connection must not resolve, or the index request must reach no host. The schema's `adapterNotes` record the path and no driver version, so an operator can read back which route answered.

During a registry outage the derived route prefers a pre-placed library over an already-installed one. The versioned presence check binds to a resolved version, and an index the request never reached resolves none. `refresh` and `setProperties` apply the same precedence as `createVirtualSchema`. A schema's recorded `driverPath` and `driverVersion` can therefore change when an outage starts and change back when it ends, with no operator action. Two schemas created either side of an outage can run different driver builds on one cluster.

Two error messages lose a sentence on every route. An unreachable registry and a rejecting registry both told the operator the same thing: no path on the mount exists to pre-load a library at. That claim is false once `adbc-drivers/<driver>/supplied/` exists, and false on the explicit route too, where the location exists and only goes unread. Both messages keep the registry, the driver, the cause or status, and `DRIVER_PATH` as the remedy.

## Dependencies

None. No new crate, no new Make target, no new CI job, no new container.

## Migration

| Current | New |
|---------|-----|
| `BUCKETFS_CONNECTION = 'ADBC_VS_BUCKETFS'` in every statement | Optional; omit it and the reserved connection answers |
| `BUCKETFS_CONNECTION` naming another connection | Unchanged — the explicit property still wins, and still never falls back on a failed resolution or an unreachable registry |
| Air gap: `DRIVER_PATH = '<any path>'` | Unchanged, and still the route for a library outside the `adbc-drivers` tree |
| Air gap without `DRIVER_PATH`: unsupported | Place the library at `/buckets/bfsdefault/default/adbc-drivers/<driver>/supplied/<library>` and set neither property. It answers on a cluster holding `ADBC_VS_BUCKETFS` with no HTTPS egress, and on a cluster where that connection does not resolve. It is not consulted while the registry index answers |
| Omitting both properties fails naming `BUCKETFS_CONNECTION` | Resolves `ADBC_VS_BUCKETFS`, self-installs, then falls to the default driver location; fails naming both properties, the location, and whichever failure blocked self-install |
| `BUCKETFS_CONNECTION = ''` fails naming the missing property | Takes the reserved-connection route, self-installs, and can write to BucketFS. `optional_property` filters the empty string throughout the adapter, so an empty property reads as absent and this is the same statement as omitting it |

Two scenarios are covered at two tiers rather than one, and neither pairing is redundant. The no-short-circuit scenario needs the provisioning tier to prove `ensure_driver` never consults the supplied path and the end-to-end tier to prove the route selection wires that through a real statement. The no-driver-anywhere scenario needs the unit tier for the message's composition, which an end-to-end assertion can only substring-match, and the end-to-end tier to prove the failure is the adapter's rather than Exasol's.

One coverage boundary is stated rather than hidden. No automated tier produces an unreachable registry inside a UDF sandbox: `Registry::public` compiles the CDN host in, no property overrides it, and the E2E stack has working egress. That trigger is therefore covered by its decision (`self_install_fallback`, `registry_unreachable`) and its outcome (`default_location_library` over an injected mount) at unit tier, by which real failure yields which variant at the provisioning tier, and end to end by the manual row below, which blocks the container's outbound HTTPS. The wiring the manual row exercises is the same wiring task 3.3 proves automatically for the other trigger — the two arms differ only in which failure reaches `default_location_library`.

Every unchanged scenario of all four features keeps the tests it has. This plan removes no coverage; the one deleted test asserted behavior the plan deliberately removes.
