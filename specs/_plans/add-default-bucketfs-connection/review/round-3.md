## Feasibility

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: `plan.md` § Design/Context para 5 (line 25), § Consequences row 4 (line 116), § Implementation Tasks 2.2 bullet 3 and 2.3 bullet 5; `decision-log.md` § [12] rationale; `driver-provisioning/driver-path-override` delta Background bullet 14 and scenario "The default driver location is used when the registry answers nothing" (line 44); `driver-provisioning/driver-version-resolution` delta Background bullet 17; against `crates/adbc-vs-adapter/src/provisioning.rs:517-518,866-868`
- Issue: the split is specified for three failures, and there are four. `download` is shared by both legs, so a body-read failure after a received status arises on the **index** request too — a proxy or link that answers HTTP 200 for `index.yaml` and then drops the connection. The plan never names that quadrant, and every place it explains the exclusion gives a reason that is false for it: "The last two happen after a version was resolved and a presence check ran" (`plan.md`:25), "both happen after the index was read, a version was resolved, and the versioned presence check ran" (decision `[12]`), "each happens after a version was resolved and the versioned presence check ran" (`driver-path-override` line 44), "both happen after this feature already resolved a version and answered the presence check" (`driver-version-resolution` bullet 17). On a truncated index nothing was resolved and no presence check ran, so an implementer reading those four sentences can reasonably conclude `TransferInterrupted` is the package leg's variant and leave the index leg's body-read failure mapped to `RegistryUnreachable`. The fallback then fires on a registry that answered 200 — the exact class of failure decision `[12]` and § Design/Key Interfaces row 4 ("Every registry that answered ... is `None`") exclude — and no planned test notices: `only_a_registry_reached_not_at_all_is_unreachable` asks which variant is accepted, `registry_unreachability_is_told_from_a_registry_that_answered` covers a closed port, HTTP 500 and an unsatisfiable range, and `a_package_download_that_failed_mid_transfer_is_not_an_unreachable_registry` covers the package leg only.
- Fix: In `plan.md` § Implementation Tasks 2.2 bullet 3, state the mapping as a four-row table rather than as three prose cases: index leg plus a connect-, DNS- or TLS-level failure yields `RegistryUnreachable`; index leg plus a body that stopped arriving yields `TransferInterrupted`; package leg plus a connect-level failure yields `PackageUnreachable`; package leg plus a body that stopped arriving yields `TransferInterrupted`. In § Implementation Tasks 2.3, extend `a_package_download_that_failed_mid_transfer_is_not_an_unreachable_registry` with a second case, or add a sibling test, in which the *index* route sends a status line and a `Content-Length` and then closes before the declared body arrives, asserting `registry_unreachable` is `None`; add the matching § Verification row beside the mid-transfer clause row. In `plan.md`:25, § Consequences row 4, `decision-log.md` § [12], `driver-path-override` Background bullet 14 and scenario line 44, and `driver-version-resolution` Background bullet 17, replace "both happen after a version was resolved and the presence check ran" with the reason that holds for all of them — the registry answered, so nothing about the cluster's egress was learned — and keep the after-resolution argument as a second ground stated for the package leg alone.

#### [EFFORT_MISESTIMATION] ADVISORY
- Location: `plan.md` § Implementation Tasks 2.3 bullet 5; against `crates/adbc-vs-adapter/tests/provisioning_test.rs:904-909,1078-1086`
- Issue: the new mid-transfer test needs a stub reply the harness cannot currently produce. `StubReply` is `{ status, body }` and `write_reply` always writes `Content-Length: body.len()` followed by the whole body, so there is no way to declare a length and then close. The test therefore requires a harness change — a third field or a second reply shape, plus a branch in `write_reply`, plus updating the six existing `StubReply` literals (`provisioning_test.rs:377`, `447`, `742`, `758`, `920`, `924`) or giving the struct a constructor. Task 2.3 states the desired stub behavior as though it were expressible today, and every other harness change in this plan (`supplied_path_for`, `SUPPLIED_BUCKET_PATH`, `copy_bucket_object`, `parse_driver_semver`) is called out explicitly, so this omission is inconsistent with the plan's own standard and understates the one test both round-2 blockers turn on.
- Fix: Add a bullet to `plan.md` § Implementation Tasks 2.3 stating that `StubReply` and `write_reply` currently send only complete bodies, and that the test needs a reply shape declaring a `Content-Length` the handler then does not satisfy before the connection closes; name the six existing literals as the call sites the new field touches, or require a constructor so they stay unchanged.

## Requirement Quality

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: `plan.md` § Implementation Tasks 2.2 (bullet 3, the variant split) and § Dead Code Removal (final paragraph); `driver-provisioning/driver-path-override` delta scenario "The default driver location is used when the registry answers nothing" (line 43); against `crates/adbc-vs-adapter/src/provisioning.rs:362-373`
- Issue: round 2's blocker was closed for `NoDriverRoute` and left open for its sibling. `ProvisioningError::RegistryRejected`'s `Display` ends with the same clause `RegistryUnreachable`'s does — "there is no path on the mount to pre-load it at, because the install path carries a version only the registry could have resolved" — and after this plan that variant is reachable on the **new** route. A statement naming neither property, on a cluster holding `ADBC_VS_BUCKETFS`, whose CDN answers HTTP 503, resolves to `DefaultBucketFs`, calls `ensure_driver`, gets `RegistryRejected`, is told `None` by `registry_unreachable`, and surfaces as `SchemaError::Provisioning(e)` — carrying, verbatim, the sentence the maintainer ruled out: "No text from the explicit route's remedy may reach the new route's error" (`decision-log.md` § Interview, round-2 answer 2; decision `[15]`). The consequence is worse than round 2's, because the plan makes this the common route (§ Impact: "A `CREATE VIRTUAL SCHEMA` on such a cluster needs `DRIVER` and `CONNECTION_NAME` only") and task 4.1 puts the pre-load location into `README.md` and `CLAUDE.md`. An operator who follows those documents, places the library at `adbc-drivers/mysql/supplied/libadbc_driver_mysql.so`, hits a 503 and retries gets a message insisting no such location exists — while `driver-path-override` Background bullet 12 promises the location "is named by the error an operator gets when nothing is there". The same denial is one copy-paste away from the two new variants: task 2.2 specifies `PackageUnreachable` and `TransferInterrupted` only as "rendered as a driver-package download that reached no host" and "rendered as a response whose body stopped arriving after its status did", says nothing about the remedy clause, and both are reachable on the derived route. No delta scenario constrains the message a registry-that-answered raises, and no planned test asserts anything about it. Nothing blocks the fix: no test asserts that phrase — `provisioning_test.rs:242-246` and `275-278` assert only that the message does not contain the library filename — and no recorded scenario mandates it (`driver-version-resolution`'s recorded "Unreachable registry names the offline fallback" requires only that the message MUST NOT *name* a fixed path).
- Fix: Add a bullet to `plan.md` § Implementation Tasks 2.2 requiring that no `ProvisioningError` a derived-route statement can surface denies the existence of the default driver location. Concretely: delete the clause "there is no path on the mount to pre-load it at, because the install path carries a version only the registry could have resolved" from `ProvisioningError::RegistryRejected`'s `Display` in `crates/adbc-vs-adapter/src/provisioning.rs:362-373`, leaving it naming the registry, the status, the driver and `DRIVER_PATH`; and state that `PackageUnreachable` and `TransferInterrupted` carry no such clause either. Decide `RegistryUnreachable`'s own arm in the same bullet and record the choice in `decision-log.md` § [12] or § [15]: after the split it is reachable only on the explicit route, where the sentence is still false of the product — the location exists, that route simply does not read it — so either reword it the same way, or state why the explicit route keeps a sentence the new documentation contradicts. Add a clause to the `driver-provisioning/driver-path-override` delta scenario "The default driver location is used when the registry answers nothing", beside line 43: a registry that answered MUST fail the statement with an error that does not state that no path on the mount exists to pre-load a library at, because on this route one does and the adapter reads it. Add a test to task 2.2's `provisioning_tests.rs` bullet list — over every `ProvisioningError` a `DefaultBucketFs` statement can surface, the rendered message MUST NOT contain `no path on the mount to pre-load` — and add its § Verification row. Update § Dead Code Removal's final paragraph, which currently narrows `RegistryUnreachable` alone and asserts its `Display` is unchanged.

#### [COMPLETENESS_GAP] ADVISORY
- Location: `plan.md` § Implementation Tasks 2.2, the `only_a_registry_reached_not_at_all_is_unreachable` bullet ("Enumerate the variants rather than sampling: a variant added later must force this test to be revisited")
- Issue: the stated mechanism does not achieve the stated guarantee. A test that constructs 21 values still compiles and still passes when a 22nd variant is added, so nothing forces revisiting. The accessor as specified — "returning the index URL and the transport cause for `RegistryUnreachable` and `None` for every other variant" — will be written with a `_ => None` arm, which is where the silence comes from. The default is the safe direction, so the risk is a stale claim rather than a live defect, but the claim is load-bearing: it is the plan's only stated defence against a future variant being misclassified, and § Design/Key Interfaces row 4 rests the whole route rule on the accessor's boundary.
- Fix: In `plan.md` § Implementation Tasks 2.2, require `registry_unreachable` to be written as an exhaustive `match` with no wildcard arm, so adding a variant is a compile error in `provisioning.rs` rather than a silent pass, and state that in its doc comment. Replace the test bullet's "a variant added later must force this test to be revisited" with what the test does hold — one constructed value per variant, `Some` for `RegistryUnreachable` and `None` for the other twenty, with the returned pair carrying the index URL and cause the variant was built with — and attribute the force-revisit property to the wildcard-free match.

#### [TRACEABILITY_GAP] ADVISORY
- Location: `plan.md` § Design/Patterns row 6, § Design/Key Interfaces row 6, § Implementation Tasks 2.2 (the `self_install_fallback` and "Replace 2.1's placeholder" bullets), § Verification rows for `an_explicit_bucketfs_connection_never_falls_back`
- Issue: `self_install_fallback(source, error)` takes the route as a parameter, but its only production call site passes a constant. Task 2.2 states that the `DefaultBucketFs` arm "routes every self-install failure through `self_install_fallback`" and that "the `SelfInstall` arm gains no fallback branch at all", so `source` is `DefaultBucketFs` at every real call and the route half of the rule can never evaluate false in production. `an_explicit_bucketfs_connection_never_falls_back` asserts `None` for `SelfInstall` and `Supplied` — a call the adapter never makes — and § Verification maps that test to two spec clauses it therefore cannot hold: `create-virtual-schema`'s "An explicitly named BucketFS connection never falls back" unreachable-registry clause, and `driver-version-resolution`'s added no-fallback clause. A later edit that gave the `SelfInstall` arm a fallback branch would break the maintainer's stated boundary with every planned test still green. This also undercuts § Design/Patterns row 6's own claim: the rule is stated as "one testable function, not two match arms" while the design is in fact two match arms with a function beside them.
- Fix: In `plan.md` § Implementation Tasks 2.2, make `self_install_fallback` the single funnel both arms' self-install errors pass through, so the route argument is live at run time and the test exercises the code path the explicit route actually takes; state in the "Replace 2.1's placeholder" bullet that the `SelfInstall` arm reaches `default_location_library` only through a `None` answer it can never receive. If the two-arm structure is kept instead, drop the `source` parameter, restate § Design/Patterns row 6 as the registry half of the rule alone, and change the § Verification rows for the two explicit-route no-fallback clauses to say the boundary is held by the arm structure and by task 1.1's end-to-end test rather than by a unit test over an unreachable call.
