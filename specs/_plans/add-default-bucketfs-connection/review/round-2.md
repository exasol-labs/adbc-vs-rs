## Feasibility

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: `plan.md` § Implementation Tasks 2.2 (`is_registry_unreachable`) and § Design/Context para 5; `decision-log.md` § [12]; against `crates/adbc-vs-adapter/src/provisioning.rs:511-540,856-893`
- Issue: the plan's whole safety argument rests on `ProvisioningError::RegistryUnreachable` meaning "the registry answered nothing at all". It does not. `provisioning_error` is the sole constructor and maps `DownloadFailure::Unreachable` to that variant, and it is called on **both** legs of `ensure_driver`: the index read at `provisioning.rs:517-518` and the **package download** at `provisioning.rs:534-535`. `download` also maps a body-read failure to `Unreachable` (`provisioning.rs:866-868`), after the status line was already received. Two failure modes therefore produce the variant the fallback fires on, and the plan denies both. First, a transport failure on the package download — a reset, or the 600 s `TRANSFER_TIMEOUT` expiring on a 46 MB body — happens *after* the index was read, a version was resolved by `select_package`, and the versioned presence check ran. `plan.md`:23 states "the fallback happens *after* a failed index read rather than before a successful one. Nothing was resolved and nothing was installed"; decision `[11]` repeats it; `driver-path-override` delta Background bullet 13 repeats it; and that delta's scenario "The default driver location is used when the registry answers nothing" asserts "the adapter MUST NOT write to BucketFS, **because no version was resolved and no package was fetched**". On the package leg all three are false, and the cluster is pinned to the unversioned pre-placed library on exactly the transient condition decision `[12]` exists to exclude. Second, a registry that answered HTTP 200 and then dropped the connection also yields `RegistryUnreachable`, against decision `[12]`'s "a registry that answered any HTTP status ... stays false" and `driver-path-override` Background bullet 14. No planned test can catch either: `only_a_registry_reached_not_at_all_is_unreachable` asks which *variant* is accepted, not which real failure produces it, and `registry_unreachability_is_told_from_a_registry_that_answered` covers only a closed port at the index leg, an HTTP 500, and an index publishing no in-range version.
- Fix: In `plan.md` § Implementation Tasks 2.2, add a bullet splitting the variant before the predicate is written: pass the download stage into `provisioning::provisioning_error` (or give `download`'s failure type a stage) so a transport failure on the package leg becomes its own `ProvisioningError` variant — name it `PackageUnreachable { url, driver, cause }` and render it as a failed package download rather than as an unreachable registry — and so a body-read failure after a received status becomes its own variant too, leaving `RegistryUnreachable` for a connect-, DNS-, or TLS-level failure of the index request alone. State in the same bullet that `is_registry_unreachable` returns true for that narrowed variant only, and that the count in `only_a_registry_reached_not_at_all_is_unreachable` rises accordingly. In § Implementation Tasks 2.3, add `a_package_download_that_failed_mid_transfer_is_not_an_unreachable_registry`: a stub registry serving a valid index whose package route closes the connection before the declared body is sent, asserting `ensure_driver` fails and `is_registry_unreachable` is false. In `decision-log.md` § [12], replace "true for `RegistryUnreachable` alone" with the narrowed boundary and name the package leg and the truncated-body case as the two failures the split removes from it. Mirror the corrected boundary into `driver-path-override` delta Background bullet 14 and `driver-version-resolution` delta Background bullet 17, and delete "and no package was fetched" from `driver-path-override`'s "The default driver location is used when the registry answers nothing" scenario, replacing it with the reason that holds — no version was resolved because the index was never read. Add a § Verification row for the new test.

#### [NFR_IGNORED] ADVISORY
- Location: `plan.md` § Implementation Tasks 3.2, against `crates/adbc-vs-adapter/tests/e2e_postgres_test.rs:1046-1054`
- Issue: round 1's `Drop`-guard fix landed on task 3.3 only. Task 3.2 copies a 44 MB object into `SUPPLIED_BUCKET_PATH` and then "delete the copied object and drop the schema before asserting" as straight-line steps. Both `Exasol::copy_bucket_object` (task 3.2 defines it around `curl --fail`) and `schema::create_virtual_schema_through` panic on failure, and the step between the copy and the delete is the one most likely to fail if the no-short-circuit route misbehaves. A panic there leaves the operator-owned object in BucketFS for the rest of a `--test-threads=1` run and for the next binary: `e2e_postgres_test.rs::installed_driver` finds the first entry under `adbc-drivers/mysql/` ending in the library name with no version parsing, so it can return the leftover `supplied` path as "the installed mysql driver". Task 3.0's filter is scoped to the MySQL binary, and the two E2E binaries share one BucketFS.
- Fix: Add a bullet to task 3.2 in `plan.md` § Implementation Tasks requiring the copied object's deletion be held by the same `Drop`-guard pattern task 3.3 uses, so a panic between the copy and the delete still removes it. Add a bullet to task 3.0 narrowing `e2e_postgres_test.rs::installed_driver` the same way `installed_drivers` is narrowed, so a leftover object cannot be reported as an installed driver in either binary.

#### [COMPLETENESS_GAP] ADVISORY
- Location: `plan.md` § Impact; `driver-provisioning/driver-path-override` delta § Background
- Issue: the widened trigger makes the fallback prefer a pre-placed library over an already-installed, presence-checked one, and neither `plan.md` nor any delta states it. The presence check binds to the resolved version (`driver-version-resolution` recorded Background bullet 7), so an unreachable index means the installed library cannot be used at all. On a cluster holding `ADBC_VS_BUCKETFS`, a working `0.6.0` install, and a stale pre-placed library, a registry outage makes every statement naming neither property — and every `refresh` of an existing such schema, since the precedence scenario's last clause applies the same precedence to `refresh` and `setProperties` — load the pre-placed library and record no `driverVersion`, then revert when the outage ends. Two virtual schemas on one cluster can run different driver builds, and one schema's notes can change under it without any operator action. This is a consequence of the direction the maintainer set, not an objection to it, but § Impact states only the write-access consequence and the not-silent claim.
- Fix: Add a paragraph to `plan.md` § Impact stating that during a registry outage the derived route loads the pre-placed library in preference to an already-installed one, that `refresh` and `setProperties` do the same and so a schema's recorded `driverPath` and `driverVersion` can change and change back with no operator action, and that two schemas created either side of an outage can therefore run different driver builds. Add a matching Background bullet to the `driver-path-override` delta, beside bullet 13, stating that the versioned presence check is unreachable on this trigger because no version was resolved.

## Requirement Quality

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: `plan.md` § Implementation Tasks 2.2 (`FallbackCause::RegistryUnreachable(error.to_string())`) and § Dead Code Removal (final line); `driver-provisioning/driver-path-override` delta § Scenario "An empty default location names the registry that answered nothing"; against `crates/adbc-vs-adapter/src/provisioning.rs:354-361`
- Issue: task 2.2 builds the last-resort error by embedding the rendered provisioning error — `Some(FallbackCause::RegistryUnreachable(error.to_string()))` — and § Dead Code Removal asserts nothing else changes, "including the unreachable-registry error the explicit route still raises". That error's `Display` ends: "supply the driver library yourself with the `DRIVER_PATH` property; **there is no path on the mount to pre-load it at**, because the install path carries a version only the registry could have resolved". The `NoDriverRoute` message on the new route therefore names `<mount>/adbc-drivers/<driver>/supplied/<library>` as the location it looked at and, in the same message, tells the operator no such path exists. That contradicts the delta scenario's "the adapter MUST return an error naming the default driver location it looked at" and Background bullet 12's "is named by the error an operator gets when nothing is there", and it re-offers the explicit route's remedy on the route the `driver-version-resolution` delta just finished scoping it away from (bullet 16: "Scoping this error rather than widening it keeps one route's remedy from being offered on a route where it is not the remedy"). The root cause is the shape of the predicate: `is_registry_unreachable` returns a bool, so `create_schema` cannot reach `RegistryUnreachable`'s own `url` and `cause` fields and has nothing to carry but the whole rendered message. No planned test catches it — `no_driver_route_names_the_registry_it_could_not_reach` asserts the message "contains the registry cause it was given", which the contradictory text satisfies.
- Fix: In `plan.md` § Design/Key Interfaces and § Implementation Tasks 2.2, replace the bool predicate with a structured accessor that hands the caller only the facts it needs — `pub fn registry_unreachable(&self) -> Option<(&str, &str)>` on `ProvisioningError`, returning the index URL and the transport cause for the narrowed variant and `None` otherwise — and change `FallbackCause::RegistryUnreachable` to carry those two values rather than `error.to_string()`. Keep the variant unexported. State in task 2.2 that `SchemaError::NoDriverRoute`'s `Display` composes the registry URL and cause into its own sentence, so no text from the explicit route's remedy reaches this message. Add a clause to task 2.2's `no_driver_route_names_the_registry_it_could_not_reach` bullet asserting the message does NOT contain "no path on the mount to pre-load", and add the same MUST NOT to the `driver-path-override` delta scenario "An empty default location names the registry that answered nothing". Update § Design/Patterns row 5 and § Consequences accordingly, and remove § Dead Code Removal's claim that the unreachable-registry error is wholly unchanged if the split in the Feasibility BLOCKER above alters its `Display`.

#### [AMBIGUOUS_REQUIREMENT] ADVISORY
- Location: `plan.md` § Design/Key Interfaces (`SchemaError::NoDriverRoute` row, `FallbackCause` row) and § Implementation Tasks 2.2
- Issue: the error is specified as `SchemaError::NoDriverRoute { driver, path, connection, fallback, cause }` — five fields — while `FallbackCause` is specified as `{ ConnectionUnresolved(String), RegistryUnreachable(String) }`, whose payload already *is* the cause, and `default_location_library(mount, driver, cause: FallbackCause)` takes three arguments and builds the error from them. An implementer cannot tell what the separate `cause` field holds, nor where `connection` comes from, nor what `connection` should hold on the `RegistryUnreachable` arm where the message "MUST NOT report the reserved connection as the failure". The plan's own rationale argues against the redundancy it then specifies: "Two variants rather than two `Option` fields, so the error cannot be built naming both causes or neither" — a `fallback` field beside a `cause` field reintroduces exactly the pairing that argument rules out.
- Fix: In `plan.md` § Design/Key Interfaces and § Implementation Tasks 2.2, reduce the variant to `SchemaError::NoDriverRoute { driver, path, fallback: FallbackCause }` and state that the `Display` arm names `DEFAULT_BUCKETFS_CONNECTION`, `BUCKETFS_CONNECTION_PROPERTY`, and `DRIVER_PATH_PROPERTY` from the constants rather than from fields, so the reserved connection is named as context on both arms and reported as the failure on the `ConnectionUnresolved` arm only.

## Design Depth

#### [INFORMATION_LEAKAGE] ADVISORY
- Location: `plan.md` § Implementation Tasks 2.2 (the `mount` bullet); `decision-log.md` § [14]; against `crates/adbc-vs-adapter/src/create_schema.rs:265-275`
- Issue: task 2.2 injects the mount into `open_driver_library` and stops there. `self_install_driver` keeps `Bucket::new(&address, BUCKETFS_MOUNT, ...)`, reading the module constant inside the branch that depends on it, so after the change one ambient decision has two owners in one module: the last-resort route computes its path under an injected mount and the self-install route under a compiled-in one. Decision `[14]` states the principle as "business logic reads no ambient state" and applies it to one of the two branches. The practical cost is in the disjointness argument the whole design rests on: `no_default_location_can_be_an_install_path` compares `default_driver_path` against `driver_install_path` under whatever mount each is handed, so the property is asserted across two mounts rather than one, and a unit test that pointed the default location at a temp directory would be comparing it with a `/buckets` install path.
- Fix: Add a bullet to task 2.2 in `plan.md` § Implementation Tasks: pass `open_driver_library`'s `mount` on to `self_install_driver` and have it hand that value to `Bucket::new` in place of `BUCKETFS_MOUNT`, so `open` is the module's only reader of the constant. Note in `decision-log.md` § [14] that both routes take the injected mount, and state in task 2.2's `no_default_location_can_be_an_install_path` bullet that both paths are computed under one mount value.

#### [INFORMATION_LEAKAGE] ADVISORY
- Location: `plan.md` § Implementation Tasks 3.0 (the `installed_drivers` narrowing bullet); against `crates/adbc-vs-adapter/tests/e2e_mysql_test.rs:1435-1441`
- Issue: task 3.0 narrows `installed_drivers` "to exclude any entry whose version segment fails `semver::Version::parse`", which puts a second, independent definition of "is this a version segment" in a file that already has one. `driver_semver` in the same file strips one optional leading `v` before parsing, and its doc comment gives that as the reason — "`v0.6.0` or `1.12.0`, the two spellings the registry index mixes". #### [PROSE_UNCLEAR] ADVISORY
