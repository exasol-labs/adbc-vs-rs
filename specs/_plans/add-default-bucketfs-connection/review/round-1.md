# Plan Review Findings: add-default-bucketfs-connection (round 1)

## Summary
- Axes checked: 6/6
- Total findings: 12 (Blockers: 4, Advisory: 8)
- Intent Fidelity blockers: 1

## Premortem

Three failure stories, each routed into the taxonomy below.

1. **Six months on, the air-gap feature has never fired.** Every cluster that followed the README holds an `ADBC_VS_BUCKETFS` connection. The last-resort route fires only when *no* BucketFS connection resolves, so an operator who pre-places a library and forgets `DRIVER_PATH` still gets a hard failure — the exact case issue #4's "Why" section says point 3 exists to soften. Routed to `[INTENT_DRIFT]`.
2. **The MySQL E2E binary panics with "installed driver version supplied is not a semantic version".** Tasks 3.2 and 3.3 write `adbc-drivers/mysql/supplied/libadbc_driver_mysql.so`, which sits inside the prefix the file's own `installed_drivers` helper scans. Routed to `[HIDDEN_DEPENDENCY]`.
3. **`/speq:record` merges a library that contradicts itself.** `driver-version-resolution`'s offline-fallback scenario is declared UNCHANGED, but its GIVEN is satisfiable by the configuration the new route serves, where the adapter succeeds instead of erroring and names a fixed pre-load path it forbids. Routed to `[REQUIREMENT_CONFLICT]`.

## Intent Fidelity

#### [INTENT_DRIFT] BLOCKER
- Location: `plan.md` § Migration (row 3) and § Design/Decision; `decision-log.md` § [4]; `specs/_plans/add-default-bucketfs-connection/driver-provisioning/driver-path-override/spec.md` § Background bullet 1
- Issue: issue #4's "Why" states the purpose of point 3 — "Point 3 also gives a soft landing when an operator pre-places a driver but forgets `DRIVER_PATH`: today that is a hard failure naming a missing property, not a fallback." The plan reaches the pre-placed location only when *no BucketFS connection resolves at all*: the delta says "the adapter looks when the statement named no `BUCKETFS_CONNECTION` and the reserved connection `ADBC_VS_BUCKETFS` did not resolve either, which is the point at which no write credential exists". `README.md:23` tells every operator to create `ADBC_VS_BUCKETFS`, and decision `[1]`'s own rationale is that "a cluster that followed the README needs no change at all". On such a cluster — connection present, no outbound egress, library pre-placed, `DRIVER_PATH` forgotten — the statement still hard-fails, now with an unreachable-registry error instead of a missing-property one. The soft landing the user named is delivered only on a cluster that has deleted the connection the same plan tells it to keep. `plan.md` § Migration row 3 compounds this: "place the library at `/buckets/bfsdefault/default/adbc-drivers/<driver>/supplied/<library>` and set neither property" states no precondition, so an operator reading it will pre-place a library that is never loaded.
- Fix: In `plan.md` § Migration, rewrite row 3's New cell to state the precondition explicitly — the pre-placed location answers only on a cluster where no `CONNECTION` named `ADBC_VS_BUCKETFS` resolves, and `DRIVER_PATH` remains the route for a cluster that holds that connection. Add a `## Open Questions` section to `plan.md` naming this one question for the human: whether issue #4 point 3's soft landing must also fire when `ADBC_VS_BUCKETFS` resolves but the registry is unreachable, which decision `[3]` currently forbids as a silent fallback. Add a matching `[plan-review]` entry to `decision-log.md` § Review Findings recording that the headless run could not settle it. Mirror the precondition into `driver-path-override`'s Background bullet 1 and into `plan.md` § Impact's closing sentence.

#### [SCOPE_REDUCTION] ADVISORY
- Location: `plan.md` § Design/Context Non-Goals; `decision-log.md` § [3]
- Issue: issue #4 point 4 reads "this only changes how the presence check resolves that location for the look-before-installing step", and its Scope note names "how 'look for the default' interacts with the presence check's existing BucketFS read" as a question the plan must answer. `plan.md` § Non-Goals answers by removing the subject: "no change to version resolution, to the presence check". The rationale in decision `[3]` is sound — a pre-index-read consult reintroduces the "answers for whichever version arrived first" defect — but a numbered point of the user's proposed behavior is declined in a headless run with no escalation recorded, while `decision-log.md` § Interview asserts "Nothing reached the escalation bar".
- Fix: Add this question to the `## Open Questions` section required by the `[INTENT_DRIFT]` fix above, stating that point 4's presence-check clause was declined on decision `[3]`'s grounds and needs human ratification.

## Feasibility

#### [HIDDEN_DEPENDENCY] BLOCKER
- Location: `plan.md` § Implementation Tasks 3.2 and 3.3, against `crates/adbc-vs-adapter/tests/e2e_mysql_test.rs:33-34,1414-1453`
- Issue: tasks 3.2 and 3.3 both "copy the installed driver to `adbc-drivers/mysql/supplied/libadbc_driver_mysql.so`". That path matches the file's existing scan predicate exactly — `DRIVER_BUCKET_PREFIX` is `"adbc-drivers/mysql/"` and `DRIVER_LIBRARY` is `"libadbc_driver_mysql.so"`, and `installed_drivers` filters `entry.starts_with(DRIVER_BUCKET_PREFIX) && entry.ends_with(DRIVER_LIBRARY)`. Three consequences the plan never surfaces. First, `installed_driver` maps every match through `installed_version` then `driver_semver`, which `panic!`s on anything `Version::parse` rejects — so any call while a supplied copy exists dies with "installed driver version supplied is not a semantic version". Task 3.2's assertion that `adapterNotes["driverPath"]` "MUST be the versioned install path" needs that path, and the obvious source is `installed_driver`. Second, `driver_lands_in_bucketfs` calls `installed_driver` unconditionally and will panic if any copy lingers after a failed run. Third, `first_use_installs_driver_from_registry` deletes every entry `installed_drivers` returns, so it would silently delete the operator-owned file whose survival task 2.3 exists to assert. The plan lists three new helpers (`copy_bucket_object`, `supplied_path_for`, `create_virtual_schema_through_expecting_failure`) and does not mention these three existing ones.
- Fix: Add a task 3.0 to `plan.md` § Implementation Tasks, ordered before 3.1 in Group C: narrow `crates/adbc-vs-adapter/tests/e2e_mysql_test.rs`'s `installed_drivers` to exclude the supplied segment (filter out any entry whose version segment fails `semver::Version::parse`, rather than panicking on it), add a `SUPPLIED_BUCKET_PATH` constant beside `DRIVER_BUCKET_PREFIX` for the tests to spell the location once, and state in `installed_drivers`' doc comment that the operator-owned `supplied` object is deliberately not an installed driver. Add a bullet to tasks 3.2 and 3.3 requiring the versioned path be captured before the copy is made. Add task 3.0 to the § Parallelization Group C row.

#### [EFFORT_MISESTIMATION] ADVISORY
- Location: `plan.md` § Implementation Tasks 3.1, 3.2, 3.3, against `crates/adbc-vs-adapter/tests/e2e_mysql_test.rs:1457`
- Issue: all three tasks read `adapterNotes` for a schema they create — `DEFAULTVS` in 3.1, an unnamed one in 3.2 and 3.3. The MySQL binary's helper is `fn adapter_notes(stack: &stack::Stack)` and hardcodes `VIRTUAL_SCHEMA`; only the PostgreSQL binary has the per-schema form `fn adapter_notes(schema: &str)`. Every task states its assertions as if a per-schema reader already exists, so a helper change and its call-site updates across the MySQL binary are unbudgeted work inside three tasks the plan presents as test additions.
- Fix: Add a bullet to task 3.1 in `plan.md` § Implementation Tasks: change `e2e_mysql_test.rs`'s `adapter_notes` to take the schema name, matching `e2e_postgres_test.rs:1057`, and update its existing call sites in the same task.

#### [NFR_IGNORED] ADVISORY
- Location: `plan.md` § Implementation Tasks 3.3
- Issue: task 3.3 drops `ADBC_VS_BUCKETFS`, which the shared setup module created and every other test in the binary depends on, and restores it seven steps later. The task guards only against assertion failures — "every assertion held until the end". It does not guard against a panic raised by a helper inside the sequence: `create_virtual_schema_through` panics on an unexpected SQL failure, and the step "create the schema again" is precisely the step most likely to fail if the pre-placed route misbehaves. A panic there leaves the connection dropped for every later test in a `--test-threads=1` binary, so one real defect surfaces as a cascade that hides it.
- Fix: Add a bullet to task 3.3 in `plan.md` § Implementation Tasks requiring the drop-and-restore of `ADBC_VS_BUCKETFS` and the deletion of the copied object be held by a `Drop` guard, so a panic anywhere in the sequence still restores the shared stack.

#### [NFR_IGNORED] ADVISORY
- Location: `plan.md` § Impact; `driver-self-install` delta § Background bullet 8
- Issue: `plan.md` § Impact addresses one security consequence — that resolving `ADBC_VS_BUCKETFS` "grants no credential the session did not already hold" — and omits the other. `adbc-drivers/<driver>/supplied/<library>` becomes a fixed, documented path from which the adapter loads native code into the UDF sandbox with no statement naming it, and the `driver-self-install` delta makes it a location self-install "neither reads, writes, nor deletes". Anyone holding BucketFS write credentials can therefore leave a library there permanently, and no later install ever overwrites it. `DRIVER_PATH` at least required an explicit statement to load an operator file.
- Fix: Add a sentence to `plan.md` § Impact's final paragraph stating who can write `adbc-drivers/<driver>/supplied/` (any holder of the BucketFS write credential), that self-install never overwrites or removes what is there, and that the route loads it without any statement naming it.

## Requirement Quality

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: `plan.md` § Features (`driver-provisioning/driver-version-resolution` row, marked UNCHANGED); `decision-log.md` § [6]; against `specs/driver-provisioning/driver-version-resolution/spec.md:66-72`
- Issue: the recorded scenario "Unreachable registry names the offline fallback" is left unchanged, and its GIVEN is only "a cluster whose UDFs have no outbound HTTPS egress" and "a request that set no `DRIVER_PATH`". It does not scope itself to the self-install route, so the new no-connection configuration satisfies it and contradicts three of its clauses. With a library pre-placed, the adapter succeeds, against "the adapter MUST return an error" and against "the adapter MUST NOT load an unrelated version it finds on the mount". Without one, the adapter returns `NoDriverRoute`, which by the `driver-path-override` delta "MUST name the default driver location it looked at" — against "the error message MUST NOT name a fixed BucketFS path to pre-load" — and never reaches the registry, so it cannot "name the registry host it could not reach". Decision `[6]`'s rationale ("Both clauses stay true on the self-install route, which is the only route that reaches that error") is the scoping the scenario text lacks; it is asserted in the decision log and absent from the spec that `/speq:record` will merge.
- Fix: Change `driver-provisioning/driver-version-resolution`'s row in `plan.md` § Features from UNCHANGED to CHANGED and add `specs/_plans/add-default-bucketfs-connection/driver-provisioning/driver-version-resolution/spec.md`. In that delta, wrap the "Unreachable registry names the offline fallback" scenario in `DELTA:CHANGED` and add a GIVEN clause scoping it to the self-install route — a request whose BucketFS connection resolves, whether named by `BUCKETFS_CONNECTION` or the reserved `ADBC_VS_BUCKETFS`. Add a Background bullet stating that a request reaching no BucketFS connection at all never reaches this error, and that `driver-provisioning/driver-path-override` owns what happens then. Add a `Verification` row and a task bullet under 2.2 for the scenario's unchanged tests.

## Task Breakdown

#### [TRACEABILITY_GAP] BLOCKER
- Location: `plan.md` § Verification/Scenario Coverage, rows for `driver-path-override` — "The default driver location is used when no BucketFS connection resolves" and "No driver on any route fails naming every route"
- Issue: both new scenarios carry a MUST NOT clause about the registry and BucketFS — "the adapter MUST NOT request the registry index, resolve a version range, download a package, or write to BucketFS" and "the adapter MUST NOT request the registry index, download a package, or write to BucketFS". The only tests mapped to either are `a_preplaced_library_answers_when_no_bucketfs_connection_resolves` and the unit test `no_driver_route_names_the_location_the_connection_and_both_properties`. The E2E stack has working egress, so it cannot observe a registry request that did not happen, and the unit test asserts message composition only. The same clause on the `DRIVER_PATH` route already has a dedicated test — `crates/adbc-vs-adapter/tests/provisioning_test.rs::the_driver_path_route_makes_no_registry_request` — and no equivalent is planned for the default-location route, so a regression that made the last-resort route read the index would pass every planned check.
- Fix: Add a bullet to task 2.2 in `plan.md` § Implementation Tasks: add `the_default_location_route_makes_no_registry_request` to `crates/adbc-vs-adapter/tests/provisioning_test.rs`, modelled on `the_driver_path_route_makes_no_registry_request`, asserting the stub registry recorded zero requests and the write-accepting BucketFS stub recorded zero `PUT`s for both the readable-library and the empty-location cases. Add two `Verification` rows naming it against both scenarios' no-registry clauses.

#### [COMPLETENESS_GAP] ADVISORY
- Location: `create-virtual-schema` delta § Scenario "The BucketFS write credential is resolved by precedence", final clause; `plan.md` § Verification/Scenario Coverage
- Issue: the clause "the same precedence MUST apply to `refresh` and `setProperties`, which resolve the credential from the properties they are answered under rather than from the route creation took" has no mapped test. It is not free behavior: `create_schema::read_properties` treats a top-level `null` as a property removal, so a `setProperties` that nulls `BUCKETFS_CONNECTION` on a schema created with an explicit one now silently switches that schema to the reserved connection, where today it would fail naming the missing property. The plan maps clauses elsewhere ("per-driver layout clause", "message-composition clause", "disjointness clause"), so this omission is inconsistent with its own standard.
- Fix: Add a bullet to task 2.1 in `plan.md` § Implementation Tasks: add a unit test to `crates/adbc-vs-adapter/src/create_schema_tests.rs` asserting that a `setProperties` request nulling `BUCKETFS_CONNECTION` over `schemaMetadataInfo.properties` that carried one yields `DriverSource::DefaultBucketFs`. Add a matching `Verification` row for the refresh/`setProperties` clause.

## Design Depth

#### [BOUNDARY_VIOLATION] ADVISORY
- Location: `plan.md` § Implementation Tasks 2.2 — "computes `provisioning::default_driver_path(Path::new(BUCKETFS_MOUNT), driver)`"; `crates/adbc-vs-adapter/src/create_schema.rs:36`
- Issue: `BUCKETFS_MOUNT` is a compile-time constant, so the branch that decides whether the last-resort route succeeds reads ambient host state no caller injects. Two consequences. The success branch — `readable_library` accepts, return `DriverLibrary::supplied(path)` — cannot be exercised below the E2E tier at all, which is why § Verification maps it to one E2E test and nothing else. And the planned unit test `no_driver_route_names_the_location_the_connection_and_both_properties` passes only because the host running `make test` happens not to have `/buckets/bfsdefault/default/adbc-drivers/mysql/supplied/libadbc_driver_mysql.so`; it asserts a branch chosen by the absence of a path outside the workspace. `/speq:design-philosophy` requires business logic to read no ambient state.
- Fix: In `plan.md` § Implementation Tasks 2.2 and § Design/Key Interfaces, thread the mount into the decision instead of reading the constant inside it: give `open_driver_library` a mount parameter that `open` passes `BUCKETFS_MOUNT` to, so `create_schema_tests.rs` can point both branches at a temp directory. Add a unit test to task 2.2 for the success branch — a readable library under an injected mount yields `DriverLibrary::supplied` with no version — and add its `Verification` row.
