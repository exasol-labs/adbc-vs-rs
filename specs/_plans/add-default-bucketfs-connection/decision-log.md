# Decision Log: add-default-bucketfs-connection

## Interview

Headless first pass, then five answers from the maintainer across three review rounds. The issue body stood in for the interview and every decision below was assumed and documented per `/speq:planning`'s Headless Mode. Round-1 review raised an Intent Fidelity blocker the headless run could not settle, the plan was persisted as blocked, and the maintainer answered both open questions directly. Round-2 review then raised two blockers about how that widening was operationalized, and the maintainer approved both fixes directly. Round-3 review found the round-2 message fix incomplete on a sibling error variant, and the maintainer directed the wider fix. Decisions `[11]` to `[15]` and the `[human]` entries under Review Findings record those answers; decisions `[3]`, `[4]`, `[6]`, `[12]`, `[14]` and `[15]` carry a revision note pointing at them.

**Q:** (round 1, to the maintainer) Must issue #4 point 3's soft landing also fire when `ADBC_VS_BUCKETFS` resolves but the registry is unreachable, which decision `[3]` forbade as a silent fallback?
**A:** (maintainer) Yes. The fallback MUST fire in that case too, because a cluster that followed the README holds the reserved connection, and an air-gapped one has no egress — the configuration point 3 exists for. The widening applies to the reserved connection route alone: an explicit `BUCKETFS_CONNECTION` MUST continue to never fall back, per issue #4's own "Why".

**Q:** (round 1, to the maintainer) Does declining issue #4 point 4's presence-check interaction need separate ratification, or does decision `[3]`'s rationale settle it?
**A:** (maintainer) The plan's own rationale settles it. No separate sign-off is needed; record the resolution so it is not silently dropped.

**Q:** (round 2, to the maintainer) `ProvisioningError::RegistryUnreachable` covers three failures, not one: the index request reaching no host, the package request reaching no host, and a body that stopped arriving after its status did. The last two happen after a version was resolved and the presence check ran, so the fallback would fire on a reset 46 MB download. Narrow the trigger, or accept the wider one?
**A:** (maintainer) Narrow it. Split the variant before the predicate is written: `PackageUnreachable` for the package leg, its own variant for a body-read failure after a received status, and `RegistryUnreachable` for a connect-, DNS-, or TLS-level failure of the index request alone. Add a test that a package download failing mid-transfer is not an unreachable registry.

**Q:** (round 2, to the maintainer) The last-resort error embeds the rendered provisioning error, whose text ends "there is no path on the mount to pre-load it at". That denies the location the same message says it looked at. Split the message, or keep one rendered text?
**A:** (maintainer) Split it. Replace the bool predicate with a structured accessor returning the index URL and the transport cause, have `FallbackCause` carry those two values, and have `NoDriverRoute`'s `Display` compose its own sentence. No text from the explicit route's remedy may reach the new route's error.

**Q:** (round 3, to the maintainer) `ProvisioningError::RegistryRejected`'s own `Display` ends with the same "there is no path on the mount to pre-load it at" clause, and after this plan that variant is reachable on the derived route — a CDN answering HTTP 503. Reword it on `RegistryRejected` alone, or on every route including the explicit one?

**A:** (maintainer) Reword it everywhere, including the explicit route. The old wording is no longer true anywhere in the product, because the path now exists. Keep the clause removed on every route rather than special-casing the explicit one.

**Q:** What is the problem?
**A:** (issue #4) `createVirtualSchema` requires `BUCKETFS_CONNECTION` whenever `DRIVER_PATH` is absent. Every virtual schema must name its own BucketFS write credential explicitly, even though most virtual schemas on one cluster share the same BucketFS target.

**Q:** What behavior is proposed?
**A:** (issue #4) Four points. (1) A default `BUCKETFS_CONNECTION` exists — the adapter looks up a reserved connection name, naming to be picked by the plan, before failing on a missing property. (2) An explicit `BUCKETFS_CONNECTION` property overrides the default. (3) If both the default and the explicit property are absent, assume the driver is already placed in BucketFS and skip self-install entirely, the same operator-vouches-for-it contract `DRIVER_PATH` has, reached without requiring `DRIVER_PATH`. (4) Drivers get a default BucketFS location too; `DRIVER_PATH`, when set, still overrides it.

**Q:** What is in scope?
**A:** (issue #4) `driver-provisioning/driver-self-install`, `driver-provisioning/driver-path-override`, and `vs-adapter/create-virtual-schema`'s "Missing required property fails with a named error" scenario. The issue names the reserved default-connection name and the interaction between "look for the default" and the presence check's existing BucketFS read as the two questions the plan must answer.

**Q:** What must the plan not do?
**A:** (orchestrator) This is a framework-level change. Per `CLAUDE.md` § Spec governance, no `<technology>-*` feature is needed and no `e2e/`, `toolchain/`, `ci/`, or `licensing/` spec group may be created.

## Design Decisions

### [1] Reserve `ADBC_VS_BUCKETFS` as the default BucketFS connection name

- **Decision:** The adapter resolves the `CONNECTION` object named `ADBC_VS_BUCKETFS` when a statement carries no `BUCKETFS_CONNECTION` property. The name is compiled in as `create_schema::DEFAULT_BUCKETFS_CONNECTION` and is not configurable.
- **Alternatives:** `ADBC_VS_BUCKETFS_CONNECTION`, which restates the object's kind in its name. A `DEFAULT_BUCKETFS_CONNECTION` property naming the default, which is a default that is not one and adds the fifth property the feature exists to avoid. A bare `BUCKETFS`, which is unscoped and could collide with an operator's own connection.
- **Rationale:** The name is not an invention. `README.md`'s quick start, both end-to-end harnesses, and `tests/common/schema.rs` already use exactly `ADBC_VS_BUCKETFS` for this object, so the convention being reserved is the one the project already documents, and a cluster that followed the README gains the shorter statement with no change at all. It is a valid unquoted Exasol identifier, so `CREATE CONNECTION ADBC_VS_BUCKETFS ...` needs no quoting, and the `ADBC_VS_` prefix scopes it to this product.
- **Promotes to ADR:** yes

### [2] Give the pre-placed route its own version-free location, `adbc-drivers/<driver>/supplied/<library>`

- **Decision:** The default driver location is `<mount>/adbc-drivers/<driver>/supplied/<library>`. It is separate from the versioned install path, carries no version segment, is read by the adapter and never written by it, and is the location the last-resort route uses.
- **Alternatives:** Reuse the versioned install path `<mount>/adbc-drivers/<driver>/<version>/<library>`, which an air-gapped operator cannot pre-place at because the version comes from a registry read they cannot perform. A `default` segment, which reads as a version and produces `/buckets/bfsdefault/default/adbc-drivers/mysql/default/...`. A separate `adbc-drivers/supplied/<driver>/` subtree, which buys nothing over a per-driver segment and puts two layouts in the same directory's first level.
- **Rationale:** ADR 003 rejected keeping release 0.2's pre-load fallback on two grounds — the path was not a supported input, and it stopped being fixed once the install path carried a version. Both are answered here rather than waived: this location is stated by `driver-provisioning/driver-path-override`, is named by the error an operator gets when nothing is there, and is version-independent by construction. `supplied` names who owns the file, matches `provisioning::supplied_driver`'s vocabulary, and can never collide with an install path, because that path's third segment is always a parsed `semver::Version` and no version parses as `supplied`.
- **Promotes to ADR:** yes

### [3] Consult the default location last, never as a pre-registry short-circuit

- **Decision:** Self-install is unchanged: it reads the registry index first, resolves the version, and tests the versioned presence check. The default location is reached only when no BucketFS connection resolves at all. A library sitting there never satisfies the versioned presence check and never short-circuits an install.
- **Alternatives:** Check the default location first as a cheap stat before the index read. Fall back to it when the registry is unreachable.
- **Rationale:** `provisioning.rs` states why the install path carries a version: an unversioned path "would have made it answer for whichever version arrived first, so a range would resolve once per cluster and never again." Any location consulted before the index read reintroduces exactly that defect, and a stale pre-placed library would then shadow self-install forever. Falling back on an unreachable registry is a silent fallback, which `driver-path-override` already forbids because it turns an operator's typo into a slow first query.
- **Revised:** the first half stands and the second is reversed, per the maintainer's answer recorded in decision `[11]`. The default location is still never consulted before the index read. It IS now consulted after an index read that reached nothing at all, which does not reintroduce the version-first defect — see `[11]`'s rationale. The fallback is also not silent: the notes record the pre-placed path and no version.
- **Promotes to ADR:** yes

### [4] Fall through on the reserved-connection route; never when an explicit property does

- **Decision:** Any failure to resolve `ADBC_VS_BUCKETFS` moves to the default driver location, carrying the failure's cause into the eventual error. A `BUCKETFS_CONNECTION` the statement named, and a `DRIVER_PATH` it named, never fall back to anything.
- **Revised:** the scope now covers two failures rather than one, per decision `[11]`. The reserved-connection route falls through both when `ADBC_VS_BUCKETFS` does not resolve and when it resolves and the registry answers nothing at all. Both explicit routes still fall back on neither failure — a failed resolution and an unreachable registry alike surface unchanged — which is the boundary the maintainer's answer stated and decision `[12]` bounds.
- **Alternatives:** Fail the statement on any resolution failure, which makes point 3 of the issue unreachable. Distinguish "no such connection" from "no access" and fall through only for the former.
- **Rationale:** The distinction cannot be drawn: `exasol_udf_sdk::error::UdfError` reports every resolution failure as one opaque `ConnectBack(String)`, with no structured not-found variant. Falling through is nonetheless safe. Exasol enforces access to a `CONNECTION` object at resolution, so a session that cannot resolve `ADBC_VS_BUCKETFS` was never entitled to its credentials and no privilege is gained. And `create_schema::open` resolves the source `CONNECTION` before it reaches the driver route, so a connect-back transport that is broken has already failed the statement — a resolution failure at this point is a fact about the connection, not about the transport. Carrying the cause into the last-resort error keeps a permission misconfiguration diagnosable rather than reported as a missing file.
- **Promotes to ADR:** yes

### [5] Extend `driver-provisioning/driver-path-override` rather than add a fourth provisioning feature

- **Decision:** `driver-path-override` owns both operator-supplied routes. Its Feature-description line broadens; its name does not change.
- **Alternatives:** A new `driver-provisioning/driver-preplaced-default` feature. Renaming the feature to something route-neutral, such as `operator-supplied-driver`.
- **Rationale:** The two routes reach the same three obligations — use exactly this file, assert only readability, never fall back — and differ only in where the path string came from. A second feature would be two shallow owners of one mechanism, which is the classitis `/speq:design-philosophy` warns against, and would leave the no-fallback rule stated twice with nothing keeping the two statements in agreement. The name is kept because `CLAUDE.md`, `specs/_decision/003-add-postgresql-support.md`, and three other feature specs reference it, and `specs/_decision/` is append-only history that a rename would leave pointing at nothing.
- **Promotes to ADR:** no

### [6] Leave `driver-provisioning/driver-version-resolution` untouched

- **Decision:** The unreachable-registry error keeps naming `DRIVER_PATH` alone, and keeps its clause forbidding a fixed BucketFS path to pre-load and forbidding the adapter from loading an unrelated version found on the mount.
- **Alternatives:** Extend that error to also name the default driver location as a remedy.
- **Rationale:** Both clauses stay true on the self-install route, which is the only route that reaches that error: the versioned path is still unknowable without the index, and the default location is still never loaded there. Naming the default location would be advice an operator cannot act on, because reaching it requires a cluster with no BucketFS connection at all — on a cluster with a shared `ADBC_VS_BUCKETFS`, that is not a change one statement can make. `DRIVER_PATH` remains the one-statement remedy the error already names.
- **Revised: reversed.** Its premise fails once decision `[11]` widens the trigger: the reserved-connection route now reaches the registry and no longer surfaces that error, so "the only route that reaches that error" is false. Decision `[13]` replaces this one. Round 1's `[REQUIREMENT_CONFLICT]` blocker had already found the unrevised version wrong for a second reason — the recorded scenario's GIVEN was never scoped to a route at all.
- **Promotes to ADR:** no

### [7] Keep route selection a pure function of the properties

- **Decision:** `create_schema::driver_source` gains a third variant, `DefaultBucketFs`, and stays a pure function of the property map. Resolving the reserved connection and testing the default location both happen in `open_driver_library`, where the UDF context already is.
- **Alternatives:** Pass `ctx` into `driver_source` and have it return a fully resolved route.
- **Rationale:** `create_schema`'s module comment states the property that ordering protects: every property is validated before any `CONNECTION` is resolved, so a statement that could never provision is refused without reaching anything outside the process. Threading `ctx` into route selection would put a connect-back round trip ahead of that validation and would make the pure route-selection unit tests need a fake context.
- **Promotes to ADR:** no

### [8] One shared definition of "a readable driver library"

- **Decision:** Extract `provisioning::readable_library(path) -> Result<(), String>` from `supplied_driver` and have both operator-supplied routes call it, each phrasing its own error over the shared cause. `supplied_driver` gains no parameter selecting which error to build.
- **Alternatives:** Have `create_schema` test the default location with a bare `Path::is_file`. Add a route descriptor parameter to `supplied_driver`.
- **Rationale:** Two callers deciding independently what counts as readable is back-door leakage — `supplied_driver` already refuses a directory as well as a missing file, and a second caller checking only `is_file` would accept what the first refuses. A route-selecting parameter is a decision the function declined to make, and the two messages differ in more than a word: they name different properties and different remedies.
- **Promotes to ADR:** no

### [9] Prove the connection probe is recoverable before building on it

- **Decision:** Task 1.1 is a live end-to-end assertion that a `BUCKETFS_CONNECTION` naming no existing `CONNECTION` object surfaces as the adapter's own error. Tasks 2.2 and 3.3 depend on its result, and the task states that a failure is a finding to report rather than a bug to work around.
- **Alternatives:** Assume recoverability and discover it during implementation. Design a second mechanism as a hedge.
- **Rationale:** `UdfContext::connection`'s body in `exasol-udf-sdk` 0.23.0 is a default returning `Unimplemented`; the real implementation lives in the script language container's host bridge, which is not in this workspace, and no test in this repository resolves a connection that does not exist. Point 3 of the issue is unreachable if the host aborts the statement instead of answering. Points 1, 2 and 4 do not depend on it, so the plan is still worth most of its value if the probe fails — which is why the dependency is stated rather than hedged with a second design.
- **Promotes to ADR:** no

### [10] `BUCKETFS_CONNECTION` becomes optional unconditionally, and its missing-property error is deleted

- **Decision:** `create-virtual-schema`'s "Missing required property fails with a named error" scenario keeps `DRIVER` and `CONNECTION_NAME` and loses every `BUCKETFS_CONNECTION` clause. The `required_property` call and the unit test asserting that error are removed.
- **Alternatives:** Keep the error as a fallback for a cluster with no reserved connection, raising it instead of the new last-resort error.
- **Rationale:** After this change the property is never required, so an error naming it as missing would be false. The information it carried is not lost: the new error names both `BUCKETFS_CONNECTION` and `DRIVER_PATH` as the explicit routes, alongside the reserved connection and the location the adapter actually looked at, which is strictly more than the old message said.
- **Promotes to ADR:** no

### [11] Reach the default driver location when the registry answers nothing through the reserved connection

- **Decision:** The last-resort route has two triggers, not one. The default driver location answers when `ADBC_VS_BUCKETFS` does not resolve, and when it resolves and self-install through it reaches a registry that answered nothing at all. Both triggers produce the same result: the pre-placed library, recorded in `adapterNotes` with no driver version. **Human-directed** — the maintainer answered round 1's Intent Fidelity blocker, and this is not a headless assumption. Supersedes the trigger half of decision `[3]`, "Consult the default location last, never as a pre-registry short-circuit", and reverses decision `[6]`, "Leave `driver-provisioning/driver-version-resolution` untouched".
- **Alternatives:** The no-connection-only trigger the headless pass chose, which round 1 flagged as intent drift. Widening the trigger to every provisioning failure, rejected by decision `[12]`.
- **Rationale:** The narrow trigger delivered the soft landing only to a cluster that had deleted the connection `README.md` tells every operator to create, so the air-gapped cluster issue #4's "Why" describes — reserved connection present, no HTTPS egress, library pre-placed, `DRIVER_PATH` forgotten — still hard-failed. The version-first defect decision `[3]` guards against survives the widening, because the fallback happens after a failed index read rather than before a successful one: nothing resolved, nothing installed, and the next statement reads the index again, so a pre-placed library shadows self-install for exactly as long as the registry stays unreachable. The fallback is also not the silent one `driver-path-override` forbids: the notes record the pre-placed path and no version, which is the same signature `DRIVER_PATH` leaves, so an operator reads back which route answered.
- **Promotes to ADR:** yes

### [12] Only the registry index request reaching no host at all triggers the fallback

- **Decision:** `ProvisioningError::registry_unreachable` answers `Some((index URL, transport cause))` for a connect-, DNS-, or TLS-level failure of the index request, and `None` for everything else. Reaching that boundary needs the taxonomy split first: `RegistryUnreachable` covered four failures, and three of them move out. The two axes are the leg and the point of failure, so the mapping is a four-row table: index plus a connect-level failure is `RegistryUnreachable` and fires the fallback; index plus a body that stopped arriving is `TransferInterrupted`; package plus a connect-level failure is `PackageUnreachable`; package plus a body that stopped arriving is `TransferInterrupted`. The three excluded rows fail the statement on every route, as do a registry that answered any HTTP status, an index that will not parse, a range no published version satisfies, a resolved version with no `linux_amd64` package, an archive that will not unpack, and every BucketFS failure. The accessor lives in `provisioning`, beside the taxonomy that answers it, and is written as a `match` over every variant with no wildcard arm so a variant added later stops the crate compiling.
- **Alternatives:** Fall back on any `ProvisioningError`, which is the simplest reading of "self-install could not run". Fall back on `RegistryRejected` as well, on the argument that a proxy answering 403 is also an air gap. Export the variant and let `create_schema` match on it. Keep one variant covering all three transport failures and state the boundary in prose, which round 2 found unenforceable.
- **Rationale:** An air gap is the one condition under which nothing answers, and it is the condition the fallback exists for. Every other failure means something answered, so falling back on it would pin a cluster to whatever library was pre-placed through a transient CDN outage or a bad package, with a stale library loading for as long as nobody noticed. `RegistryRejected` is excluded for the same reason: HTTP 503 from the CDN and HTTP 403 from a proxy are indistinguishable in the status alone, and the failure mode of guessing wrong is silent staleness. The two package-leg rows are excluded on a second ground as well: both run after the index was read, a version was resolved, and the versioned presence check ran, so decision `[11]`'s "nothing resolved, nothing installed" argument does not reach them. A 600-second transfer timeout on a 46 MB body is the transient condition this decision exists to exclude, and before the split it was the condition that fired the fallback. Keeping the accessor in `provisioning` rather than exporting the variant means `create_schema` asks the question in its own vocabulary and learns no variant name, so the error taxonomy can grow without a second module needing an edit.
- **Revised:** the boundary is narrowed and the predicate reshaped, per round 2's Feasibility `[UNSTATED_ASSUMPTION]` and Requirement Quality `[REQUIREMENT_CONFLICT]` blockers, both answered by the maintainer. The original text read "true for `RegistryUnreachable` alone", which named a variant that did not mean what the decision assumed. The predicate is also no longer a bool: see decision `[15]`.
- **Revised again:** the split covers four cases rather than three, and its stated ground changes, per round 3's Feasibility `[UNSTATED_ASSUMPTION]`. `download` is shared by both legs, so the index request's own body can stop arriving too — a proxy that answers HTTP 200 for `index.yaml` and then drops the connection. The after-resolution argument is false for that row: nothing was resolved and nothing was installed. The ground that holds for all three excluded rows is that the registry answered, so nothing about the cluster's egress was learned, and that is the ground `plan.md`, both spec deltas and this entry now state first. The after-resolution argument survives as a second ground for the package leg alone. Round 3's `[COMPLETENESS_GAP]` also replaced "a variant added later must force this test to be revisited" with the wildcard-free `match` that actually forces it.
- **Promotes to ADR:** yes

### [13] Scope `driver-version-resolution`'s unreachable-registry error to the explicit route

- **Decision:** The recorded scenario "Unreachable registry names the offline fallback" gains a GIVEN clause binding it to a request whose `BUCKETFS_CONNECTION` property named a `CONNECTION` that resolved. Its THEN clauses are unchanged, and one clause is added: the adapter MUST NOT fall back to the default driver location on that route. Supersedes decision `[6]`, "Leave `driver-provisioning/driver-version-resolution` untouched".
- **Alternatives:** Leave the feature untouched, as the headless pass did. Extend the error to name the default driver location as a remedy on every route.
- **Rationale:** Two of the three routes no longer reach that error — `DRIVER_PATH` reads no index, and the reserved-connection route answers an unreachable registry from the default location — so an unscoped GIVEN describes configurations the adapter now answers differently. Round 1's `[REQUIREMENT_CONFLICT]` blocker showed the unscoped text contradicting itself in three clauses at once against the new route. Naming the default location inside that error would offer the pre-placed remedy on the one route that refuses it, which is worse than saying nothing.
- **Promotes to ADR:** no

### [14] Inject the BucketFS mount into the route that decides on it

- **Decision:** `open_driver_library` takes a `mount: &Path`, which `open` supplies as `Path::new(BUCKETFS_MOUNT)`. The last-resort route computes the default location under the mount it was given rather than reading the constant inside the branch.
- **Alternatives:** Read `BUCKETFS_MOUNT` inside the branch, as the pre-review plan did.
- **Rationale:** `/speq:design-philosophy` requires business logic to read no ambient state, and the practical cost of the violation was a test gap: a branch chosen by whether a path outside the workspace exists cannot be asserted below the E2E tier, and the planned unit test for the error branch would have passed only because the host running `make test` happens to hold no `/buckets` mount. Constructing the concrete value at the entry point is where Clean Architecture puts it. Raised as round 1's `[BOUNDARY_VIOLATION]`.
- **Extended:** both routes take the injected mount, not one. `self_install_driver` hands it to `Bucket::new` in place of `BUCKETFS_MOUNT`, so `open` is the module's only reader of the constant. Injecting it on one branch alone left one ambient decision with two owners in one module, and made `no_default_location_can_be_an_install_path` compare a default location under a temp directory against an install path under `/buckets`. The disjointness the whole design rests on is only a property when both paths are computed under one mount value. Raised as round 2's Design Depth `[INFORMATION_LEAKAGE]`.
- **Promotes to ADR:** no

### [15] Hand `create_schema` two facts rather than a rendered provisioning error

- **Decision:** `ProvisioningError::registry_unreachable(&self) -> Option<(&str, &str)>` replaces the bool predicate and returns the index URL and the transport cause. `FallbackCause::RegistryUnreachable { url, cause }` carries those two values. `SchemaError::NoDriverRoute { driver, path, fallback: FallbackCause }` has three fields, and its `Display` names `DEFAULT_BUCKETFS_CONNECTION`, `BUCKETFS_CONNECTION_PROPERTY` and `DRIVER_PATH_PROPERTY` from the constants rather than from fields. **Human-directed** — the maintainer approved the split after round 2's Requirement Quality blocker, and this is not a headless assumption.
- **Alternatives:** Keep the bool predicate and embed `error.to_string()` in the last-resort error, which is what round 2 found. Export `RegistryUnreachable` and let `create_schema` match its fields directly. Keep five fields on `NoDriverRoute`, carrying the connection name and a second cause beside `fallback`.
- **Rationale:** A bool answers "was it unreachable" and hands back nothing to say it with, so the caller's only material is the whole rendered message. That message ended "there is no path on the mount to pre-load it at, because the install path carries a version only the registry could have resolved", and it names `DRIVER_PATH` as the remedy, which is the explicit route's answer. Quoting it would make the new route's error deny the location the same message names as the one it looked at, contradicting `driver-path-override`'s own scenario and re-offering a remedy `driver-version-resolution` had just finished scoping away. Two facts let each route phrase its own sentence over one shared answer, which is the rule `readable_library` already follows for readability. Exporting the variant instead would put the taxonomy's shape in a second module. The three-field error follows from the same discipline: a `cause` field beside a `fallback` field reintroduces the "built naming both causes or neither" pairing `FallbackCause`'s two variants exist to rule out, and the three property names are compile-time constants of the module that renders them.
- **Extended:** the pre-load denial is deleted from every provisioning message, not routed around. **Human-directed** — round 3's Requirement Quality blocker found `ProvisioningError::RegistryRejected` carrying the same clause independently, and that variant is reachable on the derived route: a cluster holding `ADBC_VS_BUCKETFS` whose CDN answers HTTP 503 gets `None` from `registry_unreachable`, correctly, and surfaces `RegistryRejected` verbatim. Structuring one variant's facts therefore did not close the conflict. Task 2.2 deletes the clause from `RegistryRejected` and from `RegistryUnreachable`, and writes `PackageUnreachable` and `TransferInterrupted` without it. The two existing variants keep the rest of their text, `DRIVER_PATH` remedy included.
- **Alternatives to the extension:** delete the clause on `RegistryRejected` alone and leave it on `RegistryUnreachable`, which after the narrowing is reachable only on the explicit route. Suppress it at render time when the statement took the derived route.
- **Rationale for the extension:** the maintainer ruled that the sentence is false of the product everywhere once `adbc-drivers/<driver>/supplied/` exists and task 4.1 documents it in `README.md` and `CLAUDE.md`. Keeping it on the explicit route would tell an operator who correctly pre-placed a library that the location they used does not exist — a worse outcome than saying nothing, and one no route rule can justify. Suppressing it per route would put a message's truth under a condition the renderer cannot see. `no_provisioning_message_denies_the_default_location` asserts the phrase's absence over every variant, so one test holds the boundary rather than the question of which variants a route happens to reach today.
- **Promotes to ADR:** yes

## Review Findings

### [human] Widen the last-resort trigger to include a registry that answers nothing

- **Finding:** round 1's Intent Fidelity `[INTENT_DRIFT]` BLOCKER: the pre-placed route fired only when no BucketFS connection resolved at all, so the soft landing issue #4 point 3 names never reached a cluster that followed `README.md` and holds `ADBC_VS_BUCKETFS`. The headless pass could not settle it, and the plan was persisted as blocked with the question in `open-questions.md` and in PR #6.
- **Direction change:** the maintainer answered that the fallback MUST also fire when the reserved connection resolves and the registry is unreachable, and that the explicit-property routes MUST continue to never fall back. Decision `[11]` records the widening, `[12]` bounds it to a registry reached not at all, `[13]` reverses the `driver-version-resolution` non-change, and `[14]` makes both branches testable. `plan.md`'s Summary, Context, Architecture, Patterns, Key Interfaces, Consequences, Features, Impact, Migration, tasks, Parallelization and Verification are revised accordingly, and the widening reaches all four spec deltas.
- **Promotes to ADR:** yes

### [human] Point 4's presence-check declination needs no separate sign-off
