# Plan Review Findings: remove-pushdown-collation-and-like-escape (round 1)

## Summary
- Axes checked: 6/6
- Total findings: 15 (Blockers: 4, Advisory: 11)
- Intent Fidelity blockers: 1
- Human-escalation blockers: 1

## Premortem

Six months from now this plan failed. Three ways it got there:

1. A MySQL user's report merges `Widget` and `widget` into one group. The source schema belongs to another team, so the user cannot declare `utf8mb4_0900_bin`, and Exasol rejects `COLLATE` in a query. The README offers no remedy the user can apply in Exasol SQL. The requester expected "the user writes the right SQL" and approved a remedy ("user writes COLLATE") that does not exist. Routed to Intent Fidelity (`[INTENT_DRIFT]`).
2. The recorded spec library holds scenarios that still say a delegated `MIN`, `MAX`, grouping, or ordering comparison returns what Exasol returns "unqualified" and "over every mapped operand type". Next to them sit the new scenarios that say the opposite. The phase-2 refactor writes tests from the stale scenarios over default-collation fixtures. The tests fail, or a contributor re-adds a collation to make them pass. Routed to Requirement Quality (`[REQUIREMENT_CONFLICT]`).
3. A PostgreSQL 16 operator has an ICU nondeterministic column. After `REFRESH` the column appears. A delegated `LIKE` over it fails at the source, and Exasol does not re-plan, so a query that used to work now fails hard. Routed to Requirement Quality (`[COMPLETENESS_GAP]`, ADVISORY).

## Intent Fidelity

#### [INTENT_DRIFT] BLOCKER
- Location: plan.md § Summary, § Impact; decision-log.md § Design Decisions [1]; `vs-adapter/pushdown-filter` and `vs-adapter/{mysql,postgresql}-collation` Background deltas; task 4.2
- Issue: The plan offers a different remedy than the one the requester approved. The interview answer is "plain passthrough, document it (... source collation applies; user writes COLLATE for Exasol semantics)". The comparison report shown as evidence says "Users who need Exasol string semantics write `COLLATE` themselves". The original request says "rely on the user to write the right SQL". The plan instead says "a user who needs Exasol's code-point semantics declares the collation at the source", because Exasol 2025.2.1 rejects `COLLATE` in a query. That fact changes who can apply the remedy: a source DBA instead of the person writing the Exasol query. The interview has no follow-up question about it, and no `[plan-review]` entry records the change. The plan also leaves out a remedy that works in a query today: wrapping the operand in an expression no dialect advertises makes Exasol evaluate the predicate itself. Escalation is HUMAN because only the requester can decide whether a source-side-only remedy is acceptable. The decision changes what a user can do when they do not control the source schema.
- Fix: Ask the requester: "Exasol rejects `COLLATE` in a query. The remedies are (a) declare `utf8mb4_0900_bin` or `"C"` on the source column or in a source view, (b) wrap the operand in an expression the adapter does not advertise (for example `"name" || ''`), so Exasol evaluates the predicate itself, until phase 3 advertises scalar functions. Document (a) only, or (a) and (b)?" Record the answer as an `## Interview` line in decision-log.md. Update decision [1] Rationale, plan.md § Impact, the README text in task 4.2, and the pushdown-filter Background sentence on the remedy to match. Correct line 57 of pushdown-comparison-report.md so that it no longer says users write `COLLATE` themselves.
- Escalation: HUMAN. The interview's remedy is impossible as worded, and only the requester can accept the replacement.

Other intent checks found no objection. `[4]` (MySQL and PostgreSQL keep `FN_PRED_LIKE_ESCAPE` and render it verbatim), `[5]` (keep the three collation features), and `[6]` (drop the PostgreSQL nondeterministic guard) were not asked of the user. Each still follows the requester's passthrough model and the "simplify" goal: `[4]` and `[6]` delete or add no emulation, and `[5]` follows CLAUDE.md governance. The phase split (plan.md § Context, Interview "Split") is agreed scope, not a scope reduction. The requested comparison report exists at `pushdown-comparison-report.md`.

## Feasibility

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: plan.md § Context bullet 7, task 3.5, § Parallelization group E; decision-log.md [3] Consequences; task 4.2 (README Trino sentence)
- Issue: The README gives Trino users one remedy: write an explicit `ESCAPE` clause, and Exasol evaluates it. That remedy depends on Exasol 2025.2.1 never sending `predicate_like` with an `escapeChar` while `FN_PRED_LIKE` is advertised and `FN_PRED_LIKE_ESCAPE` is not. If Exasol does send it, task 3.2 makes the dialect fail with a named error, and every such query fails hard. The evidence is indirect: `MySQLSqlDialect.java:61` declares `LIKE` without `LIKE_ESCAPE`. The plan checks the assumption only in task 3.5, which runs in group E as the last step. The plan does not say what happens if the check fails. This project has measured negotiation questions of this kind with a throwaway Lua adapter probe against the local container before.
- Fix: Add a step before group C that runs the Lua-probe measurement on the local Exasol 2025.2.1 container. Record the result in plan.md § Context. Alternatively, add a contingency to task 3.5: if Exasol sends `escapeChar`, render the request's own escape character in an explicit `ESCAPE` clause rather than fail. Restate decision [3] to match.

#### [EFFORT_MISESTIMATION] ADVISORY
- Location: plan.md tasks 1.4, 1.5, 2.5
- Issue: Task 1.5 says to retarget four tests "to `items_bin` against the existing mirror". `assert_matches_mirror` in `tests/e2e_mysql_test.rs:1166` takes a closure keyed on the schema alone. Every query hard-codes `{schema}."items"`. A virtual `items_bin` cannot be compared with `MIRROR."items"` until the helper takes a table per side or the mirror gains an `items_bin` table. The same holds for `items_c` in `e2e_postgres_test.rs`. Task 1.4 also says "with every character column declared `COLLATE utf8mb4_0900_bin`". `items.region` is `CHARACTER SET latin1` (`tests/common/mysql.rs`), and MySQL rejects that collation for `latin1`. If the implementer converts `region` to `utf8mb4` instead, the column becomes mapped. The column sets then differ from the mirror's.
- Fix: In task 1.5 (and 2.5), state how a retargeted query reaches the mirror. Either change `assert_matches_mirror` to take a virtual table name and a mirror table name, or add a mirror table. In task 1.4, state that `region` stays `CHARACTER SET latin1` with no collation clause, so it stays unmapped in `items_bin`.

## Requirement Quality

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: recorded `specs/vs-adapter/mysql-pushdown/spec.md` scenario "Aggregation pushdown reaches MySQL rather than Exasol"; `specs/vs-adapter/postgresql-pushdown/spec.md` scenario "Aggregation pushdown reaches PostgreSQL rather than Exasol"; `specs/vs-adapter/postgresql-collation/spec.md` scenario "A select-list predicate over the grouped character column is delegated"; `specs/vs-adapter/pushdown-join/spec.md` scenarios "Outer join emits nulls for the unmatched side" and "Join composes with a delegated filter and aggregation"; `specs/vs-adapter/pushdown-filter/spec.md` scenario "Conjunction, disjunction, and negation nest without losing grouping". None of these is touched by a delta.
- Issue: After merge, these unchanged scenarios contradict the plan's new scenarios. mysql-pushdown requires the returned values to equal Exasol's "unqualified: `COUNT`, `MIN`, and `MAX` ... each is exact over every operand type". The new mysql-collation scenario "A delegated comparison and grouping follow the column's own collation" requires one group per case/accent pair, which is not Exasol's answer. postgresql-pushdown requires equality with Exasol "for `COUNT`, `MIN`, and `MAX` over every mapped operand type". The new postgresql-collation scenario requires `MIN` = `a` where Exasol returns `B`. The unchanged postgresql-collation select-list scenario requires the rows to equal the mirror. Its test uses `"category" < 'm'`, an ordering comparison. The plan itself retargets that test to `items_c` (task 2.5), but the scenario never says so. The MySQL counterpart delta adds "over a column declaring `COLLATE utf8mb4_0900_bin`". The pushdown-join and pushdown-filter scenarios require equality with Exasol "over the same data" for each driver, with no restriction on character operands.
- Fix: Add DELTA:CHANGED blocks to the affected deltas. (1) mysql-pushdown "Aggregation pushdown reaches MySQL rather than Exasol": delete "unqualified" and restrict the equality-with-Exasol step to non-character operands or to a column declaring `utf8mb4_0900_bin`. (2) postgresql-pushdown "Aggregation pushdown reaches PostgreSQL rather than Exasol": restrict the character `MIN`/`MAX` equality to a column declaring `COLLATE "C"`. (3) postgresql-collation "A select-list predicate over the grouped character column is delegated": add "over a column declaring `COLLATE "C"`" to the rows-equal-mirror step, the same way the MySQL delta does. (4) pushdown-join's two scenarios and pushdown-filter's conjunction scenario: qualify "over the same data" to data whose character operands carry a code-point collation or hold no collation-sensitive values. Add the new deltas to plan.md § Features, and update § Scenario Coverage with the tests that now cover them.
- Escalation: MECHANICAL. Reading the recorded scenarios next to the new deltas settles it.

#### [COMPLETENESS_GAP] ADVISORY
- Location: decision-log.md [6]; postgresql-type-mapping and postgresql-collation deltas; plan.md § Impact ("PostgreSQL, columns appear"); task 4.2
- Issue: Decision [6] maps a `character varying` column of a nondeterministic collation. The only evidence that `LIKE` works over such a column is from PostgreSQL 18.6 (recorded `003-add-postgresql-support` decision log, "Divergence 3"). The recorded spec's earlier statement that such a collation "makes `LIKE` fail outright" matches PostgreSQL before 18, which raises an error for pattern matching under a nondeterministic collation. This is general knowledge about PostgreSQL release history and was not verified here. adbc-vs states no PostgreSQL version floor. On PostgreSQL 12 to 17, a delegated `LIKE` over a newly exposed column therefore fails at the source. Exasol does not re-plan, so the query fails hard, where before the column was absent.
- Fix: Check the PostgreSQL 17 behavior against its documentation or a container. If it fails, add a sentence to plan.md § Impact and the README Limits entry (task 4.2): on PostgreSQL before 18, a delegated `LIKE` over a column with a nondeterministic collation fails at the source. Alternatively, record in decision [6] that the guard stays for servers before 18.
