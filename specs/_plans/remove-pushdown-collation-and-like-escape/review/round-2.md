## Premortem

Six months from now this plan failed. Three ways it got there:

1. Phase 2 makes push-down pluggable per dialect. Its planner reads `create-virtual-schema`, which says a precondition is "stated by the dialect that renders it" and that no check runs where the dialect renders nothing that needs it. It reads `architecture.md`, which after this plan says `sql_dialect` states no precondition. It reads `postgresql-type-mapping`, which grounds the `UTF8` check in the mapping alone. The three disagree, and the refactor either drops the PostgreSQL encoding check or moves it into the dialect interface. Routed to Requirement Quality (`[REQUIREMENT_CONFLICT]`, BLOCKER).
2. A MySQL dashboard groups by a case-insensitive column. The group label flips between `Widget` and `widget` after a MySQL upgrade, because MySQL reports an unspecified member of a folded group. Nothing in the spec or README warns, and an E2E test that asserted `Widget` turns red. Routed to Requirement Quality (`[COMPLETENESS_GAP]`, ADVISORY).
3. An operator runs plan.md § Manual Testing to confirm the wrapper remedy. The shell strips the doubled quotes, exapump reports a syntax error, and the operator concludes the remedy does not work. Routed to Feasibility (`[UNSTATED_ASSUMPTION]`, ADVISORY).

## Feasibility

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: plan.md § Verification › Manual Testing, row 3 (mysql-collation wrapper) and rows 6 and 7 (trino-pushdown `LIKE`)
- Issue: Each of these commands wraps its SQL in shell single quotes and doubles the inner single quotes the way SQL does. A shell does not read `''` inside a single-quoted string as an escaped quote. It closes the string and opens a new one. Checked with `printf`: row 3 reaches exapump as `SELECT "category" FROM MYSQLVS."items" WHERE "category" ||  = widget`, and row 7 as `EXPLAIN VIRTUAL SELECT "sort_key" FROM TRVS."items" WHERE "sort_key" LIKE a!% ESCAPE !`. Row 6 loses its quotes the same way. Each command fails with a syntax error, so the manual check of the wrapper remedy and of the Trino `ESCAPE` withdrawal cannot pass as written.
- Fix: In plan.md § Manual Testing, rewrite rows 3, 6, and 7 as double-quoted shell strings with escaped identifier quotes and plain SQL single quotes, for example `exapump sql --dsn "$DSN" "SELECT \"category\" FROM MYSQLVS.\"items\" WHERE \"category\" || '' = 'widget'"`, and `exapump sql --dsn "$DSN" "EXPLAIN VIRTUAL SELECT \"sort_key\" FROM TRVS.\"items\" WHERE \"sort_key\" LIKE 'a!%' ESCAPE '!'"`. Apply the same form to the `EXPLAIN VIRTUAL` variant row 3 names and to row 6.

#### [COMPLETENESS_GAP] ADVISORY
- Location: `vs-adapter/mysql-collation` delta § Scenario "A delegated comparison and grouping follow the column's own collation"; plan.md task 1.5 (`comparison_and_grouping_follow_the_columns_own_collation`); § Impact "MySQL, results change"; task 4.2
- Issue: Under `utf8mb4_0900_ai_ci`, `Widget` and `widget` fold into one group. MySQL reports one member of a folded group as the group's value, and it does not specify which one. The same holds for `MIN` or `MAX` over two values of equal collation weight. This is general MySQL behavior and this plan did not measure it. The scenario asserts group counts only, which is correct. Nothing tells the implementer not to assert the label, and the README text in task 4.2 does not tell a user that a folded group can report either spelling. A test that asserts `Widget` can pass for months and fail after a MySQL plan change.
- Fix: Add an AND step to that scenario: "the value each group reports MUST be one of the values the group folds, and no step requires which one". In task 1.5, state that the test asserts the group and distinct counts and checks each reported label only for membership in its pair. In task 4.2, add to the new Limits entry that a folded group, or a `MIN` or `MAX` tie, reports one of the folded spellings and the source chooses which.
