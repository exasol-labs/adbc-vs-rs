# Plan Review Findings: change-pushdown-aggregation-sum-avg-having

## Summary
- Axes checked: 6/6
- Total findings: 14 (Blockers: 2, Findings: 12)
- Intent Fidelity blockers: 0

Ways this plan may fail, routed below:

1. Exasol computes `SUM` and `AVG` over `BOOLEAN`, `VARCHAR`, and `CHAR` operands, and the plan never checks whether it delegates them. If it does, the PostgreSQL and Trino dialects send a `SUM` the source rejects, and a query that works today fails. Routed to Feasibility, `[UNSTATED_ASSUMPTION]` BLOCKER.
2. The plan adds a system-wide rule: a delegated floating-point result follows the source, and the user wraps the operand to get Exasol's value. `specs/architecture.md` § Constraints records the collation version of this rule, and the plan writes no delta. Routed to Design Depth, `[ARCHITECTURE_DRIFT]` BLOCKER.
3. The MySQL `SUM` over `BIGINT` and `DECIMAL(30,2)` returns a decimal wider than 38 digits. Task 2.6 leaves the scan fix conditional, and no scenario covers it. Trino's decimal-to-double cast is not verified, so an exact-numeric `AVG` on Trino can differ from Exasol's. Routed to Feasibility, FINDINGS.

Reviewer measurements, all read-only `SELECT` statements over literals on the local test stack (`exasol/docker-db:latest-2025.2`, `postgres:18.6`):

- Exasol `SUM` over `TRUE`, `FALSE` returned `1`. `AVG` over `TRUE`, `FALSE`, `TRUE` returned `0.6666666666666666`.
- Exasol `SUM` and `AVG` over the `VARCHAR` values `'5.5'` and `'7'` returned `12.5` and `6.25`. `SUM` over a `CHAR(3)` value `'5'` returned `5.0`. `SUM` over a `DATE` failed with "Cannot cast from DATE to DOUBLE".
- PostgreSQL `CAST(57368047004647539.3325::numeric AS DOUBLE PRECISION)` returned `5.7368047004647536e+16`. This is the correctly rounded value. Converting the unscaled integer first and then dividing gives `...544`.

## Feasibility

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: decision-log.md § [1] Decision; `vs-adapter/pushdown-aggregation-delegation` delta; plan.md § Implementation Tasks 2.2, 3.2, 4.2
- Issue: Decision [1] says "A capability stays advertised only when its dialect renders it for every operand type it admits". The plan never lists the operand types Exasol admits for `SUM` and `AVG`. It covers only `DECIMAL` and `DOUBLE`. Measured on the local test Exasol, Exasol also computes `SUM` and `AVG` over `BOOLEAN`, `VARCHAR`, and `CHAR` operands through implicit conversion. These operand types are mapped: PostgreSQL `boolean` and `bit`, MySQL `BIT`, PostgreSQL `numeric` without a precision or above 36 digits (`VARCHAR`, read as `CAST(<c> AS TEXT)`), MySQL `DECIMAL(p>36)` (`VARCHAR`), and every character column. Exasol already delegates `MIN` and `MAX` over a `BOOLEAN` operand (`postgresql-pushdown` "MIN and MAX over a BOOLEAN column render as bool_and and bool_or"), so a delegated `SUM` over one is plausible. If Exasol delegates these, the PostgreSQL dialect renders `SUM("flag")` or `SUM(CAST("n" AS TEXT))` and Trino renders `sum` over a `varchar`. Neither source defines those functions, so the query fails where Exasol answers it today. That outcome contradicts decision [1], the recorded `pushdown-dialect` scenario "A withheld capability carries one of two reasons", and `specs/architecture.md` § Constraints "Each advertised capability must be renderable by its dialect". Nobody has checked whether Exasol sends the raw column or inserts a conversion and withdraws the aggregation.
- Fix: Measure before implementation with the existing probe (`crates/adbc-vs-adapter/tests/common/probe.rs`). Its table `t` has `b BOOLEAN` and `g VARCHAR(100)`, and it already advertises `FN_AGG_SUM` and `FN_AGG_AVG`. Capture the `pushdown` request for `SUM`, `SUM(DISTINCT)`, `AVG`, and `AVG(DISTINCT)` over `b` and `g`. Record the result in plan.md § Context. Add a `DELTA:NEW` scenario to `vs-adapter/pushdown-aggregation-delegation` that states the outcome for a `BOOLEAN` and a `VARCHAR` operand. If Exasol withdraws the aggregation, add one end-to-end test per dialect. It asserts that `EXPLAIN VIRTUAL` carries no `SUM` and that the value equals Exasol's local result, so a later Exasol change trips it. If Exasol delegates, add a decision-log entry and per-dialect rendering that reproduces Exasol's conversion, for example `SUM(CASE WHEN <b> THEN 1 ELSE 0 END)` for a `BOOLEAN` operand in PostgreSQL. Back it with unit tests and end-to-end tests.

#### [UNSTATED_ASSUMPTION] FINDINGS
- Location: decision-log.md § [2] Rationale, § [3] Rationale; `vs-adapter/pushdown-aggregation-delegation` delta "SUM and AVG are delegated by every dialect..."; `vs-adapter/mysql-pushdown` delta "Aggregation pushdown reaches MySQL rather than Exasol"
- Issue: The plan does not label four load-bearing claims as sourced or unverified, or it states them in a way that contradicts itself. (a) Decision [3] says "Trino's `sum` returns its input's type (Trino documentation)" and then says "The cast is a no-op ... for a `decimal` operand in Trino". Both cannot be true: if `sum(decimal(12,4))` returns `decimal(12,4)`, the cast to `DECIMAL(38,4)` is a widening, not a no-op. (b) The delegation scenario justifies exact-numeric `AVG` parity for every dialect with "reproduced Exasol's AVG in every exact-numeric case measured on the test MySQL". Parity for PostgreSQL and Trino depends on each target's decimal-to-double cast being correctly rounded. The reviewer measured PostgreSQL as correct on a value above 2^53. Trino is unverified, and the Trino fixture `decimal(12,4)` cannot expose a rounding fault. (c) "MySQL sums a `FLOAT` operand in double precision" is unsourced. The fixture rule in task 2.5 ("partial sums are exact in double precision") also passes under single precision, so no test checks the claim. (d) "MySQL's `CAST(... AS DOUBLE)` needs MySQL 8.0.17" is unsourced.
- Fix: In decision-log.md § [3], replace the Trino sentence with the measured or documented return type of `sum` over `bigint` and over `decimal(p,s)` on Trino 483, or label it "(unverified)". In task 4.5, add a `decimal` value with a non-zero scale whose group sum exceeds 2^53 in unscaled digits, for example `57368047004647539.3325`, so `sum_and_avg_are_delegated_and_match_the_mirror` checks Trino's decimal-to-double rounding. In task 2.5, give the MySQL `FLOAT` column `16777216` and `1` in one group, as task 3.5 does for PostgreSQL `real`. Add the source "(MySQL documentation)" or "(unverified)" to the 8.0.17 claim in decision-log.md § [2] Consequences and plan.md § Impact.

#### [EFFORT_MISESTIMATION] FINDINGS
- Location: plan.md § Implementation Tasks 2.6
- Issue: Task 2.6 says "if the scan cannot cast the driver's Arrow type for it, extend `crates/adbc-vs-scan/src/coerce.rs` under the existing `scan-udf/arrow-coercion` scenario 'Decimal width variation is normalized'". This affects every MySQL `SUM` over a `BIGINT` or a `DECIMAL(p≥17,s)` column, because MySQL widens the result past 38 digits. That scenario covers a `DECIMAL(12,4)` column returned as `decimal64`, `decimal128`, floating point, or string. It does not cover a value wider than Arrow's 38-digit `Decimal128`. An extension would therefore add behavior that no scenario states, inside a dialect task, in another crate. The plan does not say what the MySQL driver returns for a `DECIMAL(41,0)` result, and the stack can answer that now.
- Fix: Before implementation, record in plan.md § Context the Arrow type the MySQL driver returns for `SELECT SUM(big_id) FROM orders`. If the scan needs a new branch, make it its own task in group B and add a `DELTA:CHANGED` to `scan-udf/arrow-coercion` "Decimal width variation is normalized". That delta adds a source decimal wider than 38 digits that fits the declared type, and its overflow error.

#### [NFR_IGNORED] FINDINGS
- Location: plan.md § Impact "Breaking for MySQL servers older than 8.0.17"; decision-log.md § [2] Consequences
- Issue: The plan adds a compatibility break that the user did not ask for: a delegated `AVG` fails on MySQL before 8.0.17. Decision [2] records the break but no alternative spelling. A spelling that needs no `CAST ... AS DOUBLE`, such as `(SUM(x) * 1E0) / COUNT(x)`, converts the `DECIMAL` sum to double on any MySQL 8.0 server. The plan also states no supported MySQL version range. A user on an older server cannot know whether this break concerns them.
- Fix: In decision-log.md § [2], either adopt a version-free MySQL spelling after measuring that it equals the `CAST` form on the test MySQL, or add it to Alternatives with the reason it lost. If the 8.0.17 floor stays, state the supported MySQL range in task 1.4's documentation change.

## Requirement Quality

#### [REQUIREMENT_CONFLICT] FINDINGS
- Location: `vs-adapter/pushdown-aggregation` delta "AVG renders as the double-precision quotient of SUM and COUNT", second AND step
- Issue: The step requires "the distinct values are taken over the operand's own type and never over its double-precision cast". The same scenario says the `SUM` renders "as the `SUM` scenario states", and the `SUM` scenario widens the operand. For PostgreSQL, the `SUM` operand declared `DOUBLE` is cast to `DOUBLE PRECISION` (task 3.2, `postgresql-pushdown` "SUM over a real column accumulates in double precision"). So `AVG(DISTINCT x)` over a `real` column renders `SUM(DISTINCT CAST(x AS DOUBLE PRECISION))`, and the distinct values are taken over the double-precision cast. The result is the same because `real` to double is lossless, but a test written from the step fails for PostgreSQL.
- Fix: Reword the step to: "both the `SUM` and the `COUNT` MUST carry `DISTINCT` before the operand, so the cast to the double-precision type applies to the `SUM` result and never to the `DISTINCT` operand, except for a lossless widening that the dialect's `<technology>-pushdown` feature states".

#### [REQUIREMENT_CONFLICT] FINDINGS
- Location: `vs-adapter/pushdown-aggregation-delegation` delta "Every dialect delegates the same aggregate set" and "A floating-point SUM or AVG follows the source's accumulation order"; plan.md § Impact
- Issue: The floating-point scenario says a `NaN` makes a delegated `SUM` null "where Exasol's local computation reads that one value as null and skips it". By that reasoning, a delegated `COUNT(x)` counts a `NaN` row that Exasol skips. A PostgreSQL `MAX(x)` also returns `NaN`, which Exasol reads as null, while Exasol's local `MAX` returns the largest finite value. The same feature's CHANGED scenario still requires "`COUNT`, `MIN`, and `MAX` MUST be exact over every operand type, because none of them sums". plan.md § Impact claims the `NaN` behavior for "a PostgreSQL or Trino floating-point column", but only PostgreSQL has a test (`a_nan_operand_makes_the_delegated_sum_and_avg_null`).
- Fix: In "Every dialect delegates the same aggregate set", change the AND step to say `COUNT`, `MIN`, and `MAX` are exact over every operand value except a floating-point `NaN`, which the source counts and orders while Exasol reads it as null. In task 4.5, add a separate Trino table with a `double` `NaN` beside finite values. In task 4.6, add `a_nan_operand_makes_the_delegated_sum_and_avg_null`, and list it in plan.md § Scenario Coverage.

#### [COMPLETENESS_GAP] FINDINGS
- Location: plan.md § Implementation Tasks 1.1; `vs-adapter/pushdown-aggregation` delta "A having element renders as a HAVING clause"
- Issue: Task 1.1 says "Parse the `having` element into the `Query` model" but does not say where. The `pushdown-dialect` Background places it on the aggregation ("an optional aggregation with an optional `having` predicate"). `Aggregation` is an enum, so that placement changes every dialect's grouping renderer. A field on `Query` leaves a `having` without an `aggregationType` representable. No scenario states what happens to that request. Rendering `HAVING` with no aggregation turns the source statement into an aggregate query that rejects its plain columns.
- Fix: In task 1.1, name where the predicate lives. Add an AND step to "A having element renders as a HAVING clause": a request carrying a `having` element and no `aggregationType` MUST fail with an error naming the `having` element. Add a unit test for it to task 1.1.

#### [COMPLETENESS_GAP] FINDINGS
- Location: plan.md § Implementation Tasks 1.4, § Manual Testing "documented workaround" row
- Issue: Task 1.4 tells users "to get Exasol's result, wrap the operand in an expression the adapter does not send, such as `SUM("price" + 0)`". Only a manual check covers this promise, and no scenario states it. The workaround stops working if a later plan advertises a scalar function such as addition, or if Exasol simplifies `+ 0`. The project already has an automated tripwire for its collation wrap-the-operand remedy.
- Fix: Add an AND step to `pushdown-aggregation-delegation` "A floating-point SUM or AVG follows the source's accumulation order": `SUM` over the operand plus zero MUST produce a generated statement carrying no `SUM` and MUST return Exasol's local value. Add the end-to-end test `wrapped_operand_sum_is_computed_by_exasol` to task 3.6, and add it to § Scenario Coverage.

#### [INFORMATION_COUPLING] FINDINGS
- Location: decision-log.md § [2] Consequences; plan.md § Implementation Tasks 2.2, 3.2, 4.2
- Issue: Decision [2] makes one shared choice: `AVG` is `SUM` cast to double, divided by `COUNT`, with `DISTINCT` inside both. The plan copies that choice into three `render_aggregate` functions and holds the copies together with one scenario and three unit tests. Any later fix to the rewrite has to change three places. One example is excluding a `NaN`, which the source counts and Exasol skips. The decision log gives no alternative, such as one `sql_dialect` helper that takes each dialect's rendered `SUM`, `COUNT`, and double type name.
- Fix: In decision-log.md § [2], either move the quotient into one helper in `sql_dialect.rs` that each dialect calls with its own `SUM` rendering and double type name, and update tasks 2.2, 3.2, and 4.2, or add that helper to Alternatives with the reason it lost.

#### [INFORMATION_COUPLING] FINDINGS
- Location: decision-log.md § [3] Decision and Alternatives
- Issue: Decision [3] keys the PostgreSQL and Trino `SUM` cast on the declared Exasol type. It rejects keying on the recorded source type because "it would put type-mapping knowledge in the aggregate renderer". Keying on the declared type still puts type-mapping knowledge in `render_aggregate`: knowledge that a PostgreSQL `DOUBLE` can be `real` and that a Trino `DECIMAL(p,0)` can be `bigint`. The accepted ADR `column-records-source-type-and-type-mapping-names-read-expression` rejects "Key the conversion on the declared Exasol type" and gives the type mapping ownership of per-type conversions. Decision [3] neither cites that ADR nor explains why a widening for accumulation falls outside it. A later reader sees an unexplained exception to an accepted rule.
- Fix: In decision-log.md § [3] Rationale, cite `column-records-source-type-and-type-mapping-names-read-expression`. State that the cast changes the target's accumulator type, not the value the scan emits, so it is not a read expression. State which mapped source types the declared-type rule reaches today: PostgreSQL `real`, `double precision`, and `money`, and Trino `integer`, `bigint`, and `decimal(p,s)`.
