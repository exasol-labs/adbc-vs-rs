### Premortem

Three ways the revised plan still fails six months out:

1. **`make test` is red the moment `Driver::Trino` lands.** `capabilities_tests.rs::advertised_set_matches_the_rendered_fragments` iterates `Driver::ALL` and asserts every advertised entry is either in `MAIN_CAPABILITY_CONSTANTS` or carries `FN_PRED_`, `FN_AGG_`, or `LITERAL_`. `AGGREGATE_GROUP_BY_TUPLE` is in neither, and no task edits that constant. Routed to `[EFFORT_MISESTIMATION]`.
2. **The merged library contradicts itself about multi-column grouping.** `/speq:record` merges the deltas and the recorded `vs-adapter/pushdown-aggregation` still states that Exasol sends no `groupBy` naming more than one column in this release, while `vs-adapter/trino-pushdown` requires an end-to-end test proving it does. Routed to `[REQUIREMENT_CONFLICT]`.
3. **A fourth driver installs over Trino's library.** The pairwise-distinctness clause moved to a test that names two drivers literally and asserts exactly two paths, so nothing ever observes a third. Routed to `[TRACEABILITY_GAP]`.

## Feasibility

#### [EFFORT_MISESTIMATION] BLOCKER
- Location: plan.md § Implementation Tasks task 6.4; `crates/adbc-vs-adapter/src/capabilities_tests.rs` lines 115 to 145 and 165 to 190; notes/planning.md § Design questions checked against the code before deciding
- Issue: advertising `AGGREGATE_GROUP_BY_TUPLE` turns an existing released invariant test red, and no task edits the constant that keeps it green. `capabilities_tests.rs::advertised_set_matches_the_rendered_fragments` loops `for driver in Driver::ALL` and asserts of every advertised entry that `MAIN_CAPABILITY_CONSTANTS.contains(&capability.as_str()) || FUNCTION_CAPABILITY_PREFIXES.iter().any(|prefix| capability.starts_with(prefix))`, failing with "advertises `{capability}`, which is neither a `MainCapability` constant this release renders nor a function or literal capability". `MAIN_CAPABILITY_CONSTANTS` holds eleven names and `AGGREGATE_GROUP_BY_TUPLE` is not one of them; the prefixes are `FN_PRED_`, `FN_AGG_`, and `LITERAL_`, none of which it carries. Once task 4.1 adds `Driver::Trino` to `Driver::ALL` and `drivers/trino.toml` states the 36th entry, `make test` fails. Task 6.4 names this test only to say that it "admits any entry carrying a known prefix and cannot catch either", which is true of the prefix branch and misses the constant branch entirely; the string `MAIN_CAPABILITY_CONSTANTS` appears nowhere in plan.md or decision-log.md. Two neighbouring facts go stale with it: `SHARED_MAIN_CAPABILITIES`'s doc comment reads "[`MAIN_CAPABILITY_CONSTANTS`] less the one entry the two targets disagree on", which describes two dialects and one difference where this release ships three and two; and notes/planning.md records "Whether `capabilities_tests.rs`'s `SHARED_MAIN_CAPABILITIES` and the MySQL-vs-PostgreSQL difference test break with a third dialect: no", a conclusion reached before the widening and false for the constant list. `vs-adapter/trino-pushdown`'s own scenario clause "every entry MUST be a `MainCapability` constant, or carry the prefix `FN_PRED_`, `FN_AGG_`, or `LITERAL_`" is exactly the clause this test enforces, so the delta and the suite disagree about whether `AGGREGATE_GROUP_BY_TUPLE` is a recognized name.
- Fix: In plan.md task 6.4, add the instruction to extend `crates/adbc-vs-adapter/src/capabilities_tests.rs`'s `MAIN_CAPABILITY_CONSTANTS` with `AGGREGATE_GROUP_BY_TUPLE`, stating that the list is what `advertised_set_matches_the_rendered_fragments` recognizes an advertised name by and that the Trino set would otherwise fail it. In the same task, add the instruction to rewrite `SHARED_MAIN_CAPABILITIES`'s doc comment so it describes a floor every dialect holds rather than "the one entry the two targets disagree on", naming both per-dialect entries — `JOIN_TYPE_FULL_OUTER` and `AGGREGATE_GROUP_BY_TUPLE` — as excluded from the shared list, and state that `SHARED_MAIN_CAPABILITIES` itself is unchanged because Trino advertises every entry in it. Also in task 6.4, state that `trino_dialect_tests.rs::query_exercising` MUST carry an `AGGREGATE_GROUP_BY_TUPLE` arm returning a two-column `GROUP BY` request and its expected fragment, because `every_advertised_capability_renders_per_dialect` calls it for every advertised entry and no existing dialect fixture has that arm. Correct notes/planning.md's "Design questions checked" bullet to record that the constant list does break with the widened third set.
- Escalation: MECHANICAL — every fact is in this repo's own test file and the plan's own task text. Reading them settles it.

- Fix: In `specs/_plans/add-trino-support/vs-adapter/pushdown-aggregation/spec.md`, add a `DELTA:CHANGED` block reproducing the recorded scenario "GROUP BY renders every grouping column the request carries, in request order" with its final clause replaced: state that the rendering MUST be verified by a unit test over a constructed request for every dialect, and that under the Trino dialect it MUST additionally be verified end to end, because that dialect advertises `AGGREGATE_GROUP_BY_TUPLE` and Exasol therefore sends a `groupBy` naming more than one column over it. Add a `vs-adapter/mysql-pushdown` delta file with a `DELTA:CHANGED` Background block rewriting the "so this release groups by exactly one column" bullet to scope the cap to the MySQL dialect and to name `vs-adapter/pushdown-aggregation` and decision `[16]` as the owner of the Trino exception, leaving that feature's two scenario clauses barring `AGGREGATE_GROUP_BY_TUPLE` from the MySQL set unchanged. Add `vs-adapter/mysql-pushdown` to plan.md § Features as `technology | CHANGED`, remove it from the no-delta bullet, and update decision-log.md `[15]` to state eight features carrying no delta with `vs-adapter/mysql-pushdown` named as the second technology feature that does carry one and why. Add a plan.md § Verification Scenario Coverage row for the reworked `pushdown-aggregation` scenario naming the existing unit test that covers it.
