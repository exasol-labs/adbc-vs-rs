### Premortem

Four ways this revision fails six months out.

1. **`make test` goes red the moment task 5.1 lands.** `connection_tests.rs::no_drivers_failure_subject_carries_the_credential` loops `Driver::ALL` and builds `trino://10.0.0.5:5432/adbc_vs`, a Trino address carrying one path segment. Task 5.1 tells the implementer to rebuild the `uri` value "from the host, port, catalog, schema, and query parameters", which a `PostgresAddress`-shaped parser answers with an error on that address. Routed to `[EFFORT_MISESTIMATION]`.
2. **`trino_it_test.rs::a_hostile_ascii_credential_authenticates_through_the_separate_options` cannot authenticate.** `docker/trino/password.db` holds one principal, `adbc_vs`, and both existing integration binaries hardcode `adbc_vs_password`. The scenario requires a server whose configured password holds `@ / : ? # & %` and a space. Routed to `[HIDDEN_DEPENDENCY]`.
3. **The permanent library records a rationale the plan's own gate disproved and the shipped code calls false.** Gate 2.3(b) corrected one Background bullet. The same sentence still stands in the scenario clause that merges beside it, in two plan.md tables, and in decision `[8]`. Routed to `[REQUIREMENT_CONFLICT]`.
4. **`specs/_decision/` gains an ADR for a design nobody built.** Decision `[6]`, the percent-encoded URI credential, still carries `Promotes to ADR: yes` and no supersession marker, while `[17]` replaces it whole. Routed to `[ADR_OVERPROMOTION]`.

## Feasibility

#### [EFFORT_MISESTIMATION] BLOCKER
- Location: plan.md § Implementation Tasks task 5.1; `scan-udf/trino-scan/spec.md` § Scenarios, "The credential travels in the driver's own username and password options", third clause; `crates/adbc-vs-scan/src/connection_tests.rs:178`
- Issue: task 5.1 states the Trino arm as a decomposition, "rebuild the `uri` option's value from the host, port, catalog, schema, and query parameters alone", and the spec clause repeats it as "the `uri` option's value MUST be the address's host, port, catalog, schema, and query parameters and nothing else". A released driver-generic test contradicts that shape. `connection_tests.rs::no_drivers_failure_subject_carries_the_credential` loops `for driver in Driver::ALL` and builds `uri: format!("{}://10.0.0.5:5432/adbc_vs", driver.as_str())`, then calls `database_target` and panics on an `Err` with "`{}`'s target is built". For Trino that address carries one path element, not two. An implementer following task 5.1 writes a `TrinoAddress::parse` mirroring `PostgresAddress::parse` at `connection.rs:190`, which splits the path and fails when a segment is missing, so `database_target(Driver::Trino, ...)` returns `Err` and the test panics. The test's own doc comment states the intent the plan must preserve: "Run once per identity rather than once for PostgreSQL: the rule is a property of the open path, so a technology added later inherits it". No task in the plan names `connection_tests.rs::no_drivers_failure_subject_carries_the_credential` or `a_failure_message_never_contains_the_password`, and the string `connection_tests.rs` appears in plan.md only for the one new test task 5.1 adds. The plan also already owns the counter-rule the decomposition violates: § Patterns row 2 states that the qualifier segment count is "one declared value, not a fact two modules know", and `crates/adbc-vs-scan/drivers/trino.toml` declares `[qualifier] segment_count = 2` for `create_schema.rs::parse_qualifier` to read. A Trino arm that re-derives a catalog and a schema from the path gives that count a third owner in a second crate.
- Fix: In plan.md task 5.1, replace the decomposition with the rule that the arm strips the userinfo component from the address and passes every other component through byte for byte, validating no path-element count, because `create_schema.rs::parse_qualifier` already checks that count against `drivers/trino.toml`'s `[qualifier] segment_count` and the scan must not hold a second copy of it. In the same task, name `crates/adbc-vs-scan/src/connection_tests.rs::no_drivers_failure_subject_carries_the_credential` and `::a_failure_message_never_contains_the_password` as the two released driver-generic tests the new arm MUST satisfy unchanged, and state that the first one builds a single-path-element `trino://` address. In `scan-udf/trino-scan/spec.md`, rewrite the third clause of "The credential travels in the driver's own username and password options" to require that the `uri` option's value equal the address with its userinfo component removed and nothing else changed, so no query parameter and no path element the operator set is dropped or re-derived.
- Escalation: MECHANICAL — the conflict is between the plan's own task text, its own § Patterns row, and a test file in this repo. Reading the three settles it.

#### [REQUIREMENT_CONFLICT] ADVISORY
- Location: `scan-udf/trino-scan/spec.md` § Background, bullet 12; plan.md § Impact, the "New capability" bullet; `decision-log.md` decision `[17]` Consequences
- Issue: the Background bullet states "The limit belongs to the Trino server rather than to the driver or to this adapter, so the scan passes the resolved bytes unchanged and transcodes nothing", and § Impact states the limit "is a property of the server's HTTP Basic charset rather than of this adapter". Decision `[17]`'s own Consequences says otherwise: "The ISO-8859-1 workaround gate 2.1 found existed only through the URI userinfo the driver percent-decodes, which this decision removes, and it covered U+0000 to U+00FF alone." `notes/B.md` § Gate 2.1c records the measurement behind that: `trino://g_utf8:abc%FCdef@...` authenticates and `trino://g_utf8:abc%C3%BCdef@...` does not. The limit is therefore the combination of the server's ISO-8859-1 decoding and the driver sending UTF-8 through the option path this plan chose, and for U+0080 to U+00FF it is the chosen design rather than the server that closes the door. A reader of the merged spec concludes that no client can do better, which the plan's own evidence contradicts for that range.
- Fix: In `scan-udf/trino-scan/spec.md` Background bullet 12, restate the attribution as the pair of facts the gate measured: the server decodes an HTTP Basic credential as ISO-8859-1 per RFC 7617, and the driver sends the option value's UTF-8 bytes, so no password holding a character above U+007F authenticates through the separate options. Add that gate 2.1 measured an ISO-8859-1 spelling reaching the server through the URI userinfo the driver percent-decodes, that the route covers U+0000 to U+00FF alone, and that decision `[17]` removes it deliberately rather than by oversight. Make the matching correction to plan.md § Impact's "New capability" bullet.
