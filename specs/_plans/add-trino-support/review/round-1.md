# Plan Review Findings: add-trino-support (round 1)

## Summary
- Axes checked: 6/6
- Total findings: 12 (Blockers: 5, Advisory: 7)
- Intent Fidelity blockers: 1
- Human-escalation blockers: 1

### Premortem

Three ways this plan fails six months out:

1. **Wrong rows, silently.** A Trino-backed virtual schema returns a different row set than the Exasol mirror for mixed-case and accented strings. The "no `COLLATE` suffix" rule shipped on claims labelled "measured on Trino 483" that were never executed: `notes/planning.md` records "No live Trino server was reached", and several of those claims have no gate task behind them either. Routed to `[UNSTATED_ASSUMPTION]`.
2. **The stack never comes up.** Task 1.1 turns on `http-server.authentication.type=PASSWORD` and TLS; task 1.2 and the Manual Testing table both address the unauthenticated plain-HTTP port with no credential. Phase 1 stalls, and phases 8 and 9 with it. Routed to `[HIDDEN_DEPENDENCY]`.
3. **A merged spec nobody can satisfy.** Two scenarios quantified over "each driver this release supports" are recorded as covered by a test binary whose stack holds two of the three drivers. Routed to `[TRACEABILITY_GAP]`.

## Intent Fidelity

#### [SCOPE_REDUCTION] BLOCKER
- Location: plan.md § Design → Non-Goals; decision-log.md `[2]` Alternatives
- Issue: the user's ask was "matching (and where Trino's SQL surface allows, exceeding) the PostgreSQL dialect's advertised capability set". The plan declines the exceeding half by fiat: "**Non-Goals** — widening the capability vocabulary itself." Decision `[2]`'s own Alternatives names capabilities Trino executes today, one of which costs nothing to render: "Advertise `AGGREGATE_GROUP_BY_TUPLE` for Trino alone, which needs no rendering change in any dialect." `vs-adapter/pushdown-aggregation` confirms it: "adding it would need no rendering change in any: each dialect already renders every grouping column a request carries." The withholding rests on a release-scope boundary set by a previous plan, not by this plan's requester, and the requester asked for the opposite. The plan also withholds `JOIN_CONDITION_ALL` on a mission.md boundary, which is a stronger claim and may well stand, but the two cases are decided together with no separation.
- Fix: Put the question to the requester with `AskUserQuestion` before revising: state that `AGGREGATE_GROUP_BY_TUPLE`, `AGGREGATE_GROUP_BY_EXPRESSION`, and `AGGREGATE_HAVING` are executable by Trino and that `AGGREGATE_GROUP_BY_TUPLE` needs no rendering change in any dialect, and ask whether "full pushdown coverage" means lifting those release-wide boundaries for Trino or keeping parity with PostgreSQL exactly. Record the answer as a new decision-log entry. If the answer is to lift any of them, add the entry to `drivers/trino.toml`'s list in task 4.1, delete it from plan.md § Design's withheld table, revise `vs-adapter/trino-pushdown` § Background and its "Capability set advertises the fragments this dialect renders" scenario, and revise `vs-adapter/pushdown-aggregation`'s "advertised by no dialect" sentences to name the exception. If the answer is to keep parity, record that in decision `[2]`'s Rationale as the requester's own answer rather than as a planner non-goal.
- Escalation: HUMAN — the user named exceeding PostgreSQL as part of the ask and the plan substitutes parity. A dropped ask is never the reviewer's to resolve, and choosing whether a driver addition may move a release-wide scope boundary is a judgement only the requester can make.

## Feasibility

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: `vs-adapter/trino-collation/spec.md` § Background lines 8-10; `vs-adapter/trino-pushdown/spec.md` § Background lines 9, 16-19; `vs-adapter/trino-type-mapping/spec.md` § Background line 14; plan.md § Summary and § Design Consequences; decision-log.md `[4]`, `[8]`
- Issue: the plan's load-bearing rendering rules are stated as completed measurements against a live server, and the planner's own hand-off note says no such server was reached. `notes/planning.md` § Not checked: "No live Trino server was reached. Every rendering claim the plan makes is tagged to a gate task that measures it, not asserted from documentation alone." Against that, the artifacts assert specific execution results as fact: "Measured on Trino 483 over the values `a`, `B`, `Z`, `z`, `A`, `ä`, `Ä`, `é`, `e`: `ORDER BY` returned `A B Z a e z Ä ä é`"; "`min` returned `B` and `max` returned `ä`"; "Measured, `typeof(123.45)` is `decimal(5,2)`"; "measured on 483, `FULL OUTER JOIN … ON a.k < b.k`, `ON a.k <> b.k`, and `ON true` each execute and null-extend both sides". The second half of the note is false as well: six of these claims have no gate task behind them at all. Gate 2.3 covers ordering and equality (a), the `DOUBLE` literal (b), `LIKE … ESCAPE` (c), a full outer join over **an equality only** (d), and the bare grouping key (e). Nothing measures: `E'a'` parsing as a typed literal of unknown type `e` and failing (trino-pushdown line 16); `DATE '2024-01-01' = '2024-01-01'` failing with `Cannot apply operator: date = varchar(10)` (line 17); Trino rejecting a decimal literal above 38 significant digits (line 19); `FULL OUTER JOIN` over a non-equi condition (line 9); `COLLATE` being usable as an ordinary column alias and its exclusion from every reported set of legal continuations (trino-collation line 9); `CAST('abc' AS CHAR(5)) LIKE 'abc'` being false while `= 'abc'` is true (trino-type-mapping line 14). These specs merge into the permanent library at `/speq:record`, carrying unexecuted results as recorded evidence, and an implementer reading "measured, returned `A B Z a e z Ä ä é`" will write that literal expectation into a test rather than run the gate.
- Fix: In `vs-adapter/trino-collation/spec.md`, `vs-adapter/trino-pushdown/spec.md`, and `vs-adapter/trino-type-mapping/spec.md`, replace every "measured on 483" and "measured," with wording naming the actual source read, and state the gate that will confirm it: Trino's own documentation, or the `trinodb/trino` tag `483` source files `notes/planning.md` lists. Do the same in plan.md § Summary paragraph 2, § Design Consequences rows for the collation, the `LITERAL_DOUBLE` form, and `char(n)`, and in decision-log.md `[4]` Alternatives and Rationale and `[8]` Alternatives. Then extend plan.md § Implementation Tasks phase 2 so every remaining claim has a gate: add to task 2.3 the measurement of a non-equi and an `ON true` full-join condition, the `E'<body>'` rejection, a bare quoted string compared against a `date` column, and a decimal literal above 38 significant digits; add to task 2.2 the measurement that `CAST('abc' AS CHAR(5)) LIKE 'abc'` and `= 'abc'` disagree; add a new gate measuring that `COLLATE` is not a Trino keyword in any syntactic position. Change plan.md § Design Goals from "every rendering rule is measured against a live Trino before it is advertised" only after those gates cover every rule the specs state.
- Escalation: MECHANICAL — the contradiction is settled by the plan's own `notes/planning.md`, and the gates the fix extends are already in the plan. No external judgement is needed to relabel an unexecuted claim or to add a gate line.

#### [HIDDEN_DEPENDENCY] BLOCKER
- Location: plan.md § Implementation Tasks tasks 1.1 and 1.2; plan.md § Verification → Manual Testing, row `vs-adapter/trino-type-mapping`
- Issue: the plan configures the Trino container for authenticated TLS and then seeds and hand-verifies it over an unauthenticated plain-HTTP endpoint, with no statement of how the two coexist. Task 1.1 mounts "`docker/trino/config.properties` enabling `http-server.https.enabled`, `http-server.https.port=8443`, `http-server.https.keystore.path`, `http-server.authentication.type=PASSWORD`" plus a file password authenticator, and names "the image's own `HEALTHCHECK` as the readiness signal" without saying what that healthcheck authenticates as once `PASSWORD` is on. Task 1.2 then says "Seed it from `stack-up-trino` through the container's own CLI at `/usr/bin/trino`" and names no server URL, no user, no password, and no truststore for the self-signed certificate task 1.1 generates. The Manual Testing table is explicit and incompatible: `docker compose exec -T trino trino --server http://localhost:8080 --execute "SELECT column_name, data_type FROM memory.information_schema.columns …"`, with no credential and against the plain-HTTP port. Either the container admits unauthenticated plain-HTTP queries, which defeats the whole reason decision `[14]` chose password authentication ("an unauthenticated container would leave the percent-encoding rule untested end to end"), or the seeding step, the readiness signal, and the manual check all fail and phase 1 never completes. Group A is a prerequisite of B, E, F, G, and H, so this blocks every later phase.
- Fix: In plan.md task 1.1, state explicitly whether `docker/trino/config.properties` sets `http-server.authentication.allow-insecure-over-http`, and state which endpoint and which credential the readiness signal uses under `PASSWORD` authentication; if the image's own `HEALTHCHECK` cannot answer an authenticated server, replace it with a bounded poll in the `stack-up-trino` recipe, matching the pattern `stack-up`'s existing Exasol loop uses. In task 1.2, name the CLI invocation in full: the `--server` URL, the `--user` and password source, and the truststore or `--insecure` flag the self-signed certificate needs. In § Verification → Manual Testing, correct the `vs-adapter/trino-type-mapping` row's command to the same authenticated form. Add the readiness and seeding path to task 1.3's `make_targets_test.rs` extension so a silently unauthenticated container fails a test rather than passing.
- Escalation: MECHANICAL — the inconsistency is between task 1.1 and tasks 1.2 and the Manual Testing table, all inside plan.md. Resolving it is naming the transport and credential the seeding step uses, not a judgement call.
