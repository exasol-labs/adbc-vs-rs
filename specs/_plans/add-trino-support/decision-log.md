# Decision Log: add-trino-support

## Interview

**Q:** Which database technology should adbc-vs add next? The roadmap names Snowflake, Databricks, and DuckDB.
**A:** Iterate on the candidates before committing to a plan.

**Q:** Measured against the `dbc` driver registry, the candidates rank as follows. Snowflake publishes `v1.14.0` across 9 releases, is mature, covers `linux_amd64`, and takes a URI plus connection kwargs, which is the closest fit to the connection model adbc-vs already has. Databricks publishes `v0.1.3` across 2 releases, and its own documentation calls itself an early version with no transactions, no temporary tables, and a broken `NUMERIC` mapping. DuckDB and SQLite are mature drivers but embedded and file-based, with no host, port, user, and password model, so either would need a new connection shape rather than a new driver. Snowflake is the lowest-risk pick.
**A:** Check whether a Trino driver exists. If it does, plan for Trino with full pushdown coverage.

**Q:** It exists. The registry publishes "ADBC Driver Foundry Driver for Trino" under `path: trino`, Apache-2.0, latest `v0.5.3` across 9 releases, with `linux_amd64` among its four platforms. Its documented connection URI is `trino://[user[:password]@]host[:port][/catalog[/schema]][?attributes]`, which is the same shape the existing drivers use. Its documentation states that HTTP Basic authentication works only over an encrypted connection, shows `SSLVerification=NONE` for a self-signed certificate, and says nothing about `LIMIT`, `JOIN`, or aggregation pushdown, because those are properties of Trino's SQL rather than of the driver. Confirm the SQL surface during planning rather than assuming it.
**A:** Plan Trino with full pushdown coverage. Full coverage means matching the PostgreSQL dialect's advertised set — projection, filter expressions, aggregation single-group and `GROUP BY`, the full predicate set, every literal type, and every join type PostgreSQL advertises including `FULL OUTER` — and exceeding it where Trino's SQL surface allows. Trino is highly ANSI-compliant and supports `FULL OUTER JOIN` natively, so there is no known SQL-level reason to withhold anything PostgreSQL already advertises. Confirm that rather than assume it, and flag anything Trino's dialect cannot actually render. State the capability set feature by feature with a reason for each entry, mirroring `postgresql.toml`'s own reasoning rather than copying its list. Tag any task that needs confirming a rendering detail against a real Trino instance as `[expert]`.

**Q:** Interview mode for the planning run itself?
**A:** Headless. Assume and document conventional decisions, following the PostgreSQL-addition precedent wherever it applies. The one thing not to assume quietly is the Trino capability set.

## Design Decisions

### [1] Trino is the next driver, ahead of the aspirational v1 set

- **Decision:** Add Trino as the third supported technology, before Snowflake, Databricks, and DuckDB. Add a Trino line to the README roadmap and to mission.md's driver set, which name neither Trino nor a rule that would have excluded it.
- **Alternatives:** Snowflake, recommended on registry maturity before the user chose Trino. Databricks, whose driver's own documentation describes it as early with a broken numeric mapping. DuckDB or SQLite, which are embedded and file-based and would need a new connection shape rather than a new driver.
- **Rationale:** Asked for in the interview. Trino also fits the existing connection model without change: its address is a `<scheme>://host[:port]/<path>` URI carrying the source user and password beside it, which is the shape `vs-adapter/create-virtual-schema` already requires.
- **Consequences:** mission.md's "aspirational v1 driver set" sentence names three technologies that no longer describe what ships next, and task 9.3 rewrites it rather than leaving a plan-shaped gap in the mission.
- **Promotes to ADR:** no

### [2] Trino's advertised set is PostgreSQL's 35 entries, and every absence is a framework decision

**Superseded in part by decision `[16]`, which adds `AGGREGATE_GROUP_BY_TUPLE` to the set.** This entry records the parity floor and the reason each remaining absence stands; `[16]` records the one entry that rose above it and who decided that.

- **Decision:** `drivers/trino.toml` states the 35 entries `drivers/postgresql.toml` states, written out independently and rendered entry by entry through `TrinoDialect`. Nothing is withheld from Trino for a reason about Trino's SQL. Every capability name in this release's vocabulary that the set omits — `JOIN_CONDITION_ALL`, `AGGREGATE_GROUP_BY_EXPRESSION`, `AGGREGATE_HAVING`, `FN_AGG_SUM`, `FN_AGG_SUM_DISTINCT`, `FN_AGG_AVG`, `FN_AGG_AVG_DISTINCT`, `LITERAL_BOOL`, every scalar function, and the four ordering and limiting capabilities — is withheld by a framework or mission decision that binds every dialect identically, and the plan's § Design names the owner of each. `AGGREGATE_GROUP_BY_TUPLE` was in that list when this entry was written and is not any more; decision `[16]` says why.
- **Alternatives:** Advertise `JOIN_CONDITION_ALL` for Trino alone, which Trino's documented join syntax permits even under a full outer join and which gate 2.3(d) measures. Advertise `AGGREGATE_GROUP_BY_TUPLE` for Trino alone, which needs no rendering change in any dialect. Advertise `FN_AGG_SUM` for Trino alone. All three were rejected here on one argument — lifting a release-wide boundary under cover of adding a driver — and decision `[16]` reopened that argument on `AGGREGATE_GROUP_BY_TUPLE` at the requester's instruction and accepted it for that entry alone. The `JOIN_CONDITION_ALL` and `FN_AGG_SUM` rejections stand as written: mission.md scopes non-equi joins out for the project, and `vs-adapter/pushdown-aggregation` withholds the summing aggregates for every dialect for reasons that are not about any target's SQL.
- **Rationale:** This is the plan's floor for "full pushdown coverage": Trino reaches the ceiling this release's vocabulary sets, and that ceiling is not Trino's. Stating the two reasons a capability can be absent — the target cannot express it, or a framework decision withholds it — makes the answer checkable rather than asserted. What this entry got wrong was treating "a framework decision withholds it" as settling the question rather than as naming the decision the requester could still be asked about; decision `[16]` records that correction and the answer.
- **Consequences:** The 35 entries the Trino and PostgreSQL sets share is an agreement between two independent statements rather than a rule, and a test asserts both the agreement and the one deliberate difference, so a later change to either set fails rather than being absorbed. `vs-adapter/pushdown-dialect`'s scenario pinning "the one difference in this release" to `JOIN_TYPE_FULL_OUTER` is replaced by one asserting that at least one pair of sets differs and that every difference is named by the feature that owns the withholding, together with its reason.
- **Promotes to ADR:** yes

### [3] The recorded source qualifier becomes an ordered segment list

- **Decision:** `MetadataSource::namespace` returns an ordered list of name segments, `SourceTable` carries the list, and each dialect's table qualifier joins the quoted segments. `AdapterNotes` accepts a JSON string or a JSON array on deserialization, and serializes one segment as a string and more as an array. MySQL and PostgreSQL supply one segment, so their generated statements and recorded notes stay byte-identical.
- **Alternatives:** Record `<catalog>.<schema>` as one string the Trino dialect splits on a dot, rejected because a catalog or schema name may contain a dot and the split is then unrecoverable. Qualify with the schema alone and rely on the catalog the connection selected, rejected because it puts state into name resolution that the generated statement does not carry and `EXPLAIN VIRTUAL` does not show, which is the invisible-server-state argument that already rejected `search_path` auto-detection for PostgreSQL. Add a second notes field for the catalog, rejected because two records of one fact can disagree.
- **Rationale:** A Trino table is named `catalog.schema.table` and its `information_schema` is scoped per catalog, so two segments are the smallest honest representation. A list also answers the next technology rather than only this one: Snowflake, next on the roadmap, nests a table under a database and a schema the same way.
- **Consequences:** How many segments a technology's qualifier carries becomes a declared value in that technology's own TOML file, generated into the compiled-in tables the way its capability list already is, because the address check runs before any connection exists while the metadata source answers after one does, and two modules deciding how deeply a technology nests its tables can disagree. The address's path element count is checked against that one value, and both too few and too many elements fail with a named error. That narrows released behavior: before this release `mysql://host:3306/db/extra` took `db/extra` as the database and failed later at the source. § Impact states it. Notes Exasol persisted before this release parse unchanged, so no virtual schema needs recreating.
- **Promotes to ADR:** yes

### [4] The Trino dialect renders no collation suffix

- **Decision:** `TrinoDialect` renders no collation anywhere: not on an equality operand, an ordering operand, a `LIKE` operand, an `IN` operand, a `GROUP BY` key, a `DISTINCT` operand, a `MIN` or `MAX` operand, or a join key. `vs-adapter/trino-collation` states the rule as a measured claim about Trino's own comparison rather than as an absence.
- **Alternatives:** Render an ordering collation, mirroring PostgreSQL. Refuse character operands outright. Both are expected to be unavailable rather than merely worse: `COLLATE` appears in no part of Trino's documented SQL grammar and in no reserved-word list it publishes, so it should be usable as an ordinary column alias and should produce a parse error, in every position a suffix could occupy, whose reported legal continuations never include it. That is read from documentation, not executed; gate 2.5 measures it, and a Trino that does have a collation mechanism re-decides this entry rather than shipping it.
- **Rationale:** Trino's documentation states that its `varchar` comparison and ordering are Unicode code-point order, which is how Exasol answers both of its own questions. Applied to `a B Z z A ä Ä é e` that rule yields `A B Z a e z Ä ä é` for `ORDER BY`, and `B` and `ä` for `min`/`max` over `a B Z ä` — Exasol's answers, and not what a locale collation returns. Equality follows from the same rule, so one answer covers both questions. No live Trino has returned any of those values yet: gate 2.3(a) measures them against Trino 483 and Exasol 2025.2.1 over one fixture before the no-suffix rule is advertised.
- **Consequences:** Trino is the only one of the three dialects whose grouping key and select-list occurrence need no coordination and whose operands keep the source's own execution options. MySQL's composed-shape exclusion has no analogue here, for the same reason it has none for PostgreSQL.
- **Promotes to ADR:** yes

### [5] Trino's connector-pushdown condition is stated and not checked

- **Decision:** adbc-vs runs no check for it, refuses no catalog over it, and renders the same statement whatever catalog a virtual schema is over. `vs-adapter/trino-collation` states the condition and names who owns it, and mission.md's Constraints carries it beside the two existing per-technology entries.
- **Alternatives:** Refuse a virtual schema over a catalog whose connector reaches a remote database, rejected because it refuses what Trino exists for. Withhold `FN_PRED_LESS`, `FN_PRED_LESSEQUAL`, `FN_PRED_BETWEEN`, `FN_AGG_MIN`, and `FN_AGG_MAX` from Trino, rejected because it costs every Trino deployment the coverage this plan delivers for a condition the operator configures and can avoid.
- **Rationale:** Trino's PostgreSQL connector documents that it does not push string range predicates down "to ensure correctness of results since the remote data source may sort strings differently than Trino", while equality and inequality predicates on textual columns are pushed down; its MySQL connector pushes no textual predicate down at all; its SQL Server connector decides per column collation. That is a per-connector convention, not an engine guarantee, and the PostgreSQL connector documents a property that removes it. No catalog Trino exposes reports which comparisons a connector pushes down or which collation the remote source applies, so there is no query a precondition check could run. Stating an unenforceable condition is the honest outcome; implying it does not exist is not.
- **Consequences:** Trino is the first supported technology whose source precondition is unenforceable, where MySQL's collation floor and PostgreSQL's encoding requirement are both checked. The asymmetry is stated in the spec rather than left to be inferred from an empty check. The measurements the plan records are taken against a catalog that reaches no remote system, so what they measure is Trino's own comparison.
- **Promotes to ADR:** yes

### [6] The Trino credential is percent-encoded in full into the connection URI's userinfo

- **Decision:** The Trino arm of the shared open path parses the address, drops any userinfo it carries, percent-encodes every byte of the resolved user and password outside the RFC 3986 unreserved set, and rebuilds the URI with the encoded credential. Redaction strips both the verbatim bytes and the percent-encoded spelling from every surfaced message. The failure subject is built from the host, port, catalog, and schema rather than from the value handed to the driver.
- **Alternatives:** Encode only the characters the URI grammar reserves, rejected because it is the partial escaping that made URI form wrong for PostgreSQL and leaves a set to keep correct. Pass the credential as a query parameter, rejected because it is not where the driver documents a credential. Assume an undocumented `username` option exists, rejected as an assumption: gate 2.1 probes for one empirically, and a separate option would move the credential out of the URI and this decision with it.
- **Rationale:** The driver accepts one `uri` option and documents no separate credential option, so the only choice is the form of the encoding rather than whether to encode. Encoding every byte outside the unreserved set is one unconditional pass, is always valid in a userinfo component, and has no set of hazardous characters to keep in step with the grammar. Decision `postgresql-credentials-in-single-connection-option` rejected URI form for PostgreSQL because a total escaping was available in another form; here no other form exists, so the encoding is made total instead of avoided.
- **Consequences:** A third spelling of a secret now exists inside the process, so the redaction strips two forms rather than one. The driver sends Basic authentication only over an encrypted connection, so a `CONNECTION` whose address selects plain HTTP and whose password field holds a value fails rather than connecting as an unauthenticated principal, and the adapter neither strips the password nor rewrites the address to make it succeed. A Trino `CONNECTION` deserves a least-privilege, read-only principal for the same reason a PostgreSQL one does.
- **Promotes to ADR:** yes

### [7] Every Trino LIKE renders an explicit ESCAPE clause, and an inadmissible escape sequence fails in the dialect

- **Decision:** The Trino dialect renders an `ESCAPE` clause for every `LIKE`, carrying the request's own `escapeChar` when it has one and a backslash when it has none. A pattern whose escape character precedes a character the target does not admit fails with a named error rather than reaching the source. `vs-adapter/pushdown-filter`'s framework rule is restated: reproducing Exasol's escape handling is per dialect, and two targets need no clause because their default is Exasol's.
- **Alternatives:** Pass the pattern through unchanged as the other two dialects do, rejected because Trino's documentation states that a wildcard is matched literally only by specifying an `ESCAPE` character, so a pattern carrying `\%` would match a backslash followed by anything — wrong rows rather than an error. Drop or rewrite the inadmissible sequence, rejected because it changes which rows come back. Emit the statement and let Trino reject it, rejected because the failure then reaches an operator as the source's message about a pattern the operator never typed.
- **Rationale:** Exasol's own default treats a backslash as escaping the character after it, and a delegated filter is never re-applied, so a dialect whose target has no default escape character must supply one or return a different row set.
- **Consequences:** `vs-adapter/pushdown-filter` gains a scenario for the exclusion, bound to the dialects whose targets have the restriction rather than to every dialect. Gate 2.3(c) measures whether Trino is one of them, and its answer is a spec correction rather than a code special case.
- **Promotes to ADR:** yes

### [8] A floating-point literal renders typed and an exact-numeric literal renders bare

- **Decision:** The Trino dialect renders `LITERAL_DOUBLE` as `DOUBLE '<value>'` and `LITERAL_EXACTNUMERIC` as a bare numeric constant, through the same numeric-constant grammar the PostgreSQL dialect uses to guard both.
- **Alternatives:** Render both bare, as the other two dialects do, rejected because Trino's type documentation states that a bare decimal constant is typed `DECIMAL` — so `typeof(123.45)` is expected to be `decimal(5,2)` — and a floating-point literal rendered bare is then an exact-numeric operand where Exasol meant a floating-point one. Append `E0`, rejected because it breaks on a value already carrying an exponent. The typing claim is read from documentation rather than executed; gate 2.3(b) measures it.
- **Rationale:** Trino distinguishes the two literal families where the other two targets resolve one from the other operand. The bare form stays safe for every exact-numeric literal Exasol can send, because Trino documents a maximum `DECIMAL` precision of 38 and rejects a decimal literal above it rather than widening it, while Exasol's own maximum `DECIMAL` precision is 36. Gate 2.3(h) measures the rejection, since a Trino that widened instead would make the bare form silently change a literal's type.
- **Promotes to ADR:** no

### [9] Trino's mapping parses the catalog's type string

- **Decision:** `trino_type_mapping` parses `information_schema.columns.data_type` for every declared length, precision, and scale, reading a bare name, a name with one parameter, and a name with a precision and a scale separated by a comma with no space. An unrecognized `data_type` leaves the column unmapped with that string in the reason rather than being read as the name before its parameters.
- **Alternatives:** Read `character_maximum_length`, `numeric_precision`, and `numeric_scale` as the other two mappings do. Unavailable: Trino's `information_schema.columns` has exactly `table_catalog`, `table_schema`, `table_name`, `column_name`, `ordinal_position`, `column_default`, `is_nullable`, and `data_type`, plus three hidden comment columns. The precision columns are absent rather than null, so selecting one fails the catalog query.
- **Rationale:** `data_type` is the only place the declared type exists. Trino's own connector test suite reads it the same way.
- **Consequences:** `vs-adapter/type-mapping`'s statement that each catalog carries fields the others do not widens: Trino carries a detail that is not a field at all, which is a second reason no shared source-column struct can serve every source. Gate 2.2 records the exact spelling of every `data_type` the mapping reads, so the parser is written against measurement rather than against documentation.
- **Promotes to ADR:** no

### [10] Trino's dialect states no source-server precondition

- **Decision:** `TrinoSource::check_source` succeeds without querying the server. `vs-adapter/trino-type-mapping` states the absence as a decision with its reason rather than leaving an empty method to be read as an oversight.
- **Alternatives:** Check a server version floor, rejected because the oldest release any rendered construct needs is 335, which introduced the variable-precision `timestamp(p)` type, older than any server a supported driver reaches. Check the catalog's connector, rejected in decision `[5]` because nothing reports it.
- **Rationale:** `vs-adapter/create-virtual-schema` requires a precondition only for what a dialect's rendering depends on, and everything Trino's rendering depends on — code-point comparison, the absence of collation, the double-quote identifier form, the typed-literal requirement — is fixed in Trino's SQL engine rather than configurable. The framework check still runs at the same point for Trino as for the other two, so no driver is excepted from the contract.
- **Promotes to ADR:** no

### [11] The driver version range is `>=0.5.3, <0.6.0`

- **Decision:** `drivers/trino.toml` states `version_range = ">=0.5.3, <0.6.0"`, with the file's own comment stating why each bound is where it is.
- **Alternatives:** `>=0.5.0, <0.6.0`, rejected because nothing has run this adapter against a lower published `0.5.x`. `>=0.5.3, <1.0.0`, rejected because a pre-1.0 minor bump is breaking by SemVer convention. Pin `0.5.3` exactly, rejected because decision `driver-version-range-resolved-against-registry` removed pinning.
- **Rationale:** The floor is the version this plan measured against; resolution selects the highest satisfying version, so the floor states what was measured rather than what gets installed. The ceiling follows the pre-1.0 rule MySQL's ceiling follows and PostgreSQL's does not, which is why the three ranges stay three independent statements.
- **Promotes to ADR:** no

### [12] The Trino package row is read out of the published package rather than derived

- **Decision:** `library = "libadbc_driver_trino.so"` and `entry_point = "AdbcDriverTrinoInit"`, both read out of the published `v0.5.3` package's own `MANIFEST` and exported symbol table rather than derived from the registry path `trino`.
- **Alternatives:** Derive the symbol from the registry path, rejected because the MySQL package exports two spellings of its own name, which shows the capitalization is hand-chosen per driver rather than mechanical. Use the generic `AdbcDriverInit` symbol every package also exports, rejected because a named entry point is what `scan-udf/arrow-scan` requires and a generic one would load whichever library the manager happened to open.
- **Rationale:** The same rule `driver-provisioning/driver-self-install` already states: provisioning compares the archive's `MANIFEST` against the compiled-in filename and installs only the file it names, so the value has to be the one the package declares.
- **Promotes to ADR:** no

### [13] Each end-to-end target starts Exasol plus only the sources its own binary queries

- **Decision:** Split `stack-up` into `stack-up-exasol` and one target per source. `make stack-up` keeps its name and meaning as the local everything-up target. `test-e2e` depends on Exasol and MySQL, `test-e2e-postgres` on Exasol, PostgreSQL, and MySQL, `test-e2e-trino` on Exasol, Trino, and MySQL, and `bench` on Exasol and MySQL. `make_targets_test.rs` asserts the edges.
- **Alternatives:** Add `stack-up-trino` to `stack-up` and leave every end-to-end job starting four containers, rejected because a Trino image and a JVM turn the two accepted-but-wasteful notes already in `CLAUDE.md` from negligible into a real cost on a GitHub-hosted runner whose free disk is roughly 21GB.
- **Rationale:** The one-entry-point acceptance was taken when the waste was one idle PostgreSQL container. A fourth source changes the arithmetic rather than the principle, and each end-to-end binary already names exactly which sources its own setup module creates.
- **Consequences:** This supersedes the two `CLAUDE.md` notes recording the previous acceptance, and task 9.2 rewrites them rather than leaving both statements standing. `make bench` stops taking every throughput sample on a host running two databases it never queries, which those notes recorded as an uncorrected bias.
- **Promotes to ADR:** no

### [14] The end-to-end Trino serves HTTPS with file password authentication over the built-in memory catalog

- **Decision:** The `trino` compose service runs `trinodb/trino:483` with HTTPS on 8443, a self-signed certificate generated at stack-up into a gitignored path, file-based password authentication, and an internal shared secret. The fixture lives in the stock image's built-in `memory` catalog, seeded through the container's own CLI at `/usr/bin/trino`.
- **Alternatives:** Run the container unauthenticated over plain HTTP, rejected because the driver sends Basic authentication only over an encrypted connection, so the percent-encoding rule decision `[6]` rests on would never be exercised end to end — and a wrong parse there produces a connection to a different host rather than a test failure. Back the fixture with a JDBC catalog against the existing PostgreSQL container, rejected because the collation evidence would then measure a connector's comparison rather than Trino's. Use the `tpch` catalog, rejected because it is read-only and cannot hold the case, accent, and null fixtures the differential tests need.
- **Rationale:** The `memory` connector implements only limit pushdown and reaches no remote system, so every comparison it answers is Trino's own. It also ships in the stock image, so the stack needs no catalog file mounted.
- **Consequences:** The `memory` connector discards its data when the container restarts, so seeding runs from `stack-up-trino` on every start rather than once from an entrypoint directory. Because `PASSWORD` authentication admits no plain-HTTP request and `http-server.authentication.allow-insecure-over-http` is deliberately left unset, every path into the container is authenticated HTTPS: the seeding step, the readiness poll, and the hand-verification command all run `trino --server https://localhost:8443 --user … --password --insecure`. The published `8080` port therefore answers no query and exists only so the end-to-end credential test can assert the driver's own refusal to send a password over it. The image's own `HEALTHCHECK` is not used as the readiness signal, because what it authenticates as under `PASSWORD` is not established; `stack-up-trino` carries a bounded poll of the authenticated CLI instead, plus a credential-free probe that must fail, so a silently unauthenticated container fails stack-up rather than passing.
- **Promotes to ADR:** no

### [15] Eight live features carry no delta, and each absence has a reason

- **Decision:** `vs-adapter/result-ordering`, `vs-adapter/pushdown-projection`, `vs-adapter/mysql-collation`, and `driver-provisioning/driver-path-override` carry no delta because every driver-dependent claim they make is already stated over "each driver this release supports". `vs-adapter/mysql-type-mapping`, `vs-adapter/postgresql-collation`, `vs-adapter/postgresql-type-mapping`, and `scan-udf/mysql-scan` carry none because each states one target's own facts and makes no claim about another target that a third driver falsifies. `vs-adapter/mysql-pushdown` was on this list until round 2 and is not: its Background states "so this release groups by exactly one column", which is a claim about the release rather than about MySQL, and decision `[16]` falsifies it. Its delta narrows that one reason's scope to the MySQL dialect and names `vs-adapter/pushdown-aggregation` as the owner of the Trino exception; MySQL's advertised set and every scenario clause barring `AGGREGATE_GROUP_BY_TUPLE` from it are unchanged.
- **Alternatives:** Delta every feature that names a driver, rejected because naming a driver is not the same as claiming something about the set of drivers. Two technology features do carry a delta, both because a bullet of theirs describes the framework's withholding or the capability landscape rather than its own target alone: `vs-adapter/postgresql-pushdown` on two bullets and `vs-adapter/mysql-pushdown` on one.
- **Rationale:** Writing the reason down is what stops the next reader treating an unchanged file as an oversight.
- **Promotes to ADR:** no

### [16] Trino advertises `AGGREGATE_GROUP_BY_TUPLE` beyond PostgreSQL parity, and nothing else

- **Decision:** `drivers/trino.toml` states the 35 entries `drivers/postgresql.toml` states plus `AGGREGATE_GROUP_BY_TUPLE`, 36 in all. The MySQL and PostgreSQL dialects keep their sets unchanged. `AGGREGATE_GROUP_BY_EXPRESSION` and `AGGREGATE_HAVING` stay withheld for every dialect, Trino included, and no rendering work is scheduled for either. `JOIN_CONDITION_ALL` stays withheld on the mission.md boundary decision `[2]` records, untouched by this entry. Supersedes in part decision `[2]`, "Trino's advertised set is PostgreSQL's 35 entries, and every absence is a framework decision".
- **Alternatives:** Keep exact PostgreSQL parity, which is what decision `[2]` chose and what the plan-reviewer flagged as a dropped half of the requester's ask. Lift `AGGREGATE_GROUP_BY_EXPRESSION` and `AGGREGATE_HAVING` for Trino beside it, rejected because neither is confirmed to need no rendering change: Trino executes both, but lifting either would buy rendering work in three dialects rather than none, and the requester declined to pursue it. Lift `AGGREGATE_GROUP_BY_TUPLE` for every dialect, rejected because widening this release's shared floor is a scope change for MySQL and PostgreSQL that nothing about adding a Trino driver motivates. Lift `JOIN_CONDITION_ALL`, not considered here: the reviewer judged the mission.md boundary behind it the stronger claim and the requester's answer did not reach it.
- **Rationale:** The interview's own words were "matching, and where Trino's SQL surface allows, exceeding, PostgreSQL's capability set", and decision `[2]` answered only the matching half, declining the exceeding half by planner fiat under a Non-Goal. The reviewer found the one entry where the exceeding half is free: `vs-adapter/pushdown-dialect` already records that `AGGREGATE_GROUP_BY_TUPLE` "would need no rendering change in any: each dialect already renders every grouping column a request carries", so advertising it for Trino costs no renderer anything and the withholding was scope alone. That question was put to the requester, who answered: lift `AGGREGATE_GROUP_BY_TUPLE` for Trino only, hold the line on `AGGREGATE_GROUP_BY_EXPRESSION` and `AGGREGATE_HAVING` given neither is confirmed rendering-free, and pursue no rendering work for those two. Choosing whether a driver addition may move a release-wide scope boundary is the requester's judgement rather than the planner's, which is why decision `[2]`'s Non-Goal was the wrong place to settle it.
- **Consequences:** A Trino-backed virtual schema delegates a multi-column `GROUP BY` where a MySQL- or PostgreSQL-backed one withdraws it and Exasol groups locally, which is a throughput difference rather than a correctness one and the first capability difference in this release that is not about a target's SQL. The Trino and PostgreSQL sets no longer hold the same entries, so `vs-adapter/trino-pushdown`'s comparison scenario asserts one named difference rather than equality, and `capabilities_tests.rs::trino_capability_set_is_exact` pins the 36-entry set against an independently written constant so neither the widening nor any remaining absence rests on prose. `vs-adapter/pushdown-aggregation` and `vs-adapter/pushdown-dialect` now state Trino as the one exception to a withholding they previously stated for every dialect. plan.md's Non-Goal is narrowed from "widening the capability vocabulary itself" to naming what specifically stays out. Gate 2.3(i) confirms Trino executes the rendered multi-column form before the entry ships.
- **Promotes to ADR:** yes

## Review Findings

### [plan-review] Trino's advertised set was capped at PostgreSQL parity against the requester's ask

- **Finding:** `[SCOPE_REDUCTION]` BLOCKER, round 1, Intent Fidelity. - **Promotion note:** the decision this finding produced is decision `[16]`, which carries the promotion; a second ADR for the act of resolving the finding would say nothing `[16]` does not.
