# Plan: add-trino-support

## Summary

Adds Trino as a third ADBC source with full pushdown coverage: the Trino dialect advertises the 35 capabilities the PostgreSQL dialect advertises plus one it does not, `AGGREGATE_GROUP_BY_TUPLE`, 36 in all, stated independently and rendered by its own renderer. Nothing is withheld from Trino for a reason about Trino's SQL. Two framework changes carry it: the recorded source qualifier becomes an ordered segment list, because a Trino table is named `catalog.schema.table`, and the credential travels percent-encoded inside the one connection URI the Trino driver accepts.

**One capability exceeds PostgreSQL parity, and exactly one.** `AGGREGATE_GROUP_BY_TUPLE` is advertised for Trino alone. Trino executes a multi-column `GROUP BY`, and `vs-adapter/pushdown-dialect` already records that adding the capability needs no rendering change in any dialect, because each one already renders every grouping column a request carries. Decision `[16]` records the requester's own answer on that boundary, and why `AGGREGATE_GROUP_BY_EXPRESSION` and `AGGREGATE_HAVING` stay withheld beside it.

**Trino needs no collation suffix anywhere.** Trino's documentation states that `varchar` comparison and ordering are Unicode code-point order, which is Exasol's, and lists no `COLLATE` keyword in its SQL grammar. Where MySQL renders two collations and PostgreSQL one, Trino renders none. Every claim in that sentence is read from documentation rather than executed: gates 2.3(a) and 2.5 measure both halves against a live Trino before the rule is advertised. Decision `[7]` records the rule, its source, and the one deployment condition that can still break it.

**One source property this release states without enforcing.** A Trino catalog whose connector pushes a string comparison down to a remote database applies that database's collation rather than Trino's. Trino documents the hazard per connector and offers no engine-level guarantee, and no catalog Trino exposes reports the condition, so no check the adapter could run would read it. Decision `[8]` records why it is stated rather than checked, and § Impact states what an operator owns.

## Design

### Context

adbc-vs keys every per-driver fact on a closed `Driver` enum with three tables behind it: the driver package in `adbc-vs-scan`, and the dialect and the metadata source in `adbc-vs-adapter`. Adding PostgreSQL established that shape; adding Trino exercises it. The compiler names every table a third variant must extend, so the mechanical half of this plan is decided already.

Three things the existing shape does not answer:

- **A Trino table has a two-part qualifier.** `adapterNotes` records one namespace string, and every dialect renders it as one quoted identifier. A Trino table is `catalog.schema.table` and its `information_schema` is scoped to one catalog, so one string cannot name the qualifier without being split at a character a catalog or schema name may contain.
- **Trino's catalog reports a column's full type only as a string.** `information_schema.columns` has no `character_maximum_length`, `numeric_precision`, `numeric_scale`, or `datetime_precision` column at all: those names are absent, not null. Every declared length, precision, and scale lives inside the `data_type` string, so Trino's mapping parses where the other two read fields.
- **The credential has only a URI to travel in.** The driver accepts one `uri` option and documents no separate username or password option. This is PostgreSQL's problem in a different shape: that driver offered a keyword/value form whose escaping is total, and Trino's offers a URI whose userinfo component is percent-encoded.

- **Goals** — Trino advertises every capability this release's vocabulary holds that any dialect advertises, plus `AGGREGATE_GROUP_BY_TUPLE`, which no dialect advertised before this release and which costs no dialect a rendering change; each entry it does not advertise is named together with the decision that withholds it; every rendering rule this plan states is sourced to Trino's own documentation or to the `trinodb/trino` source at tag `483`, and carries a phase-2 gate that measures it against a live Trino before the code advertising it is written.
- **Non-Goals** — widening the capability vocabulary beyond `AGGREGATE_GROUP_BY_TUPLE`. `AGGREGATE_GROUP_BY_EXPRESSION` and `AGGREGATE_HAVING` stay withheld for every dialect, Trino included, because neither is confirmed rendering-free and lifting either would buy a rendering change in three dialects rather than none. `JOIN_CONDITION_ALL`, `FN_AGG_SUM`, `FN_AGG_AVG`, and every scalar function likewise stay withheld for every dialect. Trino would execute all of them, but each is withheld by a framework or mission decision that binds every target identically, and lifting one is a change to this release's scope rather than a driver addition. Decision `[16]` records who drew that line and where.

### Decision

#### Architecture

```
CREATE VIRTUAL SCHEMA … DRIVER='trino' CONNECTION_NAME='…'
        │
        ▼
  create_schema ──► provisioning ──► drivers/trino.toml   (package row + capability list)
        │                                    │
        │                                    ▼  build.rs, compile time
        │                             Driver::Trino ──► package() / capabilities()
        ▼
  connection::trino_target ──► uri = address + percent-encoded userinfo
        │
        ▼
  TrinoSource  ──► <catalog>.information_schema.{tables,columns}
        │              └─► trino_type_mapping: parse data_type → MappedType
        ▼
  adapterNotes.database = ["<catalog>", "<schema>"]     (array; one segment still a string)
        │
        ▼
  getCapabilities / pushdown ──► dialect_for(Trino) ──► TrinoDialect
                                                            │
                                     "cat"."sch"."tab", no COLLATE, DOUBLE '…',
                                     LIKE … ESCAPE '\', FULL OUTER JOIN
```

#### Patterns

| Pattern | Where | Why |
|---------|-------|-----|
| Qualifier as an ordered segment list, not one string | `MetadataSource::namespace`, `AdapterNotes.database`, `SourceTable.namespace` | A Trino table is named by two segments and a catalog or schema name may contain a dot, so a single string cannot be split back into them |
| The qualifier's segment count is one declared value, not a fact two modules know | `drivers/<technology>.toml`, generated like the capability list | The address check runs before a connection exists and the metadata source answers after one does; both need the count, and two modules deciding how deeply a technology nests its tables can disagree |
| Single-segment qualifier serialized exactly as before | `AdapterNotes` writes a string for one segment and an array for more | A virtual schema created before this release is read back rather than recreated, and one field cannot disagree with itself where two could |
| Qualify fully, never rely on a session default | `TrinoDialect` renders `"catalog"."schema"."table"` | The connection selects a catalog, but a generated statement that depends on it carries state `EXPLAIN VIRTUAL` does not show and the adapter does not control |
| Percent-encode the whole credential, not the characters that need it | `connection::trino_target` | Encoding every byte outside the RFC 3986 unreserved set is one unconditional pass; a rule that recognized a hazardous set is the partial escaping that made URI form wrong for PostgreSQL |
| Redact both forms of the secret | the shared open path's diagnostic | A driver message quoting the URI it failed on discloses the percent-encoded spelling while a check for the verbatim bytes passes |
| No collation suffix, stated as a claim with a gate behind it rather than as an absence | `vs-adapter/trino-collation` | "This dialect renders none" is only safe while Trino's own comparison is Exasol's, which is a fact gate 2.3(a) measures against the same fixture that proves MySQL needs two |
| Exact-numeric and floating-point literals render differently | `TrinoDialect::render_literal` | Trino types a bare decimal constant `DECIMAL`, so a floating-point literal rendered bare is an exact-numeric operand where Exasol meant a floating-point one |
| An explicit `ESCAPE` clause on every `LIKE` | `TrinoDialect::render_like` | Trino defines no default escape character, so a pattern Exasol built under its own backslash rule matches a different row set with no clause |
| Parse the catalog's type string rather than read its fields | `trino_type_mapping` | Trino's `information_schema.columns` carries no length, precision, or scale column, so `data_type` is the only place the declared type exists |
| Precondition check that succeeds by design, not by omission | `TrinoSource::check_source` | Everything Trino's rendering depends on is fixed in its SQL engine, so a check would have nothing to read; the framework contract still runs it |
| Measure before advertising | Gates 2.0 to 2.5 precede every rule they justify, and every rendering claim in this plan names the gate that confirms it | An advertised capability the source refuses converts a query Exasol would have answered into a hard failure, and a documented behaviour is not an executed one |
| One stack-up target per source, plus one for Exasol | `Makefile` | A fourth container makes every E2E job pay for sources it never queries, which the two accepted-but-wasteful notes in `CLAUDE.md` already record as a cost |

#### Trino's advertised set, entry by entry

The set is the 35 entries `drivers/postgresql.toml` states plus `AGGREGATE_GROUP_BY_TUPLE`, 36 in all. It is written out in `drivers/trino.toml` independently, and `capabilities_tests` renders each one through `TrinoDialect`.

| Group | Advertised | Rendering that covers it |
|-------|-----------|--------------------------|
| Projection | `SELECTLIST_PROJECTION`, `SELECTLIST_EXPRESSIONS` | Quoted column list; the empty select list renders the constant `1` |
| Filter | `FILTER_EXPRESSIONS` | `WHERE` over the shared predicate renderer |
| Aggregation | `AGGREGATE_SINGLE_GROUP`, `AGGREGATE_GROUP_BY_COLUMN`, `AGGREGATE_GROUP_BY_TUPLE` | No `GROUP BY` for a single group; otherwise every grouping column the request carries, in the order `groupBy` gives them, which is the rendering every dialect already performs |
| Aggregates | `FN_AGG_COUNT`, `FN_AGG_COUNT_STAR`, `FN_AGG_COUNT_DISTINCT`, `FN_AGG_MIN`, `FN_AGG_MAX` | `COUNT`, `COUNT(*)`, `COUNT(DISTINCT x)`, `MIN`, `MAX`, all upper case, all bare of any suffix |
| Predicates | `FN_PRED_AND`, `FN_PRED_OR`, `FN_PRED_NOT`, `FN_PRED_EQUAL`, `FN_PRED_NOTEQUAL`, `FN_PRED_LESS`, `FN_PRED_LESSEQUAL`, `FN_PRED_IS_NULL`, `FN_PRED_IS_NOT_NULL`, `FN_PRED_BETWEEN`, `FN_PRED_IN_CONSTLIST` | Parenthesized standard forms; `<>` for not-equal |
| `LIKE` | `FN_PRED_LIKE`, `FN_PRED_LIKE_ESCAPE` | `x LIKE p ESCAPE 'c'`, the clause rendered for both, carrying a backslash when the request carries no `escapeChar` |
| Literals | `LITERAL_NULL`, `LITERAL_EXACTNUMERIC`, `LITERAL_DOUBLE`, `LITERAL_STRING`, `LITERAL_DATE`, `LITERAL_TIMESTAMP` | `NULL`; a bare numeric constant; `DOUBLE '…'`; `'…'` with the quote doubled; `DATE '…'`; `TIMESTAMP '…'` |
| Joins | `JOIN`, `JOIN_TYPE_INNER`, `JOIN_TYPE_LEFT_OUTER`, `JOIN_TYPE_RIGHT_OUTER`, `JOIN_TYPE_FULL_OUTER`, `JOIN_CONDITION_EQUI` | The four keywords over positionally aliased tables; Trino's documented join syntax places no restriction on a full join's condition, which gate 2.3(d) measures |

One entry is advertised for Trino and for no other dialect:

| Advertised, Trino only | Reason | Owner |
|------------------------|--------|-------|
| `AGGREGATE_GROUP_BY_TUPLE` | Trino executes a multi-column `GROUP BY`, and the capability needs no rendering change in any dialect: `vs-adapter/pushdown-dialect` already records that each dialect renders every grouping column a request carries, so this widening costs no renderer anything. The requester drew the line here and nowhere else | decision `[16]`, `vs-adapter/pushdown-aggregation` |

Every capability name this release's vocabulary holds and Trino does not advertise, with the decision that withholds it:

| Withheld | Reason | Owner |
|----------|--------|-------|
| `JOIN_CONDITION_ALL` | mission.md scopes pushdown to equi and outer joins. Trino would execute a non-equi condition, including under a full outer join; the boundary is this project's, not Trino's | mission.md, `vs-adapter/pushdown-join` |
| `AGGREGATE_GROUP_BY_EXPRESSION`, `AGGREGATE_HAVING` | This release groups by columns rather than expressions and applies `HAVING` in Exasol, for every dialect. Trino executes both, but neither is confirmed rendering-free the way `AGGREGATE_GROUP_BY_TUPLE` is, so lifting either buys a rendering change in three dialects rather than none | `vs-adapter/pushdown-aggregation`, decision `[16]` |
| `FN_AGG_SUM`, `FN_AGG_SUM_DISTINCT`, `FN_AGG_AVG`, `FN_AGG_AVG_DISTINCT` | A capability admits every numeric operand, and a floating-point sum is order-dependent. Trino distributes an aggregation and combines partial results, so its accumulation order is not stable between two runs | `vs-adapter/pushdown-aggregation` |
| `ORDER_BY_COLUMN`, `ORDER_BY_EXPRESSION`, `LIMIT`, `LIMIT_WITH_OFFSET` | The emitting-UDF transport carries no ordering guarantee, whatever the source | `vs-adapter/result-ordering` |
| `LITERAL_BOOL` | No mapped column produces Exasol `BOOLEAN`, and the declarable-set closure rests on that | `vs-adapter/type-mapping`, `vs-adapter/pushdown-dialect` |
| Every `FN_<scalar>` | No dialect advertises a scalar function, which is what keeps the declarable type set closed | `vs-adapter/pushdown-dialect` |

No entry in that table is withheld because Trino's SQL cannot render it. That is the plan's answer to "full pushdown coverage": Trino reaches the ceiling this release's vocabulary sets, exceeds it by the one entry that costs no dialect a rendering change, and every remaining ceiling is this project's rather than Trino's.

### Consequences

| Decision | Alternatives Considered | Rationale |
|----------|------------------------|-----------|
| Trino alone advertises `AGGREGATE_GROUP_BY_TUPLE` | Keep exact PostgreSQL parity; lift `AGGREGATE_GROUP_BY_EXPRESSION` and `AGGREGATE_HAVING` for Trino too; lift all three for every dialect | The requester asked for a set matching PostgreSQL's and exceeding it where Trino's SQL surface allows. This is the one entry Trino executes that costs no dialect a rendering change, which `vs-adapter/pushdown-dialect` already states. The other two are executable by Trino but not confirmed rendering-free, so they stay withheld release-wide. Lifting for every dialect is a release-scope change rather than a driver addition. Decision `[16]` records the requester's own answer |
| Recorded qualifier becomes an ordered segment list | Record `<catalog>.<schema>` as one string the dialect splits; qualify with the schema alone and rely on the catalog the connection selected; add a second notes field for the catalog | A joined string cannot be split back when a name contains a dot. Relying on the session catalog puts state into resolution that the generated statement does not carry and `EXPLAIN VIRTUAL` does not show, which is the invisible-server-state argument that already rejected `search_path` auto-detection for PostgreSQL. A second field lets two records of one fact disagree |
| A single segment still serializes as a string | Always serialize an array and migrate | Notes Exasol persisted are read back, never recreated, so a virtual schema created before this release must parse. Serializing the common case unchanged also leaves MySQL's and PostgreSQL's generated statements byte-identical |
| The address's path element count is checked against the driver's arity | Take everything after the first `/` as one qualifier, as today | Today a `postgresql://host/db/extra` address silently takes `db/extra` as the database. With two-segment qualifiers that leniency becomes a way to address the wrong object, so the count is checked and both too few and too many fail with a named error |
| Credential percent-encoded into the URI userinfo, totally | Encode only the characters the URI grammar reserves; pass the credential as a query parameter; look for an undocumented username option | Encoding every byte outside the unreserved set is one pass with no set to keep correct, and encoding more than required is always valid in a userinfo component. A query parameter is not where the driver documents a credential. Gate 2.1 checks the undocumented-option question empirically rather than inferring it from the driver's docs being silent |
| Redaction strips the percent-encoded spelling as well | Strip the verbatim bytes only, as PostgreSQL does | PostgreSQL's conninfo form and its verbatim form are both stripped today for the same reason. The URI adds a third spelling, and a driver message quoting the URI it failed on would carry exactly that one |
| The Trino dialect renders no collation suffix | Render one for ordering, mirroring PostgreSQL; refuse character operands | Trino's SQL grammar lists no `COLLATE` keyword in any syntactic position, so a suffix is not a design option; gate 2.5 measures that. It is also not needed: Trino's documentation states that `varchar` compares and sorts by Unicode code point, which implies `A B Z a e z Ä ä é` for the fixture's values and `B`/`ä` for `min`/`max` over `a B Z ä`, the answers Exasol gives; gate 2.3(a) measures both against a live Trino and a live Exasol before the rule ships |
| The connector-pushdown condition is stated and not checked | Refuse a catalog whose connector reaches a remote system; withhold `FN_PRED_LESS`, `FN_AGG_MIN`, and `FN_AGG_MAX` from Trino | Refusing every federating catalog refuses what Trino is for. Withholding the range capabilities would cost every Trino deployment the coverage this plan exists to deliver, for a condition the operator configures and can avoid. No catalog Trino exposes reports the condition, so a check would have nothing to read |
| `LITERAL_DOUBLE` renders `DOUBLE '<value>'` | Render it bare like the exact-numeric literal; append `E0` | Trino's type documentation states that a bare decimal constant is typed `DECIMAL`, so `typeof(123.45)` is expected to be `decimal(5,2)` and a bare floating-point literal is an exact-numeric operand; gate 2.3(b) measures it. Appending `E0` breaks on a value already carrying an exponent, where the typed form is total |
| Every `LIKE` renders an `ESCAPE` clause | Pass the pattern through unchanged, as the other two dialects do | Trino defines no default escape character, so a pattern carrying `\%` would match a backslash followed by anything instead of a literal `%`, which is wrong rows rather than an error |
| A pattern whose escape character precedes something the target rejects fails in the dialect | Emit the statement and let Trino reject it; drop or rewrite the sequence | An error the operator can read beats the source's message about a pattern the operator never typed, and rewriting changes which rows come back. Same outcome MySQL's composed-shape exclusion takes |
| `char(n)` unmapped | Map to Exasol `VARCHAR`; map to Exasol `CHAR` | Trino blank-pads it, and its documentation states that `char` comparison ignores trailing spaces while pattern matching does not, so `LIKE` is expected to see the padding where `=` does not and two delegated predicates over one mapped column would disagree; gate 2.2 measures that disagreement. Exasol `CHAR` would match the value but four features state that every delegated character operand is `VARCHAR` |
| `version_range = ">=0.5.3, <0.6.0"` | `>=0.5.0, <0.6.0`; `>=0.5.3, <1.0.0`; pin `0.5.3` exactly | The floor is the version phase 2's gates run against: nothing has run this adapter against a lower published `0.5.x`. The ceiling stops below the next pre-1.0 minor because a pre-1.0 minor bump is breaking by SemVer convention, which is the rule MySQL's ceiling follows and PostgreSQL's does not. Resolution selects the highest satisfying version, so the floor is a statement about what the gates measure rather than what gets installed |
| No source-server precondition for Trino | Check a server version floor; check the catalog's connector | Everything the rendering depends on is fixed in Trino's SQL engine rather than configurable, so a check would have nothing to read. The oldest release any rendered construct needs is 335, older than any server a supported driver reaches |
| `stack-up` splits into `stack-up-exasol` plus one target per source | Add `stack-up-trino` to `stack-up` and leave every E2E job starting four containers | A fourth container plus a JVM makes the two accepted-but-wasteful notes already in `CLAUDE.md` expensive rather than negligible. Each `test-e2e-<source>` now starts Exasol and only the sources its own binary queries. This supersedes the "one everything-up entry point" acceptance those notes record |
| The E2E Trino serves HTTPS with a self-signed certificate and file password authentication | Run it unauthenticated over plain HTTP | The driver sends Basic authentication only over an encrypted connection, so an unauthenticated container would leave the percent-encoding rule untested end to end — which is exactly where a wrong parse produces a wrong-host connection rather than a test failure |
| The E2E and integration fixture uses the built-in `memory` catalog | Use a JDBC catalog against the existing PostgreSQL container; use `tpch` | `memory` reaches no remote system and pushes nothing down, so what it measures is Trino's own comparison rather than a connector's. It also ships in the stock image, so the stack needs no catalog file. `tpch` is read-only and cannot hold the case, accent, and null fixtures the differential tests need |

## Impact

- **New capability.** `CREATE VIRTUAL SCHEMA … WITH DRIVER = 'trino'` becomes valid. The `CONNECTION` object's address is `trino://host[:port]/<catalog>/<schema>[?parameters]`, with the source user and password in the object's own fields. A Trino server serving a certificate the driver cannot verify is reached by adding `SSLVerification=NONE` to the address; a server on plain HTTP is reached by adding `SSL=false`, and the driver then refuses to send a password.
- **Breaking for a malformed address that used to be accepted.** A source `CONNECTION` address carrying more path elements than its driver's qualifier needs is now refused with a named error. Before this release `mysql://host:3306/db/extra` took `db/extra` as the database name and failed later at the source; it now fails at `CREATE VIRTUAL SCHEMA` with a message naming both counts. No correctly formed address changes behavior.
- **`adapterNotes` may now carry an array where it carried a string.** A virtual schema over MySQL or PostgreSQL records exactly what it recorded before, and notes written by any earlier release parse unchanged. Only a Trino virtual schema records the array. An operator reading the notes back sees two names where a Trino schema is concerned.
- **Operator responsibility this release does not check.** A Trino catalog whose connector pushes a string comparison down to a remote database applies that database's collation, not Trino's. Trino's own default is to suppress string range pushdown for exactly this reason, but that default is per connector, equality pushdown is not suppressed, and the PostgreSQL connector documents a property that removes the suppression. An adbc-vs virtual schema over such a catalog can return rows Exasol would not, and adbc-vs cannot see the condition. The remedy is the operator's: leave the connector's string-pushdown opt-out off, or back the virtual schema with a catalog whose comparison is Trino's own.
- **Developer-facing build change.** `make test-e2e` and `make test-e2e-postgres` now start Exasol plus only the sources their own binary queries, instead of every source. `make stack-up` still starts everything and keeps its meaning for local use. `make bench` no longer starts the containers it never queried.
- **A Trino virtual schema delegates a grouping the other two withdraw.** Trino is the only driver advertising `AGGREGATE_GROUP_BY_TUPLE`, so a `GROUP BY` naming more than one column is delegated over Trino and grouped locally by Exasol over MySQL and PostgreSQL. It is a throughput difference, not a correctness one: both routes return the same rows.
- **No change to any released pushdown behavior.** MySQL's and PostgreSQL's advertised sets, rendered statements, and recorded notes are unchanged, and the existing tests that assert them byte for byte stay green.

### Phase 2: Gates

Each gate measures a claim this plan advertises before the code that advertises it exists. A gate that fails is recorded in `decision-log.md` under Review Findings and the dependent rule is re-decided rather than shipped.

- [ ] 2.0 Gate [expert]: prove the Trino driver library loads inside the Exasol UDF sandbox, before anything else in this plan is built. Fetch the published `linux_amd64` package, upload the shared library it names to BucketFS, and load it from a UDF by `AdbcDriverTrinoInit`. The library is roughly 43MB, an order larger than either shipped driver, so the upload, the visibility wait, and the sandbox's own memory budget are all under test here and not only the symbol. **If the library does not load, stop and re-plan**: a load failure over an unresolved dependency is fixed in `language-container-rs` and returns through the release chain, which blocks every later phase.
- [ ] 2.1 Gate [expert]: prove the connection path against the container from task 1.1. Confirm first that the driver accepts a `trino://` scheme URI rather than only `http://` or `https://`, because `vs-adapter/driver-selection` requires the address's scheme to equal the driver's canonical name and the driver's own connect example uses `http://`. **If only an `http` scheme is accepted, stop and re-plan**: the scheme-match rule is a framework rule this plan does not otherwise touch. Then open a connection with a `uri` whose userinfo carries a percent-encoded user and password, for a password containing `@`, `/`, `:`, `?`, `#`, `&`, a space, and a multi-byte character, and assert the connection authenticates rather than merely opening. Assert that a wrong password fails and that `SSLVerification=NONE` reaches a self-signed certificate. Separately, probe whether the driver accepts a `username` or `password` database option distinct from `uri`, because the driver's documentation is silent rather than explicit. **If a separate option exists, stop and re-plan `scan-udf/trino-scan`**: the credential leaves the URI and the percent-encoding rule and its redaction scenarios go with it. **If no password can be sent at all, stop and re-plan** tasks 1.1 and 8.5.
- [ ] 2.2 Gate: read `<catalog>.information_schema.tables` and `.columns` through the driver against the task 1.2 fixture, extended for the measurement with one column of each type `vs-adapter/trino-type-mapping` names. Record the exact `data_type` string for every one, the `is_nullable` values, the `table_type` values, and the Arrow type each catalog column arrives as, `ordinal_position` included. This is what the `data_type` parser is written against; a spelling that differs from the ones the spec names is a spec correction rather than a parser special case. Measure one further claim here, because it decides an omission rather than a spelling: whether `CAST('abc' AS CHAR(5)) LIKE 'abc'` and `CAST('abc' AS CHAR(5)) = 'abc'` disagree, which is the second reason `vs-adapter/trino-type-mapping` gives for leaving `char(n)` unmapped. If they agree, that sentence is a spec correction and the blank-padding reason stands alone.
- [ ] 2.3 Gate [expert]: measure the rendering rules against Trino 483 and Exasol 2025.2.1 over one fixture. (a) Ordering and equality over `B`, `a`, `C` plus a case-only and an accent-only pair, comparing Trino's `ORDER BY`, `<`, `MIN`, `MAX`, `GROUP BY`, and `COUNT(DISTINCT)` against Exasol's answers over identical values, so the no-collation rule is proven rather than assumed. Record Trino's own returned ordering for the nine values `a`, `B`, `Z`, `z`, `A`, `ä`, `Ä`, `é`, `e` and its `min`/`max` over `a`, `B`, `Z`, `ä`, because `vs-adapter/trino-collation` states both results and neither has been executed. (b) `DOUBLE '<value>'` against a bare constant for a `double` column comparison, a bare constant against a `decimal` column, and `typeof(123.45)`, which is the claim that a bare decimal constant is typed `DECIMAL` rather than a floating-point value. (c) `LIKE` with and without `ESCAPE '\'` over a pattern carrying `\%`, `\_`, `\\`, and an escape character followed by a character that is none of those, recording whether Trino rejects the last and what Exasol returns for the same pattern. (d) `FULL OUTER JOIN` over an equality, returning both unmatched rows, and over each of `ON a.k < b.k`, `ON a.k <> b.k`, and `ON true`, recording whether each executes and null-extends both sides; `vs-adapter/trino-pushdown` states that all three do, and that statement is what separates Trino's `JOIN_TYPE_FULL_OUTER` from PostgreSQL's. (e) A select-list predicate reading the query's own bare character `GROUP BY` key, which Trino's strict grouping rule must accept. (f) `E'a'`, recording whether Trino rejects it and with what message; `vs-adapter/trino-pushdown` states it parses as a typed literal of an unknown type `e` and fails, which is why the string-literal form escapes nothing but the quote. (g) A bare quoted string compared against a `date` column — `DATE '2024-01-01' = '2024-01-01'` and a `BETWEEN` over two string bounds — recording whether each fails and with what message, which is the claim that makes the typed temporal literal mandatory rather than defensive. (h) A decimal literal carrying more than 38 significant digits, recording whether Trino rejects it outright rather than widening it to a floating-point value, which is what makes the bare exact-numeric form safe for every literal Exasol can send. (i) A multi-column `GROUP BY` rendered as the Trino dialect will render it, confirming Trino executes it, which is the one capability this plan advertises beyond PostgreSQL parity.
- [ ] 2.4 Gate: measure the Arrow type the driver returns for each mapped Trino type — specifically the decimal width for `decimal(12,4)` and `decimal(30,2)`, and the timestamp unit for `timestamp(0)`, `timestamp(3)`, `timestamp(6)`, and `timestamp(9)` — and check each against what `coerce.rs` already handles. Name every gap; task 7.2 closes them.
- [ ] 2.5 Gate: measure that `COLLATE` is not a Trino keyword in any syntactic position. Attempt a suffix after an ordering operand, an equality operand, a `GROUP BY` key, and a `DISTINCT` operand, recording the parse error and the set of legal continuations each reports; then use `COLLATE` as an ordinary column alias and as a column name, recording that both succeed. `vs-adapter/trino-collation` states all of this and none of it has been executed; it is what makes "this dialect renders no suffix" a statement about Trino's grammar rather than a stylistic choice. A failure here means Trino has a collation mechanism after all and `vs-adapter/trino-collation` is re-decided rather than shipped.

Sequencing notes:

- **Gate 2.0 runs before everything.** A Trino library the UDF sandbox cannot load is fixed in `language-container-rs` and returns through the release chain, which blocks every phase of this plan. It needs no Trino container of its own, so it does not wait on A.
- **A, C, and D start together and are the plan's only true fan-out point.** None of the three shares a file with another: A edits the stack and the build surface, C edits the adapter's qualifier plumbing, D edits the scan crate's identity and declaration. Everything downstream waits on some pair of them.
- **C and D touch one shared value.** Task 3.2 introduces the qualifier segment count into each technology's declaration file and task 4.1 declares Trino's, so 4.1 follows 3.2 for that one line while the rest of D is independent of C.
- **B gates E, F, and G, and only those.** A gate that fails changes a rule those three implement; none of them may start on a rule its gate has not returned. Gate 2.1 is the one that can invalidate a whole spec delta, so it runs first among the gates that need the container.
- **E, F, and G run concurrently** on disjoint files once B, C, and D are in. That is the plan's main parallel window: the scan crate's connection and coercion, the adapter's dialect, and the adapter's metadata source and mapping never meet.
- **G depends on C rather than merely following it.** Both edit `metadata.rs`: C changes `MetadataSource::namespace`'s signature and G adds the trait's Trino implementation. Running them concurrently is a merge in one file.
- **F depends on C for the same kind of reason one step removed.** C changes the qualifier field every dialect's table renderer reads, and F writes a new one against that field. Starting F first would write the renderer against a shape C then changes.
- **H is one group because `e2e_trino_test.rs` is one file** under `--test-threads=1` with one shared setup module. Its Knowledge overlaps F's and G's deltas because it is where those deltas are verified end to end, which is a sequence rather than a parallelism: three agents editing one test binary is contention, not a cluster.
- **I follows H** because a CI job may reference only a target whose test exists, and because `9.3`'s mission.md text states constraints the E2E tier is what proves.

`scan-udf/arrow-scan`'s existing "Provisioned driver loads inside the UDF sandbox" scenario is unchanged and already binds every supported driver, so Trino inherits it. Gate 2.0 measures it before the plan builds anything on it, and task 8.2's shared setup is what keeps it asserted afterwards.
