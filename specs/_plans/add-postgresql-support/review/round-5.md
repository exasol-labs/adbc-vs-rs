### Premortem

Six months out, three ways this failed:

1. **The merged library contradicted itself on PostgreSQL collation and nobody noticed until a query returned a syntax error.** `vs-adapter/pushdown-filter` merged with three untouched MySQL scenarios that state `COLLATE utf8mb4_0900_as_cs` and a hex literal as framework `MUST`s, while `vs-adapter/postgresql-collation` states the opposite. An implementer followed the framework feature and emitted SQL PostgreSQL cannot parse. → `[REQUIREMENT_CONFLICT]`, the one BLOCKER below.
2. **The third technology's author copied a half-migrated framework file.** `pushdown-projection` merged at 4 scenarios, 2 of them still saying "the generated MySQL statement". The next planner read the framework/technology convention off the files rather than off `CLAUDE.md` and reproduced the mixing the split existed to end. → advisory 1.

#### [REQUIREMENT_CONFLICT] BLOCKER

- Location: `specs/vs-adapter/pushdown-filter/spec.md` scenarios "LIKE renders its pattern and its escape character" (line 62), "BETWEEN and IN keep their operand order" (line 78), and "Predicate in select-list position renders as a projected boolean" (line 94) — all three untouched by any delta — against `specs/_plans/add-postgresql-support/vs-adapter/pushdown-filter/spec.md:8` (the new Background), `.../vs-adapter/postgresql-collation/spec.md:19-26`, and `.../vs-adapter/postgresql-pushdown/spec.md:54-61`.

- Issue: the restructuring rewrote `pushdown-filter`'s Background to declare the feature framework and to disclaim exactly the two rules three of its surviving scenarios still state. The new Background reads: "This feature owns what a filter fragment is, **for every dialect** … Each dialect's literal forms and advertised filter capabilities live in `vs-adapter/mysql-pushdown` and `vs-adapter/postgresql-pushdown`; each dialect's collation placement lives in `vs-adapter/mysql-collation` and `vs-adapter/postgresql-collation`." No delta marker touches the three scenarios below, so `/speq:record` merges them unchanged underneath that Background:

  - **"LIKE renders its pattern and its escape character"** — `* *THEN* the rendered clause MUST apply `COLLATE utf8mb4_0900_as_cs` to the compared operand` and `* *AND* the pattern MUST be rendered as a hex string literal`. Both are contradicted directly. `postgresql-collation` requires "the character operand of `predicate_equal`, `predicate_in_constlist`, and `predicate_like` MUST carry **no** collation suffix", and its Background bullet 5 grounds that in gate 2.3(f). `postgresql-pushdown` requires "`predicate_like` MUST render its pattern as an **escape-string constant**". Task 4.2 says `COLLATE "C"` goes on `predicate_less`, `predicate_lessequal`, and `predicate_between` "and to **nothing else**". The hex-literal step is the worse half: unlike the collation step it names no technology, so it reads as an unqualified release-wide `MUST` that PostgreSQL's `E'<body>'` form violates.
  - **"BETWEEN and IN keep their operand order"** — `* *AND* the character `IN` comparison MUST carry the collation suffix on the compared operand rather than on the list`. `postgresql-collation` requires `predicate_in_constlist` to carry none.
  - **"Predicate in select-list position renders as a projected boolean"** — `* *THEN* the generated statement MUST project the parenthesized comparison the same renderer produces for a `WHERE` clause, **including the collation suffix on a character operand**`. For a PostgreSQL equality predicate there is no suffix, so the step is either false or, read charitably, not testable as written.

  This is the class round 3 raised as ADVISORY ("Four library scenarios state a MySQL rule as an unqualified MUST"), and round 4's restructuring correctly migrated all four of the scenarios round 3 named — but not their siblings, and it **removed the defense round 3 relied on** to keep the severity at advisory. Round 3 scored it soft "because `COLLATE utf8mb4_0900_as_cs` and `_utf8mb4 X'<hex>'` name MySQL in their own text", so a reader could scope them. After round 4 the enclosing Background tells the reader the opposite: that this file contains no collation rule and no literal form. A reader who trusts the Background is wrong, and one who trusts the scenarios writes a PostgreSQL renderer that emits `COLLATE utf8mb4_0900_as_cs`, which PostgreSQL rejects outright. None of the three scenarios has a § Scenario Coverage row and no task opens them, so nothing in the plan would surface the conflict before record time.

- Fix: In `specs/_plans/add-postgresql-support/vs-adapter/pushdown-filter/spec.md`, add three `DELTA:REMOVED` blocks reproducing the library headings and bodies of "LIKE renders its pattern and its escape character", "BETWEEN and IN keep their operand order", and "Predicate in select-list position renders as a projected boolean" byte for byte from `specs/vs-adapter/pushdown-filter/spec.md:62`, `:78`, and `:94`. Then:
  (a) Add a `DELTA:NEW` framework replacement for each, stripped of every collation and literal-form step: "LIKE renders its pattern and its escape character" keeps only the `ESCAPE`-clause rules and states that each dialect's pattern literal form is its own feature's; "BETWEEN and IN keep their operand order" keeps only the two operand-order steps and states that whether a character operand carries a suffix is per dialect; "Predicate in select-list position renders as a projected boolean" replaces "including the collation suffix on a character operand" with "including whatever collation suffix that dialect's own feature requires in `WHERE` position, so one renderer serves both positions".
  (b) Add the MySQL halves as full scenarios in `specs/_plans/add-postgresql-support/vs-adapter/mysql-collation/spec.md` — a scenario asserting `COLLATE utf8mb4_0900_as_cs` on a `LIKE` operand and on an `IN` compared operand, and that a select-list predicate carries the same suffix as its `WHERE` counterpart — and add the hex-literal `LIKE` pattern step to `mysql-pushdown`'s existing "String literal is rendered as a hex literal" scenario.
  (c) Verify `postgresql-pushdown`'s "LIKE, IS NULL, BETWEEN, and IN render in their standard forms" and `postgresql-collation`'s "An ordering comparison is collated and equality is left bare" already cover the PostgreSQL halves — they do — and add no new PostgreSQL scenario.
  (d) Add a § Scenario Coverage row for each of the three replacement framework scenarios and each new MySQL scenario, mapping the framework rows to one test per dialect in `mysql_dialect_tests.rs` and `postgres_dialect_tests.rs`, and add the MySQL assertions to task 4.2's and task 4.5's scope so a task owns them.

## Design Depth

No objection — axis checked. Three questions from the diagnostic table matter here.

**Does exactly one module own each significant design decision?** For the code, yes — the `Driver` enum keys three tables and `dispatch` names no dialect. For the specs, this is where the BLOCKER above bites: collation placement currently has three owners (`mysql-collation`, `postgresql-collation`, and `pushdown-filter`'s three surviving scenarios), which is the information-leakage failure decision `[25]` cites `/speq:design-philosophy` to justify avoiding. Fixing the BLOCKER restores single ownership; nothing else in the split violates it.

**Is the `driver-provisioning` three-way cut a real boundary?** Yes, and I tested both placements the planner flagged as judgment calls independently:

- *"Already-installed driver short-circuits the fetch" in `driver-version-resolution` rather than `driver-self-install`* — correct, and arguably the only coherent placement. Decision `[23]` rebinds the presence check to the **resolved** version, so the scenario's decisive step is "the adapter MUST still read the registry index, because the version the presence check tests for is the resolved one and it cannot be known before resolution". The question it answers is "is the version I resolved to already here?", which is a resolution question. Putting it in `driver-self-install` would place an index-read requirement in a feature whose Background disclaims index reads, and would separate it from "Newer in-range version is installed beside an older installed one" — the negative arm of the same rule, which is unambiguously resolution.
- *"Unreachable registry names the offline fallback" in `driver-version-resolution` rather than `driver-path-override`* — defensible. The scenario's subject is the failure of an index read, which is squarely "an answer read out of the registry index". Naming `DRIVER_PATH` in an error message is not owning the property, the same way `create-virtual-schema` names `mysql` and `postgresql` in its unsupported-driver error without owning either technology. Its final step — "the adapter MUST NOT load an unrelated version it finds on the mount, because the install path carries a version the adapter could not resolve" — is meaningless outside the resolution feature. `driver-path-override`'s Background bullet 11 states the cross-reference explicitly, so the boundary is discoverable without reading internals.

  One seam is left implicit rather than stated: registry *transport* policy splits across two features — "Registry client always verifies the server certificate" stays in `driver-self-install` while "Unreachable registry…" moves to `driver-version-resolution`. The distinction (download-client policy vs. resolution failure) holds but is not written down. Not worth a finding; worth one sentence if the planner is editing those Backgrounds anyway.

The rejection of the execution-stage split (fetch → verify → upload) on temporal-leakage grounds is the right call and correctly reasoned in decision `[26]`: every stage would still carry the version decision. `driver-path-override` at 2 scenarios is thin but is a coherent feature with a real Background and both arms of its rule, not a stub.

**Are the framework Backgrounds deep or shallow?** Deep. Each rewritten Background states what the feature owns, what it no longer owns, and which feature took it — `pushdown-aggregation`, `pushdown-dialect`, `pushdown-filter`, `pushdown-join`, `pushdown-projection`, `type-mapping`, `arrow-scan`, and all three `driver-provisioning` features carry that sentence. `postgresql-collation`'s Background bullet 8 ("This rule set derives from nothing in `vs-adapter/mysql-collation`, and neither feature governs the other") is exactly the structural independence the instruction asked for.
