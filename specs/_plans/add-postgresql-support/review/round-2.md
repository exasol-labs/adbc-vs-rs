## Premortem

Two ways the *revision* fails, six months out.

1. **The keystone test never lands as a test.** Task 8.5 asks for the `getCapabilities` request the shipped adapter receives. Nothing captures that. The implementer either wires permanent request-echo instrumentation into the production `.so` — a disclosure surface nobody reviewed — or downgrades the assertion to the response, which is the absorbed departure the scenario forbids. The precondition the whole per-dialect design rests on ends up asserted by nothing. Routed to `[HIDDEN_DEPENDENCY]`.
2. **`speq record` halts on a threshold the plan under-counts, and the merged library keeps a MySQL claim no test asserts.** § Verification warns about three features; eight cross the line, and `vs-adapter` crosses the domain threshold too. Separately, the `pushdown-join` remove-plus-add leaves two both-dialect scenarios whose MySQL clauses map only to PostgreSQL test modules. Routed to `[COMPLETENESS_GAP]` and `[TRACEABILITY_GAP]`.

## Feasibility

#### [HIDDEN_DEPENDENCY] BLOCKER
- Location: plan.md task 8.5; § Scenario Coverage `vs-adapter/driver-selection` row "getCapabilities request carries the driver identity"; `vs-adapter/driver-selection/spec.md` scenario of the same name; `crates/adbc-vs-adapter/tests/common/probe.rs`
- Issue: task 8.5 says "capture the `getCapabilities` request the adapter receives for an existing MySQL virtual schema". No mechanism in the repo does that, and no task builds one. The only request-capture infrastructure is `crates/adbc-vs-adapter/tests/common/probe.rs`, and it cannot serve as written: it is a scratch Lua adapter script whose `createVirtualSchema` handler returns `adapterNotes = "{}"` (probe.rs:86) — empty, where the scenario needs a driver value — whose `getCapabilities` handler returns a fixed capability list without echoing anything (probe.rs:91-92), and which marker-echoes only the `pushdownRequest` JSON out through SQL error text (probe.rs:140-150). It captures what its own Lua adapter receives, never what the shipped `ADBC_ADAPTER` receives. Gate 2.1 offers two mechanisms — "the throwaway Lua adapter probe in `tests/common/probe.rs`, or log the raw request body from the Rust adapter" — both one-off instrumentation for a measurement; task 8.5 names neither and adds neither, and Group I gives it no prerequisite. The two outcomes left to an implementer are both bad: permanent request-echo instrumentation compiled into the production `.so`, which is an unreviewed disclosure surface, or a downgrade to asserting the *response*, which is exactly the departure the scenario says "MUST fail the test rather than be absorbed". Round 1's own fix text carried this gap and the planner reproduced it verbatim, so this is an under-specified prescription rather than a missed instruction — but the keystone assertion is still not executable.
- Fix: Rewrite plan.md task 8.5 to name the mechanism. State that it extends `crates/adbc-vs-adapter/tests/common/probe.rs` so the probe's `createVirtualSchema` handler returns a non-empty `adapterNotes` carrying a `driver` value and its `getCapabilities` handler echoes the request body it received through the existing `BEGIN_MARKER`/`END_MARKER` error channel, and that `get_capabilities_request_carries_adapter_notes` asserts the captured request carries `schemaMetadataInfo.adapterNotes` with that driver value. Add `crates/adbc-vs-adapter/tests/common/probe.rs` to the task's file list, and state that no request-capture instrumentation is added to the shipped adapter. Replace "for an existing MySQL virtual schema" with "for a virtual schema whose `createVirtualSchema` recorded a driver in `adapterNotes`", matching the scenario's own source-agnostic GIVEN.
