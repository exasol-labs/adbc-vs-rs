## Requirement Quality

#### [AMBIGUOUS_REQUIREMENT] BLOCKER
- Location: plan.md task 6.3, final sentence; plan.md § Scenario Coverage line 370; `crates/adbc-vs-adapter/tests/dispatch_test.rs:1-9` and `:127-141`
- Issue: two defects in the task the blocker-3 fix added, one factual and one infeasible. **Factual:** task 6.3 states that `dispatch_test.rs::missing_property_named_in_error` "asserts today that omitting `BUCKETFS_CONNECTION` errors unconditionally, which this change makes false". It does not. The test at `dispatch_test.rs:128-141` builds a request carrying `CONNECTION_NAME` and `BUCKETFS_CONNECTION` and omitting `DRIVER`, then asserts the error names `DRIVER`. The library scenario's `BUCKETFS_CONNECTION` arm has no assertion behind it today at all, so the change makes nothing false and there is no existing assertion to preserve. **Infeasible:** task 6.3 then requires that the same test "MUST additionally assert the statement succeeds when `DRIVER_PATH` is set". `dispatch_test.rs`'s own module doc fixes its contract — it "Exercises `adapter_call` for every request path that needs no live MySQL or Exasol connection", and states that "The scenarios that need live metadata discovery — a successful `createVirtualSchema` … are typed E2E in the plan and live in `e2e_mysql_test.rs`, not here." Its only context is `FakeCtx`, which resolves `CONNECTION` objects and nothing else. A `createVirtualSchema` that passes property validation goes on to open the source connection and discover tables, so success is unreachable there; worse, with `DRIVER_PATH` pointing at no real file the new readable-file check fires first and the call errors for a third reason. An implementer following the task literally either writes an assertion that cannot pass or builds live infrastructure into the file whose contract forbids it. The requirement itself is sound and already covered at the right tier — § Scenario Coverage line 375 maps "DRIVER_PATH is accepted and bypasses driver provisioning", which carries the same "MUST succeed with `BUCKETFS_CONNECTION` absent" step, to `e2e_postgres_test.rs::driver_path_is_accepted_and_bypasses_provisioning`, and line 377 maps the required-without-`DRIVER_PATH` half to `create_schema_tests.rs::bucketfs_connection_required_without_driver_path`. Only the mapping and the instruction are wrong.
- Fix: Rewrite plan.md task 6.3's final sentence. Delete the false claim that `missing_property_named_in_error` asserts a `BUCKETFS_CONNECTION` error today, and delete the instruction that it assert the statement succeeds. Replace both with: extend `dispatch_test.rs::missing_property_named_in_error` to add the `BUCKETFS_CONNECTION`-omitted-with-no-`DRIVER_PATH` case, asserting the error names `BUCKETFS_CONNECTION`, and to add a `DRIVER_PATH`-set case asserting that whatever error `FakeCtx` produces is not a missing-property error naming `BUCKETFS_CONNECTION` — the strongest claim that tier can make. State in the task that the success half of the scenario's last step is carried by `e2e_postgres_test.rs::driver_path_is_accepted_and_bypasses_provisioning` and the required half by `create_schema_tests.rs::bucketfs_connection_required_without_driver_path`. In plan.md § Scenario Coverage line 370, map "Missing required property fails with a named error" to those three tests rather than to `dispatch_test.rs::missing_property_named_in_error` alone.
