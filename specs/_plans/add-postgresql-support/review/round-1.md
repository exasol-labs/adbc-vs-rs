# Plan Review Findings: add-postgresql-support (round 1)

## Summary
- Axes checked: 6/6
- Total findings: 16 (Blockers: 5, Advisory: 11)
- Intent Fidelity blockers: 0

## Premortem

Three ways this plan fails six months out:

1. **The recorded library does not say what the plan said.** `speq record` applies `DELTA:CHANGED` by scenario name. Three CHANGED blocks name scenarios the library does not have, so `FULL OUTER JOIN` rendering, the per-dialect join-key collation rule, and the whole `mysqlType` → `sourceType` migration scenario never land, while the MySQL-named originals survive and contradict the merged Background. Routed to `[REQUIREMENT_CONFLICT]`.
2. **A PostgreSQL password reaches a SQL error message.** The adapter opens the source connection through the same code path the scan uses (`create_schema.rs:193-199`), so `createVirtualSchema` builds the same password-bearing conninfo string — but every requirement and every test about redacting it lives in `scan-udf/arrow-scan` and the scan's own test files. Routed to `[NFR_IGNORED]`.
3. **Phase 7 stalls on a URL nobody can build.** The PostgreSQL integration tier needs the driver library; the repo's only existing route to it derives the package URL from the pinned version string, which the plan asserts nothing depends on and spells two different ways. Routed to `[UNSTATED_ASSUMPTION]`.

## Intent Fidelity

Checked against the verbatim request's four clauses and the brief's five sub-requirements.

- *Dynamic pushdown*: satisfied by a real mechanism, not a second hardcoded list — `Driver` closed enum (`adbc-vs-scan::driver`), `dialect_for`/`metadata_source_for`/`package()` keyed on it, both `dispatch` arms resolving from `schemaMetadataInfo.adapterNotes`, `dispatch`'s `MySqlDialect` import removed (plan.md tasks 3.1-3.2; `driver-selection/spec.md` scenarios "Pushdown and capabilities resolve the driver from one field", "Every driver identity has a complete set of tables"). Verified against the code the refactor replaces: `dispatch.rs:91-92` does name `MySqlDialect` twice today, and `adapter_notes.rs:31` already carries `driver`.
- *Auto-download*: satisfied — `driver-self-install` delta keys the whole package row on the identity; no second install path.
- *Match MySQL scope*: pushdown scope matches exactly and adds one capability. The mapped-type set is 7 against MySQL's 8; the one divergence (`character(n)`) is disclosed in three places with a recorded alternative, so it is not a silent narrowing. See the advisory below.
- *Optimize via tasks*: satisfied — the shared foundation is Group D alone and four workstreams fan out from it on disjoint files.
- No MySQL scenario is dropped: verified mechanically that every library scenario absent from a delta is untouched (unmarked absence is a no-op at merge), and that every Background `DELTA:CHANGED` block reproduces the library bullets it replaces.

#### [SCOPE_REDUCTION] ADVISORY
- Location: decision-log.md § [9]; plan.md § Consequences, § Impact; `vs-adapter/type-mapping/spec.md` Background bullet 14
- Issue: the brief permits divergence from MySQL's scope only "where PostgreSQL's own SQL/type system genuinely cannot express something". `character(n)` is expressible — the plan says so: "Exasol `CHAR` would match both — measured on Exasol 2025.2.1 ... exactly as PostgreSQL's `character(n)` does". It is declined on cost: "four features state the invariant that every delegated character operand is Exasol `VARCHAR`, and reopening it is a larger change than this scope buys". That is a cost-based narrowing of the parity requirement, not an expressiveness limit, and MySQL's `CHAR` does map. It is loudly disclosed, which is why this is advisory rather than blocking.
- Fix: Add a sentence to decision-log.md `[9]` recording that the `character(n)` omission is bounded by the Exasol-`CHAR` invariant rather than by PostgreSQL, and naming the follow-up that would lift it (a plan revisiting the "every delegated character operand is `VARCHAR`" invariant across the four features that state it). Do not add the mapping to this plan.

## Feasibility

Verified externally against the Apache Arrow ADBC PostgreSQL driver's own source and the released 1.12.0 binary: `PostgresDatabase::SetOption` accepts only `uri` and rejects everything else with `ADBC_STATUS_NOT_IMPLEMENTED`; `Connect` calls `PQconnectdb(uri_.c_str())` with no scheme check or parsing, so a libpq keyword/value conninfo string passed as `uri` does work; `numeric` is returned as Arrow `utf8` for constrained and unconstrained columns alike; `timestamp without time zone` is always `timestamp[us]` regardless of the declared precision; the init symbol is `AdbcDriverPostgresqlInit`; the released `.so` is C++ and its `NEEDED` list is `librt.so.1`, `libdl.so.2`, `libstdc++.so.6`, `libm.so.6`, `libgcc_s.so.1`, `libc.so.6`; 1.12.0 is the current release and the driver documents testing against PostgreSQL 14-18. Every load-bearing driver claim in the plan holds. The findings below are the ones that do not.

#### [NFR_IGNORED] BLOCKER
- Location: `scan-udf/arrow-scan/spec.md` scenario "PostgreSQL credential never appears in any surfaced text"; `vs-adapter/create-virtual-schema/spec.md` scenarios "Unreachable source fails creation with a diagnosable message" and "PostgreSQL database whose encoding is not UTF8 is rejected at creation"; plan.md § Impact, task 5.4
- Issue: the adapter, not only the scan, builds the password-bearing PostgreSQL conninfo string. `crates/adbc-vs-adapter/src/create_schema.rs:193-199` opens the source connection through `adbc_vs_scan::connection::open_mysql_connection`, so `createVirtualSchema`, `refresh`, and `setProperties` all traverse the same connection value. Every requirement about redacting it is scoped to the scan — task 5.4 says "Strip the resolved password from every surfaced error", the only scenario asserting it is in `scan-udf/arrow-scan`, and both its tests live in `postgres_it_test.rs` and `connection_tests.rs`. `create-virtual-schema`'s own error scenarios require the error to "name the address it could not reach" and say nothing about the password. The current code makes this concrete: `connection.rs` calls `connect_error("opening an ADBC database for", &connection.uri, redact(&error.to_string(), &connection.password))` — `redact` is applied to the driver's message and never to the `subject`, which for PostgreSQL becomes the conninfo string itself. plan.md § Impact nevertheless claims unconditionally that "No credential is written into the scan specification, `adapterNotes`, generated SQL, `EXPLAIN VIRTUAL` output, or any log line or error message". That claim is untestable on the path where a source error is most likely.
- Fix: Add a `DELTA:NEW` scenario to `vs-adapter/create-virtual-schema/spec.md` requiring that no error surfaced by `createVirtualSchema`, `refresh`, or `setProperties` against a PostgreSQL source contains the source password — including a wrong-password error and an unreachable-host error — while still naming the host and database; map it in plan.md § Scenario Coverage to a named test in `crates/adbc-vs-adapter/tests/e2e_postgres_test.rs`. Extend task 5.4 to state that the connection value MUST NOT be interpolated as an error subject and that redaction applies to every caller of the shared open path, not to the scan alone, and add the assertion to task 8.4's scope.

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: plan.md tasks 2.4, 6.1, 7.2, § Dependencies; `driver-provisioning/driver-self-install/spec.md` Background bullet 10
- Issue: the plan's version-spelling story contradicts itself and the repo. (a) The delta asserts "The relative `url` inside a matched block ... is read from the index rather than constructed, so nothing else depends on the spelling." False here: `crates/adbc-vs-scan/tests/mysql_it_test.rs:39-44` builds the entire package URL as `{REGISTRY_BASE_URL}/{REGISTRY_DRIVER_PATH}/{DRIVER_VERSION}/{REGISTRY_DRIVER_PATH}_{PLATFORM}_{DRIVER_VERSION}.tar.gz`, and that helper is the only route the repo has to a driver library outside BucketFS. (b) Task 2.4 fetches `postgresql/v1.12.0/postgresql_linux_amd64_v1.12.0.tar.gz` — leading `v` in both the path segment and the filename — while task 6.1, § Dependencies, and the delta all pin the `version` scalar as `1.12.0` with no `v`. Under the repo's own derivation the pinned string yields `postgresql/1.12.0/postgresql_linux_amd64_1.12.0.tar.gz`. At most one of the two URLs exists; the plan asserts both. (c) Task 7.2 adds `crates/adbc-vs-scan/tests/postgres_it_test.rs` covering "driver load by the PostgreSQL entry point" but names no source for the library, and no task generalizes `package_url()`/`install_driver` for a second driver.
- Fix: In plan.md task 2.4, add recording the index's exact `version` scalar and the exact relative `url` for the PostgreSQL entry as gate outputs, and make task 6.1 and § Dependencies quote whichever spelling 2.4 measured rather than both. Correct `driver-provisioning/driver-self-install/spec.md` Background bullet 10 to state that the adapter reads the URL from the index while the integration tier derives it, and add a task to Phase 3 generalizing `mysql_it_test.rs`'s `package_url()` and `install_driver` into a per-driver helper `postgres_it_test.rs` reuses, listing it as a prerequisite of task 7.2.

#### [EFFORT_MISESTIMATION] BLOCKER
- Location: plan.md task 2.2, § Parallelization ("Group A → Group C"); decision-log.md § [15]
- Issue: task 2.2 reads as one measurement but is at least three pieces of work with none of its prerequisites stated. Loading a library "from inside the Exasol UDF sandbox ... calling the driver manager directly rather than through the scan path" requires (i) the PostgreSQL package downloaded and extracted, which depends on task 2.4 in a *different* parallel group and on the URL question above, (ii) a BucketFS upload with `BUCKETFS_CONNECTION` credentials, (iii) `make cross-udf-build` plus `make stack-up` plus the SLC installed — none listed, where tasks 8.x and 9.1 do list them, and (iv) a throwaway raw-load entry point compiled into the crates that Phase 3 then refactors. § Parallelization justifies the edge as "Group A → Group C (gates 2.2 and 2.3 need the PostgreSQL container)": gate 2.2 needs no PostgreSQL container at all, and needs Exasol, which Group A does not start. decision-log `[15]` meanwhile claims "Gate 2.2 is ordered earliest because it is the cheapest test of the highest-consequence unknown, and it needs neither the dialect nor the refactor to run" — the task graph orders it neither earliest nor cheaply, and the brief's own escalation path (a fix landing in `language-container-rs` and returning through the release chain) makes late discovery the most expensive outcome in the plan.
- Fix: Split task 2.2 into 2.2a (fetch and extract the PostgreSQL package; upload it to BucketFS by hand) and 2.2b (add a throwaway raw driver-load path and load the library inside the sandbox), state `cross-udf-build` and `stack-up` as prerequisites of 2.2b, move both ahead of Group A in § Parallelization, and correct the "Group A → Group C" rationale to bind Group A to gate 2.3 alone.

#### [UNSTATED_ASSUMPTION] ADVISORY

## Requirement Quality

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: `vs-adapter/pushdown-join/spec.md` scenarios "Each join type renders its counterpart" and "Inner join of two virtual tables renders one statement"; `vs-adapter/type-mapping/spec.md` scenario "Omission records the source type under a source-neutral field"
- Issue: all three are marked `DELTA:CHANGED`, and `/speq:spec-merge` applies that marker by replacing "scenario with same name". No library scenario carries any of these three names. The library has "Each join type renders its **MySQL** counterpart" and "Inner join of two virtual tables renders one **MySQL** statement" — the delta silently dropped "MySQL" from both headings — and `vs-adapter/type-mapping` has no omission scenario at all. Consequence at record time: the merge finds no target, so `full_outer` rendering ("`full_outer` MUST render as `FULL OUTER JOIN` in the PostgreSQL dialect"), the per-dialect join-key collation clause ("`COLLATE utf8mb4_0900_as_cs` for MySQL and no suffix for PostgreSQL"), and the entire `mysqlType` → `sourceType` migration scenario — the only test behind the plan's sole § Migration row — do not land, while the MySQL-named originals survive and contradict the merged Background, which now claims both dialects. Verified mechanically over all 11 changed features; these are the only three mismatches.
- Fix: Rename the two `pushdown-join` `DELTA:CHANGED` headings to the library's exact existing names — "Each join type renders its MySQL counterpart" and "Inner join of two virtual tables renders one MySQL statement" — keeping the new per-dialect clauses in the bodies, or add `DELTA:REMOVED` blocks for the old names alongside `DELTA:NEW` blocks for the new ones. Change the `type-mapping` omission scenario's marker from `DELTA:CHANGED` to `DELTA:NEW`.

#### [AMBIGUOUS_REQUIREMENT] ADVISORY
- Location: `vs-adapter/pushdown-filter/spec.md` scenario "PostgreSQL collates an ordering comparison and leaves equality bare", final clause
- Issue: "the suffix MUST be rendered on the compared operand rather than on a literal or on an `IN` list" is not testable for two shapes the advertised capabilities admit. A `predicate_less` whose both operands are character columns has two compared operands and the scenario does not say whether both carry the suffix; a `predicate_between` has three operands and the scenario does not say which. The Background bullet says "a character operand", which reads as all of them, and the scenario says "the compared operand", which reads as one.
- Fix: Replace the final clause with explicit rules — state that every character-typed operand of `predicate_less`, `predicate_lessequal`, and `predicate_between` carries `COLLATE "C"`, including both sides of a column-to-column comparison and all three `BETWEEN` operands, and that a literal operand carries none — and add the column-to-column and three-operand cases to task 4.5's collation-placement matrix.

#### [COMPLETENESS_GAP] ADVISORY
- Location: plan.md task 4.4; task 8.3; § Impact; § Manual Testing row `pushdown-dialect`
- Issue: task 4.4's fallback for a failed gate 2.3(a) names only `pushdown-join`'s and `pushdown-dialect`'s scenarios. Three other artifacts assert the two capability sets differ and would be left failing or false: task 8.3 ("assert each `getCapabilities` response is its own dialect's set with `JOIN_TYPE_FULL_OUTER` present for exactly one"), § Impact ("additionally delegates `FULL OUTER JOIN`"), and the § Manual Testing expectation "The PostgreSQL schema advertises `JOIN_TYPE_FULL_OUTER`; the MySQL schema does not". More importantly, if the sets coincide the plan loses its only *observable* proof that resolution is per virtual schema, and names no replacement.
- Fix: Extend task 4.4's fallback clause to list task 8.3, § Impact, and the § Manual Testing row as artifacts to revise, and name the substitute assertion for the coinciding-sets case — that each schema's response is produced by its own resolved dialect, proven by a distinct rendered statement per driver over the same request rather than by a set difference.

#### [COMPLETENESS_GAP] ADVISORY

## Design Depth

The core design holds up. `Driver` as a closed enum with three tables is the right owner for a decision release 0.2 restated in five modules (verified: `driver.rs:16-29`, `connection.rs:23`, `provisioning.rs:44-51`, `create_schema.rs`, `dispatch.rs:91-92`). `MetadataSource` returning already-mapped columns plus the source precondition check is a genuinely deep module — `create_schema` ends up branching on no driver — and decision `[12]`'s rejection of a separate `TypeMapper` on the grounds that no shared catalog row survives reduction is the correct information-hiding call. Splitting the tables across two crates keeps the dependency pointing one way, and decision `[1]` records why. Resolving both dispatch arms from one field is exactly the fix for the back-door leakage two independently-resolved fields would create.

#### [BOUNDARY_VIOLATION] ADVISORY
- Location: plan.md task 3.1, task 3.2; `vs-adapter/driver-selection/spec.md` Background bullet 9
- Issue: `Driver::parse` (case-insensitive matching of the `DRIVER` property value) and the user-facing error that "MUST list every driver value this release supports" land in `adbc-vs-scan::driver`, the scan crate. The scan executes a statement it does not parse and knows nothing else about `CREATE VIRTUAL SCHEMA`; putting the property vocabulary and the operator-facing message there gives the lower crate knowledge of the upper crate's delivery surface for no reason the plan states — the enum itself has to live low (the package table reads it), but the property parsing does not.
- Fix: Keep `Driver`, `as_str`, and `package()` in `adbc-vs-scan::driver` per decision `[1]`, and move `parse` and its supported-values error into `adbc-vs-adapter` beside `dialect_for`, where the `DRIVER` property is read; state the split in `vs-adapter/driver-selection/spec.md` Background bullet 9 so the crate boundary is part of the requirement rather than an implementation choice.

#### [PROSE_UNCLEAR] ADVISORY
- Location: `vs-adapter/pushdown-filter/spec.md` Background bullet 11; `vs-adapter/pushdown-aggregation/spec.md` Background bullet 19
- Issue: bullet 11 ends "One collation answers both of Exasol's questions for PostgreSQL where MySQL needs two, because `C` is byte equality as well as byte order", while the same bullet and the whole dialect design rest on the opposite arrangement — no collation on an equality operand, `COLLATE "C"` on an ordering one.
