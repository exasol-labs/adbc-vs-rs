## Premortem

Three ways this fails six months out.

1. **A driver TOML edit ships nothing.** `crates/adbc-vs-scan/build.rs` and `crates/adbc-vs-scan/drivers/*.toml` sit outside `SCAN_SRCS`, so `make cross-udf-build` is a no-op after a TOML edit and `make test-artifact`, `make test-e2e`, and `make bench` all certify the previous `.so`. The one edit the whole mechanism exists to make cheap is the one edit the build ignores. Routed to `[HIDDEN_DEPENDENCY]`.
2. **The build-time guarantee that justified codegen never lands.** Decision `[17]` chose `build.rs` over a run-time parse mainly to turn a bad table into a build failure. The capability half of that check validates against a `Capability` type the repo does not have, so an implementer either invents one — an unplanned refactor of `SqlDialect::capabilities`'s signature across both dialects and every capability test — or silently drops the check, leaving the guarantee asserted only in a spec. Routed to `[AMBIGUOUS_REQUIREMENT]`.
3. **The merged library contradicts itself on whether `BUCKETFS_CONNECTION` is required.** After `/speq:record`, `vs-adapter/create-virtual-schema` holds one scenario asserting its omission always errors and another asserting it is fine when `DRIVER_PATH` is set. The next planner reads whichever it finds first. Routed to `[REQUIREMENT_CONFLICT]`.

## Feasibility

#### [HIDDEN_DEPENDENCY] BLOCKER
- Location: `Makefile:36-54` (`SCAN_SRCS`, `WORKSPACE_MANIFESTS`, the `$(SO_FILE)` rule); plan.md tasks 3.1, 3.7, 6.4, 9.1; `crates/adbc-vs-adapter/tests/make_targets_test.rs`
- Issue: task 3.1 adds `crates/adbc-vs-scan/build.rs` and `crates/adbc-vs-scan/drivers/mysql.toml`; task 6.4 adds `drivers/postgresql.toml`. The `.so` rule's prerequisites are `ADAPTER_SRCS := $(shell find crates/adbc-vs-adapter/src -type f)`, `SCAN_SRCS := $(shell find crates/adbc-vs-scan/src -type f)`, and four manifest paths. `build.rs` sits at the crate root and `drivers/` sits beside it — **neither is under `src/` and neither is a manifest**, so no new file is a prerequisite. Editing a `version_range`, a capability list, or the build script itself leaves `make cross-udf-build` a no-op, and `make test-artifact`, `make test-e2e`, `make test-e2e-postgres`, and `make bench` then all assert against the previous `.so`. CLAUDE.md states the invariant this breaks: "touching a crate source forces a rebuild. No test ever runs against a stale binary." The existing guard does not catch it — `make_targets_test.rs`'s `touching_source_invalidates_so` touches `crates/adbc-vs-adapter/src/lib.rs` and asserts nothing about the contents of the prerequisite list. No task in Phases 1 to 10 edits the `$(SO_FILE)` rule; task 9.1 adds `test-e2e-postgres` and task 1.2 adds the stack targets, neither touching prerequisites. This is the single most damaging failure mode the TOML mechanism introduces, because it makes the data edit the mechanism exists to enable the one edit the build ignores.
- Fix: Add a task to plan.md § Phase 3, sequenced with task 3.1, that extends the `Makefile`'s `$(SO_FILE)` prerequisites to cover the new build inputs — add `crates/adbc-vs-scan/build.rs` and `$(shell find crates/adbc-vs-scan/drivers -type f)` (as a new `SCAN_BUILD_INPUTS` variable) to the rule's prerequisite list — and extends `crates/adbc-vs-adapter/tests/make_targets_test.rs` with a test asserting that touching `crates/adbc-vs-scan/drivers/mysql.toml` invalidates the `.so`, modelled on the existing `touching_source_invalidates_so`. State in the task that the assertion is the guard, not the Makefile edit. Add a matching bullet to task 9.3's CLAUDE.md list recording that `drivers/*.toml` and `build.rs` are `cross-udf-build` prerequisites.

## Requirement Quality

#### [AMBIGUOUS_REQUIREMENT] BLOCKER
- Location: plan.md task 3.7 ("a capability name in the TOML that no `Capability` variant matches MUST fail the build naming the unknown name"); `vs-adapter/driver-selection/spec.md:105-111` scenario "A malformed or incomplete driver TOML file fails the build" ("*GIVEN* a driver TOML file missing a required `[package]` field, or naming a capability no capability type defines")
- Issue: no capability type exists. `crates/adbc-vs-adapter/src/sql_dialect.rs:54` declares `fn capabilities(&self) -> &'static [&'static str]`, `mysql_dialect.rs:196` returns a `&[&str]` constant, and `capabilities.rs` serializes that slice straight into JSON. Capabilities are bare protocol strings — `pushdown-dialect/spec.md` Background bullet 25 says so explicitly ("Capability names follow `virtual-schema-common-java`'s serialized forms"). No task in Phases 1 to 10 creates a `Capability` enum. So the scenario's second GIVEN clause and task 3.7's last clause cannot be implemented as written, and the scenario cannot be turned into a pass/fail test today. The two ways out are both unplanned: introduce a `Capability` enum, which changes `SqlDialect::capabilities`'s signature, both dialect impls, `capabilities.rs`, every capability test, and needs a home the `adbc-vs-scan` build script can reach; or give the build script its own allowlist of valid names, which is the "second capability list" `pushdown-dialect/spec.md` Background bullet 9 forbids. The scenario also demands the failure occur "at build time rather than when a query resolves that driver", so the existing every-advertised-capability-renders invariant test does not satisfy it — that is a `cargo test`, not a build.
- Fix: Choose one and make it explicit in both places. Either (a) add a task to plan.md § Phase 3, before task 3.7, introducing `Capability` as a closed enum in `adbc-vs-adapter` with a `&'static str` serialized form, changing `SqlDialect::capabilities` to return `&'static [Capability]`, stating how the `adbc-vs-scan` build script reaches the variant list (see the Design Depth finding on the generated table's crate home), and updating `capabilities.rs` and both dialects' tests — then leave task 3.7 and the scenario as written; or (b) delete "or naming a capability no capability type defines" from `vs-adapter/driver-selection/spec.md`'s scenario and the matching clause from task 3.7, narrow the scenario to `[package]`-field validation only, and add a separate scenario stating that an unknown capability name is caught by the every-advertised-capability-renders invariant test rather than by the build.

## Design Depth

#### [INFORMATION_LEAKAGE] ADVISORY
- Location: plan.md task 3.7 ("generated by task 3.1's build script into the same `&'static` shape the trait method returns"); `vs-adapter/driver-selection/spec.md` Background bullet 9 ("Three tables are keyed on the identity, and they live in two crates because their consumers do")
- Issue: the plan places exactly one build script, in `adbc-vs-scan`, generating into that crate's `OUT_DIR` and `include!`d by `driver.rs`. `OUT_DIR` is per-crate and not reachable from `adbc-vs-adapter` without a `links` manifest key and a second build script, so the generated capability table must become part of `adbc-vs-scan`'s public API. Its only consumer is `adbc-vs-adapter`'s dialects — the scan UDF never reads a capability. That is a fourth table, living in the crate the build script happens to sit in rather than the crate its consumer sits in, which is the exact rule Background bullet 9 states the other three follow. No task says where the generated capability table lands or how the adapter's dialect reaches it, so the boundary is decided by accident at implementation time. This compounds the `Capability`-type blocker above: whichever crate owns the type must also be reachable from the build script that validates against it.
- Fix: State the crate home explicitly. Add to plan.md § Decision § Architecture and to task 3.7 that the generated capability tables live in `adbc-vs-scan` beside the package table, exposed as `pub fn capabilities(Driver) -> &'static [&'static str]`, and that each dialect's `SqlDialect::capabilities` returns that value — then amend `vs-adapter/driver-selection/spec.md` Background bullet 9 to say four tables, naming the capability list as the one whose crate follows the build script rather than its consumer, and state why that is acceptable.
