# Decision Log: add-postgresql-support

## Interview

This plan was first authored in headless mode. Four later live instructions then redirected it, so the log has five interview rounds: the original headless reading of the request, the six design decisions a human made afterwards, the human's answer to the one question round 2 escalated, a direct instruction to restructure the spec library itself, and the human's answer to the two organization questions that restructuring escalated. Decisions `[17]` to `[26]` carry rounds 2 to 5 and name the earlier decisions they supersede.

### Round 5: the human answers the library-organization escalation

Round 4's restructuring left two questions open, both stated in plan.md § Library organization after recording and in decision `[25]`'s closing consequence. A human answered both together, so decision `[26]` records them as one resolution.

**Q:** `driver-provisioning/driver-self-install` merges to 17 scenarios, the largest file in the library. Split it, accept it, or something else?

**A:** Split it into three features along framework-internal lines, never per technology: `driver-self-install` for the overall install flow, `driver-version-resolution` for range matching and fetching the newest version, and `driver-path-override` for the `DRIVER_PATH` air-gap mechanism.

**Q:** `vs-adapter` reaches 16 features against `/speq:spec-merge`'s guideline of 8, and the `driver-self-install` split does nothing for that count because it lives in a different domain. Accept 16, or revisit the rule forbidding a new top-level domain?

**A:** Accept 16 as the final, documented shape. The count is the intended result of separating framework from technology, not a regression. Record it in `CLAUDE.md` and in the decision log so no later planner "fixes" it by re-consolidating features.

### Round 4: direct instruction to separate framework specs from technology specs

A human read the plan in PR #1 and directed a structural change to the spec library, not to the product. It is recorded as an interview answer because it was given rather than assumed, and decision `[25]` implements it.

**Q:** How should the spec library be organized now that a second technology exists?

**A:** Separate specs by concern: framework and technology. One general area describes how the pushdown mechanism works in the abstract. A separate spec area per technology defines that technology's own pushdown capabilities, data-type mappings, and other technology-specific facts. Each technology must be free to define different capabilities or type mappings from any other **structurally**, not as scattered `DELTA` blocks inside shared files.

**Q:** May the split add a top-level domain, or nest directories under one?

**A:** Neither. The three live domains stay `vs-adapter/`, `scan-udf/`, and `driver-provisioning/`. Verify whether the tooling represents a third path level at all before designing around it, and if it does not, use flat prefixed feature names instead of inventing directory depth the tool cannot represent.

**Q:** Does the already-shipped MySQL-only spec content migrate, or stay where it is?

**A:** It migrates, on the same principle as the MySQL driver-package and capability-TOML migration decision `[19]` already settled: one mechanism from the first release that has two technologies. Work out the mechanical `DELTA` sequence that achieves it, and record whether the old feature files end up legitimately empty.

### Round 3: live interview resolving the escalated integrity question

Round 2 escalated one question and offered four options. A human answered both parts of that escalation, and decision `[22]` is now made rather than open.

**Q:** Which integrity model replaces the compiled-in SHA-256 digest — (A) OpenPGP signature verification pinned to a maintainer-confirmed key fingerprint, (B) TLS only, (C) TLS by default plus an optional operator-supplied checksum, or (D) keep pinned versions?

**A:** Option B, TLS only. Self-install trusts the download's TLS connection alone, the same trust boundary as every other HTTPS fetch the adapter already makes. No signature verification and no checksum verification of any kind, built in or operator supplied. Do not add the `pgp` crate, and do not build a `DRIVER_SHA256` property preemptively — manual or checksum verification can be added later as a separate enhancement, out of scope here.

**Q:** Is a weaker guarantee acceptable for MySQL specifically, whose provisioning is already released behavior at tag `v0.2.0`?

**A:** Yes. Apply it uniformly to both drivers, with no MySQL carve-out. Both move to version-range resolution with TLS-only integrity, as round 2 already decided for ranges.

### Round 2: live interview on the driver-data architecture

A human reviewed the plan in PR #1 and made six decisions. They are recorded here as answers because they were given rather than assumed, and they are not re-litigated below.

**Q:** Should per-driver data move out of Rust constants into configuration, and how much of it?
**A:** One TOML file per technology, checked into this repo and embedded into the `.so` at build time. Each file holds that technology's advertised capability list and its driver package row — registry package name, a version *range*, and a checksum policy. SQL rendering and type mapping stay Rust code. **Round 3 dropped the checksum policy from the row**, so no package row carries an integrity field — see decision `[22]`.

**Q:** Does this make adbc-vs pluggable at run time?
**A:** No. A third technology still needs a new adbc-vs release: a new enum variant, a new dialect and metadata source, and a new TOML file, shipped together. "Dynamic" means per-virtual-schema, which `adapterNotes.driver` already delivers. Build no run-time driver-loading mechanism.

**Q:** Does MySQL migrate onto the TOML mechanism, or does only PostgreSQL use it?
**A:** MySQL migrates in this same plan. Both drivers use one uniform mechanism from day one.

**Q:** How does an air-gapped cluster supply a driver?
**A:** A new `DRIVER_PATH` property on `CREATE VIRTUAL SCHEMA`. When present, the adapter skips the registry flow entirely and uses exactly that BucketFS path, for any driver technology.

**Q:** Does the TOML pin an exact driver version?
**A:** No. It states a version range, and self-install fetches the newest registry version satisfying it. The same cluster may get a different driver version on a later reinstall, with no adbc-vs release involved.

**Q:** What replaces the compiled-in SHA-256 digest, which cannot survive a version that is no longer fixed?
**A:** Research the registry's own integrity data and decide; do not invent an unverifiable substitute. Escalate if the registry publishes no per-version checksum. **It does not, so this was escalated and round 3 answered it: nothing replaces the digest — see decision `[22]`.**

### Round 1: the original headless request

No live interview took place for the first round. Every decision from `[1]` to `[16]` was assumed and documented rather than confirmed with a human, per the planning skill's headless rules. The request as received:

**Q:** What should this plan add?
**A:** "add support for PostgreSQL; make the feature push-down dynamic. Each technology (mysql, or postgresql) may advertise different features; pgsql shall also auto-download the driver; match feature scope of mysql (but optimize via tasks)"

**Q:** Which of those four clauses needed interpretation, and how was each read?
**A:** *Dynamic pushdown* was read as per-dialect capability advertisement resolved from the virtual schema's own driver, not as run-time capability probing of the source — `pushdown-dialect` already states that the dialect owns its set, so the gap was the resolution point rather than the ownership model. *Auto-download* was read as the existing `driver-self-install` mechanism generalized to a per-driver package table, not a second install path. *Match feature scope* was read as the same capability set, the same delegation tiers, and a comparably narrow mapped-type set, with divergence only where PostgreSQL's SQL or type system genuinely differs — and with each divergence documented rather than silently absorbed. *Optimize via tasks* was read as factoring the driver-identity refactor into one phase that four later workstreams build on concurrently, rather than duplicating it per driver.

**Q:** Was anything escalated?
**A:** No. Two decisions came close to the escalation bar — the PostgreSQL credential path, which narrows a stated security invariant, and exposing only the `public` schema — and both are recorded below with their alternatives. Neither is irreversible: the credential form is forced by the driver's API rather than chosen between competing designs, and a schema property can be added later with `public` as its default. Three decisions the plan could not resolve from documentation are deferred to measurement gates rather than to a human, which is what the repo's existing plans do with the same class of unknown.

## Design Decisions

### [1] A closed driver-identity enum owns every per-driver fact

> **Amended by decisions `[17]`, `[21]`, and `[22]`.** The enum, the three tables, and the exhaustive-`match` reasoning all stand. What changed is where the package row's values are written and what they contain: they come from a per-technology TOML file generated at build time rather than from hand-written Rust constants, and the row carries a version range instead of a pinned version, with no digest field at all.

- **Decision:** Introduce `Driver` as a closed enum in `adbc-vs-scan::driver`, with three tables keyed on it: the driver package (version range, library filename, registry path, ADBC entry-point symbol) in the same crate, and the dialect and the metadata source in `adbc-vs-adapter`. No call site branches on a driver name.
- **Alternatives:** Thread a driver string through the six modules that currently hold single-driver constants — rejected, because nothing would fail when a seventh place needed updating. Bundle all per-driver behavior behind one trait object — rejected, because the package data is read by `adbc-vs-scan`, which cannot depend on the adapter crate where the dialect lives, so one bundle would invert the crate dependency.
- **Rationale:** A Rust `match` over a closed enum is exhaustive, so adding a driver fails the build at every table missing a row. That converts "a second driver adds an implementation rather than editing a renderer" from a convention `pushdown-dialect` asserts into something the compiler enforces. It also gives "which drivers exist" exactly one owner, where release 0.2 restated it in `create_schema`, `provisioning`, `connection`, `driver`, and `dispatch`.
- **Promotes to ADR:** yes

### [2] Both getCapabilities and pushdown resolve the dialect from adapterNotes.driver

- **Decision:** Resolve the driver identity from `schemaMetadataInfo.adapterNotes` in both dispatch arms, and error when the field is absent rather than defaulting to a driver.
- **Alternatives:** Read `schemaMetadataInfo.properties.DRIVER` instead — kept as the fallback if gate 2.1 finds `adapterNotes` absent from `getCapabilities`, but not the first choice. Default to MySQL when the field is missing — rejected outright: advertising one dialect's set for another's source returns wrong rows for every capability the two do not share, which is the exact failure `pushdown-dialect` exists to prevent.
- **Rationale:** `pushdown` already reads `adapterNotes`, and its `driver` field is already written by `createVirtualSchema` and never read. Using one field for both answers preserves the property `dispatch`'s module doc claims for release 0.2 — that the advertised set and the renderer can never disagree — while letting the answer differ per virtual schema. Two fields could drift; one cannot.
- **Promotes to ADR:** yes

### [3] Each dialect states its own capability set, and the invariant test enumerates dialects from the type

- **Decision:** Keep `SqlDialect::capabilities` as a per-implementation hand-stated list, and generalize the invariant test that renders every advertised capability to run once per `Driver` variant, enumerated from the type rather than from a list in the test. Add a test asserting the two sets differ in exactly `JOIN_TYPE_FULL_OUTER`.
- **Alternatives:** Derive one release-wide set as the intersection of what both dialects render — rejected, because it makes one target's limitation govern the other's delegation and would discard PostgreSQL's full outer join. Derive each set from the other by addition or removal — rejected for the same reason in weaker form: a derived set makes one dialect's withholding silently govern the other's.
- **Rationale:** ADR 002 already established that a hand-stated set plus a required invariant test is what pins the advertised set to the renderer, because nothing in the type system can fail a build when a rendering path is removed. That reasoning is per dialect, so the test becomes per dialect. Enumerating variants from the type means a third dialect inherits the invariant without anyone editing the test.
- **Promotes to ADR:** yes

### [4] PostgreSQL renders a collation only where order decides the answer

- **Decision:** The PostgreSQL dialect renders `COLLATE "C"` on a character operand of `predicate_less`, `predicate_lessequal`, `predicate_between`, `MIN`, and `MAX`, and renders no collation on an equality operand, a `LIKE` operand, an `IN` operand, a `GROUP BY` key, a bare select-list occurrence of a grouped column, a `DISTINCT` operand, or a join key.
- **Alternatives:** Mirror MySQL's structure and collate every character operand uniformly — rejected on two counts: it would cost the source's index support on every equality predicate for no correctness gain, and collating the `GROUP BY` key would recreate MySQL's coordinated two-clause rule and, with it, the composed shape MySQL must reject outright. Render no collation anywhere — rejected: the official `postgres` image creates its cluster with `LC_COLLATE=en_US.utf8`, so an uncollated `MIN` over `B`, `a`, `C` returns `a` where Exasol returns `B`.
- **Rationale:** Exasol asks two questions of a character value, and MySQL's default answers both differently while PostgreSQL's default answers only one differently. A deterministic collation — which is every collation PostgreSQL ships — equates two values just when their bytes are identical, which is Exasol's equality exactly; `C` sorts by byte value, which for UTF-8 is code-point order. Rendering where the target actually diverges, rather than uniformly, is what removes a whole rule and an exclusion from the PostgreSQL dialect rather than translating them.
- **Promotes to ADR:** yes

### [5] A PostgreSQL character column of a nondeterministic collation is unmapped

- **Decision:** Unmap a PostgreSQL character column whose declared collation is nondeterministic, with the reason naming the collation. Treat a server reporting no determinism flag as deterministic.
- **Alternatives:** Document the hazard and map the column anyway — rejected: a nondeterministic collation equates values Exasol keeps apart, which is a silent wrong-rows failure, and it makes `LIKE` fail outright. Render `COLLATE "C"` on every character operand to immunize against it — rejected as decision `[4]` records, because the cost lands on every equality predicate and reintroduces the grouping-collation exclusion.
- **Rationale:** Decision `[4]` relies on PostgreSQL's equality being byte equality, and one kind of collation breaks that reliance. Refusing the column is the same answer `type-mapping` already gives a MySQL character column of the wrong character set: a character column whose comparison cannot be delegated correctly is omitted rather than exposed. Because every shipped PostgreSQL collation is deterministic, the rejection reaches only a collation an operator created.
- **Promotes to ADR:** no

### [6] PostgreSQL credentials travel inside the driver's single connection option

- **Decision:** Build a libpq keyword/value connection string in memory at connect time from the freshly resolved `CONNECTION` object — host, port, and `dbname` from the address, every address query parameter carried across as a keyword of the same name, `user` and `password` from the object, every value single-quoted with an embedded quote or backslash escaped — and pass it as the driver's only accepted database option. Pass no `username` or `password` option for this driver. Strip the resolved password from every surfaced error, including text the driver or libpq produced.
- **Alternatives:** Keep the separate `username` and `password` ADBC options — impossible: the driver's `SetOption` accepts exactly `uri` and rejects the others as unknown options. Inject the credential into the `postgresql://` URI — rejected, because URI form needs percent-encoding and a password containing `&`, `#`, `@`, or `/` changes the parse rather than the value, where conninfo escaping is total. Pass the credential through libpq's environment variables — rejected: untested inside a UDF sandbox, process-visible, and `set_var` is `unsafe` in edition 2024.
- **Rationale:** This is the plan's one deliberate narrowing of a security property, and it is forced by the driver's API rather than chosen between designs. `arrow-scan`'s invariant that no credential passes through a connection string cannot hold for a driver that accepts nothing else. Every invariant about persistence and disclosure does still hold and is now asserted rather than assumed: nothing reaches the scan specification, `adapterNotes`, SQL text, `EXPLAIN VIRTUAL` output, or any log line, and the redaction is applied by the scan rather than relied on from the driver, because libpq's diagnostics can echo connection parameters. The narrowing is stated in the plan's Impact section so an operator reads it, together with the reason a PostgreSQL `CONNECTION` deserves a least-privilege read-only role.
- **Promotes to ADR:** yes

### [7] PostgreSQL string literals are escape-string constants

- **Decision:** Render every PostgreSQL string literal as `E'<body>'`, escaping a backslash as two backslashes and a single quote as two single quotes, unconditionally rather than only for a value that needs it.
- **Alternatives:** Render a bare `'...'` literal and add a `standard_conforming_strings` precondition check at `CREATE VIRTUAL SCHEMA` — rejected, because the setting is a GUC that can change per role after creation, so a creation-time check does not bind at query time. Mirror MySQL's hex form as `convert_from(decode('<hex>','hex'),'UTF8')` — rejected on typing: that expression is typed `text`, and PostgreSQL applies no implicit coercion from `text` to a numeric or temporal column, so every non-character comparison would fail with an unknown-operator error. Choose the form per value, using bare quotes when the value holds no backslash — rejected, because it would let a literal change the shape of the generated statement, which the MySQL dialect deliberately paid a hex encoding to avoid.
- **Rationale:** The `E` prefix selects backslash-escape processing whatever `standard_conforming_strings` holds, and doubling the quote rather than backslash-escaping it also removes the dependency on `backslash_quote`. So one form is independent of both settings with no server check, and it yields an untyped literal PostgreSQL resolves from the other operand, which is what every numeric and temporal comparison needs.
- **Promotes to ADR:** no

### [8] PostgreSQL exposes the public schema only, with no new property

> **Partly superseded by decision `[20]`.** The `public`-schema-only boundary stands and `SCHEMA_NAME` is still not added. The blanket "no fourth property is added" clause does not: `DRIVER_PATH` is added, for the reasons `[20]` records. This is a deliberate revision made in the round-2 interview, not a contradiction left in place.

- **Decision:** A PostgreSQL virtual schema exposes the `public` schema of the addressed database. `adapterNotes` records `public` as the source namespace, which is both the SQL qualifier and the `information_schema` filter value. No fourth `CREATE VIRTUAL SCHEMA` property is added.
- **Alternatives:** Add a `SCHEMA_NAME` property — rejected for now: a property is a decision the adapter declined to make, and one added now becomes a supported input a later release cannot narrow. Auto-detect from the connection's `search_path` — rejected, because the exposed table set would then depend on invisible server state that the persisted metadata cannot track, so a role change would silently invalidate a created virtual schema.
- **Rationale:** MySQL's namespace comes from the address's path component because a MySQL database *is* its SQL qualifier; PostgreSQL's path component names a database, which is not a qualifier, so a namespace has to come from somewhere else. A virtual schema per source schema needs no new property, and adding `SCHEMA_NAME` later with `public` as its default stays compatible with everything created before it. The boundary is stated in the spec as this release's scope rather than left as an omission.
- **Promotes to ADR:** no

### [9] PostgreSQL boolean, character(n), text, and unconstrained numeric are unmapped

- **Decision:** Map seven PostgreSQL types — `integer`, `bigint`, `numeric(p,s)`, `character varying(n)`, `date`, `timestamp without time zone`, `double precision` — and leave every other type unmapped with a recorded reason.
- **Alternatives:** Map `boolean` to Exasol `BOOLEAN` — rejected: it would make `BOOLEAN` a type a source column produces, widening the mapped set that `pushdown-dialect`'s closure argument is built on, bringing a boolean operand into every predicate path, and requiring `LITERAL_BOOL`, which neither dialect advertises. Map `character(n)` to Exasol `VARCHAR` — rejected: PostgreSQL returns the value blank-padded and compares two of them ignoring trailing spaces, so `VARCHAR` matches neither the value nor the comparison and a delegated predicate would return wrong rows. Map `character(n)` to Exasol `CHAR`, which does match both — rejected as out of scope: four features state the invariant that every delegated character operand is Exasol `VARCHAR`, and reopening it is a larger change than this plan buys. Map `text` and unconstrained `numeric` by substituting a maximum size or precision — rejected, because Exasol compares a declared type for exact equality and a source value need not fit an invented bound.
- **Rationale:** The request asked to match MySQL's scope, and MySQL maps eight deliberately narrow types while omitting `TEXT`, `TINYINT`, `FLOAT`, `TIME`, and `JSON`. The PostgreSQL set is chosen to be the same shape rather than to exhaust PostgreSQL's type system, so the produced Exasol type set stays the same five for the release and no closure argument in `pushdown-dialect` has to be re-derived. `character(n)` is the one place the two scopes genuinely diverge, and the padding direction is why. The `character(n)` omission is bounded by adbc-vs's own invariant that every delegated character operand is Exasol `VARCHAR`, not by anything PostgreSQL cannot express: Exasol `CHAR` does match `character(n)`'s value and its comparison. Lifting it needs its own plan revisiting that invariant everywhere it is stated, and adding the mapping here without that plan would leave the others contradicting whichever one changed. After decision `[25]`'s restructuring that is **six** features, not four: the framework `vs-adapter/type-mapping`, `vs-adapter/pushdown-filter`, `vs-adapter/pushdown-aggregation`, and `vs-adapter/pushdown-join` each state it for every dialect, and `vs-adapter/mysql-type-mapping` and `vs-adapter/postgresql-type-mapping` each state their own consequence of it — MySQL `CHAR` mapping to Exasol `VARCHAR` because MySQL's `CHAR` comparison is unpadded, and PostgreSQL `character(n)` staying unmapped because its comparison is padded. A future planner should read all six rather than the four this entry originally named.
- **Promotes to ADR:** no

### [10] SUM and AVG stay withheld for PostgreSQL, despite its exact-numeric sum being exact

- **Decision:** Withhold `FN_AGG_SUM`, `FN_AGG_SUM_DISTINCT`, `FN_AGG_AVG`, and `FN_AGG_AVG_DISTINCT` from the PostgreSQL dialect as well as the MySQL one.
- **Alternatives:** Advertise `FN_AGG_SUM` for PostgreSQL and refuse a floating-point operand at render time — rejected. Advertise it and accept the divergence on `double precision` — rejected outright, since it returns a wrong number silently.
- **Rationale:** PostgreSQL's `sum` over `integer` returns `bigint` and over `numeric` returns `numeric`, both exact and order-independent, so a capability admitting only exact-numeric operands would be sound. None exists: a capability is advertised once per session and `FN_AGG_SUM` admits every numeric operand. PostgreSQL's `sum` over `double precision` is order-dependent because floating-point addition is not associative, and a parallel plan may combine partial aggregates differently between two runs of one query, so it is less stable than MySQL's measured left-to-right accumulation rather than more. ADR 002 settled that a capability which cannot be rendered safely for every operand type it admits is withheld whole rather than refused narrowly, because Exasol does not compute a delegated fragment itself after the adapter errors. Applying that existing principle, rather than reopening it, is the whole decision here.
- **Promotes to ADR:** no

### [11] JOIN_TYPE_FULL_OUTER is advertised by PostgreSQL only, gated on measurement

- **Decision:** The PostgreSQL dialect advertises `JOIN_TYPE_FULL_OUTER` and renders `FULL OUTER JOIN`; the MySQL dialect withholds it. Advertising is conditional on gate 2.3(a) measuring that PostgreSQL accepts a full join whose condition is an equality.
- **Alternatives:** Withhold it from both, keeping the two sets identical — rejected: it is the one capability the two targets genuinely disagree on, so it is what makes the per-dialect set observable rather than merely architectural, and it is a real delegation an operator gets. Advertise it without measuring — rejected: PostgreSQL restricts a full join to conditions that are merge- or hash-joinable, and an advertised capability the source refuses converts a query Exasol would have answered into a hard failure.
- **Rationale:** `pushdown-join`'s existing reason for withholding the capability is MySQL's lack of the feature, not a scope exclusion — mission.md scopes pushdown to equi and outer joins, and a full outer join is an outer join. So advertising it for a target that implements it follows the existing decision rather than revising it. An equality over one common type is both merge- and hash-joinable, which is why the restriction is expected not to bind; the gate is there because "expected" is not this repo's standard for a capability whose failure mode is a hard error. If the gate measures a rejection, the capability is withheld, the sets coincide in this release, and the plan says so rather than the architecture being wrong.
- **Promotes to ADR:** no

### [12] Type mapping moves behind MetadataSource rather than behind its own trait

- **Decision:** `MetadataSource::discover_tables` returns columns already mapped to `MappedType` with omissions recorded, so each driver's metadata source owns both its catalog SQL and its type mapping, and `create_schema` branches on no driver. The same trait carries each dialect's source precondition check.
- **Alternatives:** Add a separate `TypeMapper` trait keyed on `Driver` — rejected, because it needs a common source-column struct, and MySQL needs the unsigned flag and the column character set while PostgreSQL needs `udt_name` and the collation's determinism; a shared row would lose whichever fields one source has and the other does not, leaking each source's gaps into the caller. Keep the mapping in `create_schema` with a driver match — rejected, because it puts driver knowledge back in the module the identity was introduced to keep driver-neutral.
- **Rationale:** The reason to change a mapping and the reason to change a catalog query are the same reason: the source's own catalog and type system. Grouping by that, rather than by the technical role of "querying" versus "mapping", is what makes each driver's module deep enough that `create_schema` needs to know nothing. The precondition check joins the same trait because the requirement is stated by the dialect that renders it and executed by the module that speaks the source's SQL — which is the rule `create-virtual-schema` already states for MySQL's collations.
- **Promotes to ADR:** no

### [13] Pinned driver version strings are stored per driver, never derived

> **Superseded by decision `[21]`.** Versions are no longer pinned or matched by string equality; each driver's TOML states a range and self-install resolves the highest published version satisfying it. The hazard this entry identified is real and was correctly identified — the index does spell MySQL's version `v0.6.0` and PostgreSQL's `1.12.0` — but semantic comparison dissolves it rather than storing around it. Kept for the record; do not implement it. This is a deliberate revision made in the round-2 interview.

- **Decision:** Store each driver's pinned version string exactly as the registry index spells it — `v0.6.0` for MySQL and `1.12.0` for PostgreSQL — as a field of that driver's package row, and assert both resolve against the real index.
- **Alternatives:** Store a bare semantic version and add or strip a leading `v` when building the lookup — rejected: the index's spellings are not uniform across drivers, and the lookup matches the `version` scalar by exact string equality, so any single normalization rule fails for one of the two published versions.
- **Rationale:** This is a small decision worth recording because it is invisible until it fails, and it fails as a "version not published" error that reads like a registry problem rather than a formatting one. The relative package URL inside a matched block carries its own version segment and is read from the index rather than constructed, so nothing else depends on the spelling.
- **Promotes to ADR:** no

### [14] The PostgreSQL test container keeps its default locale

- **Decision:** Run `postgres:18.6-trixie` with the image's default `LANG=en_US.utf8` and set no `POSTGRES_INITDB_ARGS`, so the cluster is created with locale collation rather than code-point collation.
- **Alternatives:** Force `--locale-provider=builtin --builtin-locale=C.UTF-8` at initdb so the cluster sorts by code point — rejected, because the tests would then pass with the `COLLATE "C"` suffix missing from `MIN` and `MAX`, which is precisely the divergence the suffix exists to fix.
- **Rationale:** A test container configured to agree with Exasol cannot catch a dialect that fails to make the source agree with Exasol. The locale default is also the configuration a production cluster is likelier to have, so the fixture is honest as well as sensitive.
- **Promotes to ADR:** no

### [15] Three unknowns are deferred to measurement gates rather than assumed

- **Decision:** Gate 2.1 measures whether `getCapabilities` carries `schemaMetadataInfo.adapterNotes`; gates 2.2a and 2.2b measure whether the C++ PostgreSQL driver loads inside the UDF sandbox; gate 2.3 measures eight PostgreSQL semantic assumptions including the full-join condition restriction and the absence of a grouped-select-list rejection. Each gate precedes the tasks whose design it decides, and a contradicting result re-plans the affected spec bullets and scenarios before the rendering work starts.
- **Alternatives:** Assume each from documentation and correct during implementation — rejected: two of the three change the plan's architecture rather than an implementation detail. If the driver identity does not reach `getCapabilities`, per-dialect capability sets are illegal and the plan's central claim collapses to an intersection. If the driver does not load in the sandbox, the fix lands in `language-container-rs` and returns through the release chain, so the plan is blocked on another repo. Escalate all three to a human — rejected: none is a decision needing judgment, each is a fact needing a container.
- **Rationale:** Gating an unknown that decides an architecture is the pattern this repo's earlier plans used for exactly this class of question, and the gates that mattered most there were the ones that falsified a documented expectation. The driver-load gate is ordered first because it is the highest-consequence unknown and the most expensive one to discover late: a failure is fixed in `language-container-rs` and returns through the release chain. It is not cheap, and the plan says so rather than implying it: gate 2.2a needs HTTPS egress and a BucketFS upload, and gate 2.2b needs `make cross-udf-build`, `make stack-up`, the installed SLC, and a throwaway raw driver-load entry point. What it does not need is the dialect, the refactor, or a PostgreSQL container, which is why it can run before any of them.
- **Promotes to ADR:** no

### [16] Spec deltas keep each behavior with the feature that owns it, never per technology

> **Superseded by decision `[25]`.** The library is now split into framework features and per-technology features, which is what this entry rejected. One half stands: `vs-adapter/driver-selection` exists as its own feature, for the reason given below. The other half does not — PostgreSQL's rendering rules no longer live in `pushdown-filter` beside MySQL's. `[25]` answers this entry's objection rather than overruling it: `pushdown-filter` still owns what a filter fragment *is*, and stops also owning MySQL's hex literals. Kept for the record; do not implement it. This is a deliberate revision made on a direct instruction in round 4.

- **Decision:** Add PostgreSQL scenarios to the existing `pushdown-*`, `type-mapping`, `create-virtual-schema`, `driver-self-install`, and `arrow-scan` features, and add exactly one new feature, `vs-adapter/driver-selection`, for the driver identity itself.
- **Alternatives:** Create a `postgres/` spec group or a `vs-adapter/postgres-dialect` feature holding PostgreSQL's rendering rules — rejected, because it organizes specs by technology rather than by behavior, so `pushdown-filter` would stop owning filter delegation. Parameterize the existing MySQL scenarios by dialect — rejected, because those scenarios carry measured MySQL specifics (collation names, backtick escaping, hex literals) that parameterizing would erase.
- **Rationale:** The repo's own spec governance already settled the analogous question for end-to-end tests: behavior verified through a live stack belongs to the feature that owns the behavior, never to a group organized by test file. The same logic makes PostgreSQL's filter rendering a scenario in `pushdown-filter`. `driver-selection` is a new feature rather than scenarios spread across three existing ones because "which drivers exist and how one is selected" is a single coherent responsibility that would otherwise leak into `create-virtual-schema`, `pushdown-dialect`, and `driver-self-install` at once — the information-leakage smell the identity exists to remove.
- **Promotes to ADR:** no

### [17] Per-technology TOML files hold the capability list and the driver package row

- **Decision:** Add one TOML file per technology — `crates/adbc-vs-scan/drivers/mysql.toml` and `drivers/postgresql.toml` — checked into this repo. Each holds that technology's advertised capability list and its driver package row: registry path, library filename, ADBC entry-point symbol, and a version range. A `build.rs` in `adbc-vs-scan` reads them at build time and generates the Rust tables `Driver::package()` and the dialect capability lists return, so the data is compiled into the `.so` rather than read at UDF run time. Amends decision `[1]`, which put the same facts in hand-written Rust constants.
- **Alternatives:** Parse the embedded TOML at run time with `include_str!` plus `LazyLock` — rejected on three counts. It adds `serde` and `toml` to `adbc-vs-scan`, which today has neither and is the crate linked into every UDF sandbox; it turns a malformed table from a build failure into a query-time panic; and it breaks every `&'static DriverPackage` signature, because a lazily parsed value is not `'static` without leaking. Read the TOML from BucketFS at run time — rejected outright, and by the interview: Rust code is required per technology anyway, so nothing is gained by making the data late-bound, and everything about compile-time exhaustiveness is lost. Keep the constants in Rust and assert in a test that they match the TOML — rejected, because it keeps the duplication the TOML exists to remove.
- **Rationale:** The values are what change per technology; the code that consumes them does not. Moving the values to data makes adding a technology an edit to one file whose shape the build checks, and generating Rust from it at build time keeps every property decision `[1]` bought — exhaustive `match`, `&'static` tables, zero run-time parse cost inside the sandbox. The TOML is a source format, not a run-time resource, which is the reading that satisfies the interview's "embedded, not read at runtime" constraint at the lowest cost.
- **Promotes to ADR:** yes

### [18] Adding a technology stays a release-time change; the Driver enum stays closed

- **Decision:** A third technology requires a new adbc-vs release carrying a new `Driver` variant, a new `SqlDialect` and `MetadataSource` implementation, and a new TOML file. Add no run-time driver-registration, plugin, or discovery mechanism. "Dynamic" means per virtual schema, which `adapterNotes.driver` already delivers.
- **Alternatives:** Discover technologies by scanning a directory of TOML files at run time — rejected. It cannot work: a technology needs a dialect and a metadata source, which are Rust code, so a TOML file naming an unknown technology could only fail. Building the mechanism would trade the compiler's exhaustiveness for a run-time error that says the same thing later.
- **Rationale:** This is recorded because the TOML files make run-time pluggability look available, and it is not. The data moved to TOML is exactly the data that has no code behind it; every technology-specific behavior stays code. Stating the boundary keeps a later reader from adding a loader that could never load anything.
- **Promotes to ADR:** yes

### [19] MySQL migrates onto the TOML mechanism in this plan

- **Decision:** Move MySQL's capability list and package facts into `drivers/mysql.toml` in this plan, so both drivers read one mechanism from the first release that has two.
- **Alternatives:** Leave MySQL on hand-written Rust constants and give only PostgreSQL a TOML file — rejected. Two mechanisms for one kind of fact is the scattering decision `[1]` exists to end, and it would leave the next technology's author guessing which one to copy.
- **Rationale:** The migration is mechanical and its correctness is checkable: MySQL's generated capability set and package row must be byte-identical to today's constants, which the existing tests already assert. Doing it now costs one task and removes the fork permanently.

### [20] DRIVER_PATH names an operator-supplied driver and skips self-install

- **Decision:** Add a fourth `CREATE VIRTUAL SCHEMA` property, `DRIVER_PATH`, optional, applying to every driver technology. When present, the adapter uses exactly that BucketFS path and performs no registry index read, no download, no digest check, and no BucketFS write. When the named path holds no readable file, the request MUST fail with an error naming the property, the path, and the driver — never falling back to the registry, because a silent fallback would defeat the air-gap the property exists to serve. The property is recorded in `adapterNotes` and is therefore supplied once at `CREATE`; `refresh` and `setProperties` reuse the recorded value unless `setProperties` changes it. `BUCKETFS_CONNECTION` becomes optional when `DRIVER_PATH` is present, since its only purpose is the write credential self-install needs. **Supersedes decision `[8]`'s clause that no fourth property is added**, and supersedes the "place the library at a fixed compiled-in path" language in `driver-provisioning/driver-self-install`.
- **Alternatives:** Keep the existing informal fallback, where an unreachable registry names a fixed compiled-in path an operator must have pre-loaded — rejected. It is not a supported input: the path is not the operator's to choose, it is only discoverable by reading an error message, and under decision `[21]`'s versioned install path it would no longer be a single fixed location. Make `DRIVER_PATH` a compiled-in override rather than a property — rejected, because the whole point is that an operator chooses it per virtual schema without a rebuild. Fall back to the registry when the path is missing — rejected as stated above.
- **Rationale:** Decision `[8]` refused a fourth property on the general ground that a property is a decision the adapter declined to make. That reasoning holds for `SCHEMA_NAME`, where the adapter can derive a good answer, and fails here, where the adapter cannot: only the operator knows where an air-gapped cluster's driver was placed. The old fallback already conceded that an operator must be able to supply the file, and it did so through an error message rather than an interface. Making it a property turns an undocumented convention into a stated one, and decision `[21]` makes it necessary rather than merely tidy, because the compiled-in path it replaced is no longer fixed.
- **Promotes to ADR:** yes

### [21] The driver version is a range resolved against the registry, not a pinned string

- **Decision:** Each driver's TOML states a `version_range` in `semver` `VersionReq` syntax — `>=0.6.0, <0.7.0` for MySQL and `>=1.12.0, <2.0.0` for PostgreSQL. Self-install reads the index, parses every published `version` scalar for that driver, and selects the **highest** version satisfying the range, then reads that block's `linux_amd64` `url`. Parsing normalizes one optional leading `v`, because the index spells MySQL's versions `v0.6.0` and PostgreSQL's `1.12.0`. Resolution needs `semver` as a direct dependency of `adbc-vs-adapter`; it is already in `Cargo.lock` transitively and is `MIT OR Apache-2.0`, so `deny.toml`'s allow list and `about.toml` are unchanged. **Supersedes decision `[13]`**, which stored one exact spelling per driver and matched it by string equality.
- **Alternatives:** Keep one pinned exact version per driver — rejected by the interview. Pin a version and allow an operator to override it with a property — rejected: it re-pins the common case and adds a property that duplicates `version_range`'s purpose.
- **Rationale:** Two consequences are worth recording because neither is obvious. First, the exact-spelling trap decision `[13]` guarded against **dissolves**: matching is now semantic, so `v0.6.0` and `1.12.0` both parse to the same comparable value and no shared normalization rule can fail. The raw scalar still matters, but only to read the matched block's `url`, which is read rather than constructed. Second, the ranges are deliberately not derivable from one rule: MySQL sits below 1.0, where a minor bump is breaking by SemVer convention, so its range stops at `<0.7.0`; PostgreSQL is at 1.x, so its range admits minor bumps up to `<2.0.0`. A shared caret rule would be wrong for one of them, which is itself an argument for the range being per-technology data.
- **Promotes to ADR:** yes

### [22] TLS is the only integrity guarantee for a self-installed driver package

- **Decision:** Self-install verifies **no checksum and no signature** of a downloaded driver package. The download's TLS connection is the sole integrity guarantee, which is the trust boundary every other HTTPS fetch this adapter makes already relies on. The compiled-in SHA-256 digest is removed rather than replaced, the TOML package row carries no `integrity` field, and no operator-supplied digest property is added. This applies **uniformly to both drivers**, MySQL included, with no carve-out for the provisioning released at tag `v0.2.0`. Decided by a human in round 3, answering the escalation this entry previously carried. **Amends decision `[1]`**, whose package row still held a digest beside the version.
- **What is measured, not assumed:** The registry index at `https://dbc-cdn.columnar.tech/index.yaml` publishes **no checksum of any kind**. Its complete key set is `drivers`, `name`, `description`, `license`, `path`, `urls`, `docs_url`, `pkginfo`, `packages`, `platform`, `url`, `version`; a package block carries exactly `platform` and `url`. Probes for sidecar `.sha256`, `.sha512`, `.asc`, `.sig`, and `.intoto.jsonl` objects beside a package, and for `SHA256SUMS`, `checksums.txt`, and published key files at the CDN root, all return HTTP 403. So "verify against the registry's own published checksum" is not available, which is what made a decision necessary rather than a lookup.
- **Alternatives, all rejected by the human in round 3:**
  - *Pin the registry's signing key and verify each package's embedded OpenPGP signature.* Every package embeds a detached signature over the driver library, named by the archive's `MANIFEST` `[Files] signature` key, and both the MySQL and the PostgreSQL packages are signed by **one** Ed25519 key, fingerprint `AB7766E9B341299EBC7F45DD82ABD0A33A3C9E48` (key id `82ABD0A33A3C9E48`, signature algorithm 22, digest algorithm 10) — a registry-level key rather than a per-publisher one. Rejected on **key provenance, not tooling**: that key's public half was not found on `keys.openpgp.org` or `keyserver.ubuntu.com` by fingerprint, is absent from the ASF Arrow `KEYS` file, and has no `.well-known/openpgpkey` on `columnar.tech`. A key obtainable only from the CDN that serves the artifact adds ceremony without adding trust independent of that CDN. No `pgp` crate is added; recorded only so a later reader knows the license question was checked, `pgp` (rPGP) is `MIT OR Apache-2.0` and admissible under this repo's policy while `sequoia-openpgp` is `LGPL-2.0-or-later` and is not.
  - *TLS by default plus an optional operator-supplied expected digest (a `DRIVER_SHA256` property).* Rejected as premature. It is a real middle ground, not a bad one, but it adds a property, an error path, and a documented contract for a use case nobody has asked for yet, and a property added now cannot be narrowed later. Build it when an operator needs it.
  - *Keep pinned exact versions so the compiled-in digest survives.* Rejected in round 2 by decision `[21]`; re-raising it here would undo the range the interview asked for.
- **Named future work, not a forgotten gap:** adding checksum or signature verification is an intentional deferral, to be planned as its own change. Two things would unblock the strongest form: the registry publishing per-version checksums in the index, or the signing key's public half becoming obtainable independently of the CDN. A future planner revisiting this should read the measurements above rather than re-deriving them, and should treat the optional-digest property as the cheap incremental step and signature verification as the one gated on key provenance.
- **Rationale:** The registry offers nothing to verify against, and the one anchor that exists is anchored in the same host it would be protecting. Between two honest positions — a stated TLS-only boundary and a ceremony that reads stronger than it is — the human chose the stated one, and the plan states it plainly in § Impact and § Migration rather than letting silence imply the released digest guarantee survived. Uniformity with MySQL follows the same logic: two integrity models for one mechanism would be the scattering decision `[1]` exists to end, and it would leave the guarantee depending on which driver a virtual schema happens to name. An operator who needs a fixed, vouched-for artifact has `DRIVER_PATH` (decision `[20]`), which is a stronger guarantee than any of the rejected options, because the operator chooses the file.
- **Promotes to ADR:** yes

### [23] The BucketFS install path gains driver and version segments

- **Decision:** Change the installed driver's BucketFS path from `<mount>/adbc-drivers/<library>` to `<mount>/adbc-drivers/<driver>/<version>/<library>`, where `<version>` is the version resolution selected. The presence check therefore short-circuits only when the **resolved** version is already installed.
- **Alternatives:** Keep the unversioned path — rejected, because it silently defeats decision `[21]`. `driver_install_path` today is `mount.join(DRIVER_DIRECTORY).join(DRIVER_LIBRARY)` and `ensure_driver` returns early on `install_path.is_file()` before any network call, so a cluster that installed one version in range would keep answering its own presence check and never fetch a newer one. "Always fetch the newest in range" would in practice mean "fetch the newest in range once, ever". Overwrite the same path whenever the resolved version differs — rejected: a running query may have the old library mapped, and overwriting a shared object under it is not safe.
- **Rationale:** This is the load-bearing consequence of decision `[21]` and it is invisible until someone asks why a cluster never picked up a new driver. Versioning the path also makes the two drivers' co-existence assertion stronger than filename distinctness alone, and it makes an old version's continued presence harmless rather than authoritative. The cost is stated rather than hidden: the presence check can no longer run before the index is read, so `createVirtualSchema` and `refresh` now reach the registry on every call unless `DRIVER_PATH` is set, where release 0.2 could answer entirely from the mount. `DRIVER_PATH` is the supported way to keep the network out of the path, which is what makes decisions `[20]` and `[21]` fit together.
- **Promotes to ADR:** yes

### [24] adapterNotes records the resolved driver version rather than a pinned one

- **Decision:** `adapterNotes.driverVersion` records the version resolution actually selected and installed, and `adapterNotes.driverPath` records the versioned path decision `[23]` computes. A virtual schema created before this release carries an unversioned path and a pinned version, and both still parse.
- **Alternatives:** Stop recording the version — rejected: under a range it is the only record of what a given virtual schema is actually running, which is precisely when it becomes worth recording.
- **Rationale:** Release 0.2 recorded a value that could be read off the source. Under a range it cannot, so the note changes from a convenience to the answer to "which driver version is this virtual schema using", which an operator diagnosing a source-specific failure needs.
- **Promotes to ADR:** no

### [25] The spec library separates framework from technology, as flat prefixed features inside the existing domains

> **Supersedes decision `[16]`, "Spec deltas keep each behavior with the feature that owns it, never per technology."** `[16]` rejected "a `postgres/` spec group or a `vs-adapter/postgres-dialect` feature holding PostgreSQL's rendering rules" on the ground that it would organize specs by technology rather than by behavior, so `pushdown-filter` would stop owning filter delegation. That reasoning is answered rather than ignored: `pushdown-filter` still owns what a filter fragment *is*, and what changes is that it stops also owning MySQL's hex literals. The half of `[16]` that stands is `vs-adapter/driver-selection` existing as its own feature. This is a deliberate revision made on a direct instruction in round 4, not a contradiction left in place.

- **Decision:** Split every spec that mixed the two concerns into a framework feature and one feature per technology, using flat feature names prefixed by the technology inside the three existing domains. Framework features keep the protocol's own vocabulary as their names (`pushdown-dialect`, `pushdown-projection`, `pushdown-filter`, `pushdown-aggregation`, `pushdown-join`, `type-mapping`, `create-virtual-schema`, `result-ordering`, `adapter-request-dispatch`, `driver-selection`, `arrow-scan`, `driver-self-install`). Technology features are named `<technology>-<concern>`: `mysql-pushdown`, `mysql-collation`, `mysql-type-mapping`, `postgresql-pushdown`, `postgresql-collation`, `postgresql-type-mapping` in `vs-adapter/`, and `mysql-scan`, `postgresql-scan` in `scan-udf/`. A third technology adds exactly the same set of names with its own prefix.

- **The nesting question is measured, not assumed.** `speq feature get`'s own help states `Path: domain/feature or domain/feature/scenario`, and a probe against a throwaway project confirms the third segment is a scenario name: a feature placed at `dom/mysql/pushdown/spec.md` is **silently dropped** from `speq feature list` and `speq domain list`, and `speq feature get dom/mysql/pushdown` fails with `Feature not found: dom/mysql` — it parsed `pushdown` as a scenario of a feature `dom/mysql` that does not exist. Silent omission, not an error, is the decisive fact: a nested spec would be invisible to search, listing, and validation rather than rejected. Directory nesting is therefore unavailable, and the technology axis has to live in the feature *name*. A future planner should not re-probe this; they should re-probe only if `speq --version` changes.

- **Why `<technology>-<concern>` rather than one `<technology>-pushdown` feature per technology.** The instruction's own examples named four features (`mysql-pushdown`, `postgresql-pushdown`, `mysql-type-mapping`, `postgresql-type-mapping`) as an illustration. Collecting every MySQL-specific pushdown scenario into one `mysql-pushdown` lands it at roughly 19 scenarios, nearly double the ten-scenario organization threshold and larger than the `pushdown-aggregation` file whose size is itself the signal that started this. Collation is the cut that fixes it, and it is the right cut on the merits rather than a convenient one: collation placement is the single largest structural divergence between the two targets, and it is the one place where the *reason* differs rather than the syntax. MySQL's default `utf8mb4_0900_ai_ci` answers both of Exasol's character questions differently, so MySQL collates equality operands and ordering operands and pays for it with a coordinated two-clause grouping rule and one composed shape it must reject outright. PostgreSQL's collations are all deterministic, so its equality already is Exasol's and it collates ordering operands alone. Splitting on the fragment-kind axis instead (`mysql-pushdown-filter`, `mysql-pushdown-aggregation`, …) was rejected: it duplicates the framework's own taxonomy per technology, costs twice as many features, and cuts across the divergence rather than along it.

- **Driver provisioning stays pure framework, and this is a decision rather than an omission.** `driver-provisioning/driver-self-install` gains no per-technology feature. The per-technology provisioning facts — registry package name, library filename, ADBC entry-point symbol, version range — already moved out of spec prose into `crates/adbc-vs-scan/drivers/<technology>.toml` under decisions `[17]` and `[21]`, where they are *values* the build compiles into a table. No provisioning scenario states a behavior for one technology that another contradicts; the two drivers differ only in the contents of a row. A `mysql-provisioning` feature would therefore hold a table of constants, which is exactly what the TOML file already is, so it would duplicate the data rather than separate a concern. This is decision `[17]`'s "values as data, behavior as code" rule applied to specs: the split follows behavior, and provisioning's technology-dependence is entirely data.

- **The scan UDF does get the split, for the opposite reason.** PostgreSQL's credential handling is behavior, not data. Its ADBC driver's `SetOption` accepts exactly `uri` and rejects `username` and `password`, so the credential travels in a libpq keyword/value connection string built in memory and stripped from every surfaced error, where MySQL passes separate options and puts no credential in a connection string. No data format expresses that difference. `scan-udf/arrow-scan` keeps the invariants binding both drivers — nothing persisted, nothing disclosed, coercion, streaming — and each technology's own mechanism moves to `scan-udf/mysql-scan` and `scan-udf/postgresql-scan`. The symmetry is the point: leaving MySQL's mechanism inside the framework file while PostgreSQL's moved out would give one decision two owners depending on which technology asked.

- **The migration mechanics, which `/speq:spec-merge` says must never be assumed.** The merge applies `DELTA:NEW` (append a scenario), `DELTA:CHANGED` (replace the scenario of that name), and `DELTA:REMOVED` (delete the scenario of that name), always inside an existing feature file at its existing path. It has no marker for moving a scenario, splitting a file, renaming a feature, or deleting a file. Every move in this restructuring is therefore expressed as an ordered pair: a `DELTA:REMOVED` block in the old feature's delta reproducing the library's scenario heading **byte for byte**, and the same scenario reproduced in the new technology feature's spec, which is a new file and so carries a full spec with no markers at all. A heading that changes in the move is still one `DELTA:REMOVED` against the old name — never a `DELTA:CHANGED`, which would search for a name the library does not have and silently apply nothing.
- **No old feature file ends up empty, and that is a finding rather than a convenience.** Every one of the five features the instruction named as a migration source keeps a genuine framework remainder after its technology scenarios leave: `pushdown-projection` keeps 4, `pushdown-filter` 6, `pushdown-join` 8, `pushdown-aggregation` 13, `type-mapping` 5, `pushdown-dialect` 13. `pushdown-dialect` is the clearest case — 12 of its 13 scenarios were already technology-agnostic, and only "Capability set advertises the fragments this release renders" was MySQL's. The correct reading is that these files were framework features all along, carrying technology-specific scenarios as guests, so they need their guests removed rather than retirement. **No feature file is retired, no recorder-agent or human deletion step is required, and no marker is needed that does not exist.** Had any file emptied, the merge could not have expressed it: `speq feature validate` fails a spec with no scenarios (`ERROR: No scenarios defined`), so an emptied file would have blocked recording until a human deleted it by hand. The restructuring was shaped to avoid needing that, and a future planner proposing a further split MUST check the same property before committing to it.

- **Alternatives:** *A `postgresql/` or `framework/` top-level domain* — rejected by the instruction and by this repo's spec governance, which fixes the three live domains. *Directory nesting under `vs-adapter/mysql/pushdown`* — rejected because the tool silently ignores it, as measured above. *Parameterizing the existing MySQL scenarios by dialect* — rejected for the reason `[16]` gave and which still holds: those scenarios carry measured MySQL specifics (collation names, error 1055, backtick escaping, hex literals) that a parameterized scenario would erase. *Leaving PostgreSQL's scenarios as `DELTA:NEW` blocks inside the shared files, as this plan had them* — rejected by the instruction, and independently unsound at scale: `pushdown-join` had reached the state of carrying a `DELTA:REMOVED` block reproducing the library's MySQL-named scenario beside a PostgreSQL-flavored `DELTA:NEW` replacement in one file, which is the shape a third technology turns into an unreadable file.

- **Rationale:** Two technologies made the mixing visible; a third makes it unmanageable. The framework/technology split gives each significant decision exactly one owner — what a filter fragment *is* belongs to `pushdown-filter`, and what MySQL renders it as belongs to `mysql-pushdown` — which is the information-leakage test the driver identity was already introduced to satisfy in code. Doing it now, before `/speq:record` has merged anything, costs only delta authoring; doing it after would require editing permanent library files through a marker system that cannot express a move. The restructuring also answers a signal the library had already raised on its own, independent of the instruction: `pushdown-aggregation` stood at 23 scenarios against a threshold of 10, and this split takes it to 13 while moving 9 measured MySQL collation scenarios to the feature that owns them.

- **Consequence, stated rather than hidden:** `vs-adapter` reaches 16 features against `/speq:spec-merge`'s threshold of 8, and six spec files stay above the ten-scenario threshold. Neither is a defect of this split. `vs-adapter` held 9 features and roughly 96 scenarios *before* it, so the two thresholds were already jointly unsatisfiable for that domain — at ten scenarios per file, 96 scenarios need at least ten files — and the only lever that resolves them is a new top-level domain, which governance forbids. The thresholds are advisory signals returned to a human at record time, not validator errors, and they are escalated as an open question rather than silently absorbed. **Decision `[26]` answers that escalation.**
- **Promotes to ADR:** yes

### [26] driver-provisioning splits three ways, and vs-adapter's 16 features are the accepted shape

> **Resolves the open question decision `[25]` escalated.** `[25]` deliberately left two organization questions for a human rather than absorbing them: whether `driver-self-install` at 17 scenarios is split, and whether 16 features in `vs-adapter` is the standing shape. A human answered both in round 5, and this entry records them together because they were decided together.

- **Decision, part one — the split.** `driver-provisioning` holds three framework features instead of one. `driver-self-install` keeps the install mechanism: download, `MANIFEST` check, upload, visibility wait, both transport policies, and the no-bundled-binary property. `driver-version-resolution` takes everything read out of the registry index: which version a driver's range resolves to, which `linux_amd64` package serves it, and whether the mount already holds that resolved version. `driver-path-override` takes the `DRIVER_PATH` air-gap mechanism. Merged counts are 9, 6, and 2 — the whole domain clears the ten-scenario threshold, and the largest file in the library drops from 17 to 9.

- **The cut is framework-internal, which `[25]` had already ruled the only admissible axis.** Provisioning's technology-dependence is *data* in `drivers/<technology>.toml`, so a `mysql-provisioning` / `postgresql-provisioning` pair would hold a table of constants the TOML file already is. That reasoning is untouched: none of the three new features names a technology, and a third driver adds rows to a TOML file rather than a fourth provisioning feature.

- **Why these three lines and not the obvious stage split.** Cutting by execution stage — fetch, then verify, then upload — is the tempting cut and the wrong one. It organizes modules around execution order, which is the temporal leakage `/speq:design-philosophy` names: every stage would still carry the version decision, so the question "which version is this cluster running" would have three owners. Cutting by *question answered* gives it exactly one. The three questions are genuinely distinct and have distinct answers: how a package gets from the CDN onto a mount (uniform across drivers, mechanical), which version is wanted and whether it is already there (range semantics, per-driver data, the reason the install path carries a version), and how an operator opts out of both (an interface, not a mechanism).

- **Three scenarios move out of the permanent library, so each is the standard migration pair.** MySQL driver provisioning shipped in release 0.2, so `specs/driver-provisioning/driver-self-install/spec.md` exists and holds 12 scenarios. "Already-installed driver short-circuits the fetch", "Unreachable registry names the offline fallback", and "Missing platform package fails with a named error" now belong to `driver-version-resolution`. Each is expressed exactly as decision `[25]` requires: a `DELTA:REMOVED` block in `driver-self-install`'s delta reproducing the library heading and body byte for byte, plus the rewritten scenario in the new feature's full spec. A `DELTA:CHANGED` rename would search the library for a heading it does not have and silently apply nothing. The two `DRIVER_PATH` scenarios and the two range scenarios were `DELTA:NEW` in this plan and never reached the library, so they simply author into the new files.

- **No feature file empties, checked rather than assumed** — the property `[25]` requires a further split to verify before committing to it. `driver-self-install` keeps 9 scenarios: two the delta rewrites, two it adds, and the five transport and BucketFS scenarios the library already holds and no delta touches. `speq feature validate` fails a spec with no scenarios, so an emptied file would have blocked recording until a human deleted it by hand.

- **Decision, part two — the feature count.** `vs-adapter`'s 16 features exceed `/speq:spec-merge`'s generic guideline of 8, and that is accepted as final. The guideline and the ten-scenario file guideline were already jointly unsatisfiable for this domain before the plan: 9 features and roughly 96 scenarios cannot both fit under 8 files and under 10 scenarios each. The only lever is a new top-level domain, which this repo's spec governance forbids and which the human declined to revisit.   The shape assertions matched too: a `TIMESTAMP` entry carries `fractionalSecondsPrecision` 3, a `VARCHAR` entry carries `size` and **no** `characterSet`, and a select-list `predicate_less` entry carries `BOOLEAN`. The three Exasol types PostgreSQL's mapping produces that MySQL's fixture does not exercise behave by the same rules: `MIN`/`MAX` over `DECIMAL(10,0)`, `DECIMAL(19,0)`, and `DATE` each carry the operand's own type, `COUNT(DISTINCT)` over any of them carries `DECIMAL(18,0)`, and `SUM` carries `DECIMAL(min(p+11,36),s)` — `DECIMAL(21,0)` over `DECIMAL(10,0)`, `DECIMAL(30,0)` over `DECIMAL(19,0)`. **Consequence: `vs-adapter/pushdown-aggregation`'s declared-type rule stays one framework rule over both dialects**, exactly as its Background states, and nothing per dialect is needed. This is what the Background bullet "Nothing about it is per dialect: the type Exasol expects is Exasol's answer, not the source's" predicts, now measured over a second source shape rather than inferred from one.

- **Divergence 1 — `Infinity` and `-Infinity` are NOT storable in a `numeric(p,s)` column, only `NaN` is.** `INSERT … VALUES ('Infinity')` into a `numeric(12,4)` column is rejected with `ERROR: numeric field overflow / DETAIL: A field with precision 12, scale 4 cannot hold an infinite value`, and so is `-Infinity`; `'Infinity'::numeric(12,4)` is rejected identically. `NaN` is accepted and stores as `NaN`. An **unconstrained** `numeric` accepts all three. This contradicts `scan-udf/postgresql-scan`'s Background bullet "PostgreSQL `numeric` legitimately holds `NaN`, `Infinity`, and `-Infinity`" *as applied to a mapped column*, and plan.md § Context's "`NaN`/`±Infinity` are legal source values no Exasol `DECIMAL` can hold". The bullet is true of the `numeric` type in general and false of every column this release maps, because `vs-adapter/postgresql-type-mapping` maps only `numeric(p,s)` and leaves unconstrained `numeric` unmapped. **Consequences:** (i) task 7.1's `NaN` case is reachable end to end and its `Infinity`/`-Infinity` cases are reachable **only as unit tests over a constructed Arrow string array** — no fixture and no E2E query can make a mapped column produce one; (ii) task 8.1 cannot seed `Infinity` into its `numeric(12,4)` column and must seed `NaN` there instead, seeding the infinities into the unconstrained `numeric` column it already plans, which stays unmapped; (iii) the coercion must still refuse all three, since refusing a value it can never see costs nothing and the unmapping that makes it unreachable is a *mapping* decision the coercion must not depend on. Also measured: `MAX("n")` over a `numeric(12,4)` column holding a `NaN` returns `NaN`, because PostgreSQL sorts `NaN` above every finite value — so a delegated `MAX` is a second route by which `NaN` reaches the scan, beside a bare projection.
- **Divergence 2 — the driver spells the specials `nan`, `inf`, and `-inf`, not `NaN`, `Infinity`, and `-Infinity`.** Read back through Arrow, a `NaN` stored in a `numeric(12,4)` column arrives as the string `nan`; an unconstrained `numeric` holding the three specials arrives as `nan`, `inf`, `-inf`. `scan-udf/postgresql-scan`'s Background says only "the strings the driver produces", which stays true, but **plan.md task 7.1 names `NaN`, `Infinity`, and `-Infinity`** — the PostgreSQL spellings, which never reach the scan. **Consequence: task 7.1 must match the driver's spellings, not PostgreSQL's, and must not lean on a permissive numeric parse** — Rust's `f64::from_str` and `str::parse` accept `nan`, `inf`, and `-inf`, so a parse-then-check implementation would silently produce a non-finite value rather than the named error the scenario requires. The safe shape is a strict decimal parse that rejects any non-digit body, with the three spellings named explicitly so the error can name the value; matching both casings costs nothing and survives a driver that changes its rendering.
- **Divergence 3 — outside the eight, found while confirming (f)'s precondition: PostgreSQL 18.6 accepts `LIKE` over a nondeterministic collation.** `vs-adapter/postgresql-type-mapping`'s Background says a nondeterministic collation "equates values Exasol keeps apart and makes `LIKE` fail outright". The first half is confirmed: a column collated `und-u-ks-level2` grouped `widget` and `Widget` into **one** group where Exasol returns two, and `"g" = 'widget'` matched both rows. The second half is **false on 18.6** — `SELECT … WHERE "g" LIKE 'W%'` was accepted and matched **both** `widget` and `Widget`. PostgreSQL 18 added pattern matching over nondeterministic collations; earlier majors raised `nondeterministic collations are not supported for LIKE`. **The unmapping decision is unchanged and if anything better supported**: on 18.6 a nondeterministic collation now fails *silently with wrong rows* in the `LIKE` path too, rather than erroring, which is the failure mode the mapping exists to prevent. **Consequence: the Background bullet's `LIKE` clause needs rewording before record** — the reason is "returns rows Exasol does not, in every comparison path including `LIKE`", not "fails outright". No scenario text changes: `vs-adapter/postgresql-type-mapping` asserts that such a column is unmapped, never that `LIKE` errors.
- **Also confirmed, outside the eight, because a late contradiction would be expensive.** The ADBC PostgreSQL driver rejects the separate-credential options exactly as plan.md § Context and `scan-udf/postgresql-scan` state: `new_database_with_opts` carrying `username` fails with `NotImplemented: [libpq] Unknown database option username`. A libpq **keyword/value conninfo string** passed as the `uri` option connects and executes successfully (`host='127.0.0.1' port='5432' dbname='adbc_vs' user='adbc_vs' password='…'`), so task 5.4's chosen form works against a live server. The URI form connects too, so the plan's choice between them rests on escaping totality as decision `[6]` states, not on one form failing. A wrong-password failure surfaced `IO: [libpq] Failed to connect: connection to server at "127.0.0.1", port 5432 failed: FATAL: password authentication failed for user "adbc_vs"` — carrying **neither** the password nor any conninfo fragment. That is one observation of one error path, not a guarantee, so task 5.4's requirement that the adapter redact at its own boundary rather than trust the driver stands unchanged.
