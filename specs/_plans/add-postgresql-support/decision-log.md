# Decision Log: add-postgresql-support

## Interview

No live interview took place. This plan was authored in headless mode, so every decision below was assumed and documented rather than confirmed with a human, per the planning skill's headless rules. The request as received:

**Q:** What should this plan add?
**A:** "add support for PostgreSQL; make the feature push-down dynamic. Each technology (mysql, or postgresql) may advertise different features; pgsql shall also auto-download the driver; match feature scope of mysql (but optimize via tasks)"

**Q:** Which of those four clauses needed interpretation, and how was each read?
**A:** *Dynamic pushdown* was read as per-dialect capability advertisement resolved from the virtual schema's own driver, not as run-time capability probing of the source — `pushdown-dialect` already states that the dialect owns its set, so the gap was the resolution point rather than the ownership model. *Auto-download* was read as the existing `driver-self-install` mechanism generalized to a per-driver package table, not a second install path. *Match feature scope* was read as the same capability set, the same delegation tiers, and a comparably narrow mapped-type set, with divergence only where PostgreSQL's SQL or type system genuinely differs — and with each divergence documented rather than silently absorbed. *Optimize via tasks* was read as factoring the driver-identity refactor into one phase that four later workstreams build on concurrently, rather than duplicating it per driver.

**Q:** Was anything escalated?
**A:** No. Two decisions came close to the escalation bar — the PostgreSQL credential path, which narrows a stated security invariant, and exposing only the `public` schema — and both are recorded below with their alternatives. Neither is irreversible: the credential form is forced by the driver's API rather than chosen between competing designs, and a schema property can be added later with `public` as its default. Three decisions the plan could not resolve from documentation are deferred to measurement gates rather than to a human, which is what the repo's existing plans do with the same class of unknown.

## Design Decisions

### [1] A closed driver-identity enum owns every per-driver fact

- **Decision:** Introduce `Driver` as a closed enum in `adbc-vs-scan::driver`, with three tables keyed on it: the driver package (pinned version, library filename, package SHA-256, registry path, ADBC entry-point symbol) in the same crate, and the dialect and the metadata source in `adbc-vs-adapter`. No call site branches on a driver name.
- **Alternatives:** Thread a driver string through the six modules that currently hold single-driver constants — rejected, because nothing would fail when a seventh place needed updating. Bundle all per-driver behavior behind one trait object — rejected, because the package data is read by `adbc-vs-scan`, which cannot depend on the adapter crate where the dialect lives, so one bundle would invert the crate dependency.
- **Rationale:** A Rust `match` over a closed enum is exhaustive, so adding a driver fails the build at every table missing a row. That converts "a second driver adds an implementation rather than editing a renderer" from a convention `pushdown-dialect` asserts into something the compiler enforces. It also gives "which drivers exist" exactly one owner, where release 0.2 restated it in `create_schema`, `provisioning`, `connection`, `driver`, and `dispatch`.
- **Promotes to ADR:** yes

### [2] Both getCapabilities and pushdown resolve the dialect from adapterNotes.driver

- **Decision:** Resolve the driver identity from `schemaMetadataInfo.adapterNotes` in both dispatch arms, and error when the field is absent rather than defaulting to a driver.
- **Alternatives:** Read `schemaMetadataInfo.properties.DRIVER` instead — kept as the fallback if gate 2.1 finds `adapterNotes` absent from `getCapabilities`, but not the first choice. Default to MySQL when the field is missing — rejected outright: advertising one dialect's set for another's source returns wrong rows for every capability the two do not share, which is the exact failure `pushdown-dialect` exists to prevent.
- **Rationale:** `pushdown` already reads `adapterNotes`, and its `driver` field is already written by `createVirtualSchema` and never read. Using one field for both answers preserves the property `dispatch`'s module doc claims for release 0.2 — that the advertised set and the renderer can never disagree — while letting the answer differ per virtual schema. Two fields could drift; one cannot.
- **Promotes to ADR:** yes

### [3] Each dialect states its own capability set, and the invariant test enumerates dialects from the type

- **Decision:** Keep `SqlDialect::capabilities` as a per-implementation hand-stated list, and generalize the invariant test that renders every advertised capability to run once per `Driver` variant, enumerated from the type rather than from a list in the test. Add a test asserting the two sets differ in exactly `JOIN_TYPE_FULL_OUTER`.
- **Alternatives:** Derive one release-wide set as the intersection of what both dialects render — rejected, because it makes one target's limitation govern the other's delegation and would discard PostgreSQL's full outer join. Derive each set from the other by addition or removal — rejected for the same reason in weaker form: a derived set makes one dialect's withholding silently govern the other's.
- **Rationale:** ADR 002 already established that a hand-stated set plus a required invariant test is what pins the advertised set to the renderer, because nothing in the type system can fail a build when a rendering path is removed. That reasoning is per dialect, so the test becomes per dialect. Enumerating variants from the type means a third dialect inherits the invariant without anyone editing the test.
- **Promotes to ADR:** yes

### [4] PostgreSQL renders a collation only where order decides the answer

- **Decision:** The PostgreSQL dialect renders `COLLATE "C"` on a character operand of `predicate_less`, `predicate_lessequal`, `predicate_between`, `MIN`, and `MAX`, and renders no collation on an equality operand, a `LIKE` operand, an `IN` operand, a `GROUP BY` key, a bare select-list occurrence of a grouped column, a `DISTINCT` operand, or a join key.
- **Alternatives:** Mirror MySQL's structure and collate every character operand uniformly — rejected on two counts: it would cost the source's index support on every equality predicate for no correctness gain, and collating the `GROUP BY` key would recreate MySQL's coordinated two-clause rule and, with it, the composed shape MySQL must reject outright. Render no collation anywhere — rejected: the official `postgres` image creates its cluster with `LC_COLLATE=en_US.utf8`, so an uncollated `MIN` over `B`, `a`, `C` returns `a` where Exasol returns `B`.
- **Rationale:** Exasol asks two questions of a character value, and MySQL's default answers both differently while PostgreSQL's default answers only one differently. A deterministic collation — which is every collation PostgreSQL ships — equates two values just when their bytes are identical, which is Exasol's equality exactly; `C` sorts by byte value, which for UTF-8 is code-point order. Rendering where the target actually diverges, rather than uniformly, is what removes a whole rule and an exclusion from the PostgreSQL dialect rather than translating them.
- **Promotes to ADR:** yes

### [5] A PostgreSQL character column of a nondeterministic collation is unmapped

- **Decision:** Unmap a PostgreSQL character column whose declared collation is nondeterministic, with the reason naming the collation. Treat a server reporting no determinism flag as deterministic.
- **Alternatives:** Document the hazard and map the column anyway — rejected: a nondeterministic collation equates values Exasol keeps apart, which is a silent wrong-rows failure, and it makes `LIKE` fail outright. Render `COLLATE "C"` on every character operand to immunize against it — rejected as decision `[4]` records, because the cost lands on every equality predicate and reintroduces the grouping-collation exclusion.
- **Rationale:** Decision `[4]` relies on PostgreSQL's equality being byte equality, and one kind of collation breaks that reliance. Refusing the column is the same answer `type-mapping` already gives a MySQL character column of the wrong character set: a character column whose comparison cannot be delegated correctly is omitted rather than exposed. Because every shipped PostgreSQL collation is deterministic, the rejection reaches only a collation an operator created.
- **Promotes to ADR:** no

### [6] PostgreSQL credentials travel inside the driver's single connection option

- **Decision:** Build a libpq keyword/value connection string in memory at connect time from the freshly resolved `CONNECTION` object — host, port, and `dbname` from the address, every address query parameter carried across as a keyword of the same name, `user` and `password` from the object, every value single-quoted with an embedded quote or backslash escaped — and pass it as the driver's only accepted database option. Pass no `username` or `password` option for this driver. Strip the resolved password from every surfaced error, including text the driver or libpq produced.
- **Alternatives:** Keep the separate `username` and `password` ADBC options — impossible: the driver's `SetOption` accepts exactly `uri` and rejects the others as unknown options. Inject the credential into the `postgresql://` URI — rejected, because URI form needs percent-encoding and a password containing `&`, `#`, `@`, or `/` changes the parse rather than the value, where conninfo escaping is total. Pass the credential through libpq's environment variables — rejected: untested inside a UDF sandbox, process-visible, and `set_var` is `unsafe` in edition 2024.
- **Rationale:** This is the plan's one deliberate narrowing of a security property, and it is forced by the driver's API rather than chosen between designs. `arrow-scan`'s invariant that no credential passes through a connection string cannot hold for a driver that accepts nothing else. Every invariant about persistence and disclosure does still hold and is now asserted rather than assumed: nothing reaches the scan specification, `adapterNotes`, SQL text, `EXPLAIN VIRTUAL` output, or any log line, and the redaction is applied by the scan rather than relied on from the driver, because libpq's diagnostics can echo connection parameters. The narrowing is stated in the plan's Impact section so an operator reads it, together with the reason a PostgreSQL `CONNECTION` deserves a least-privilege read-only role.
- **Promotes to ADR:** yes

### [7] PostgreSQL string literals are escape-string constants

- **Decision:** Render every PostgreSQL string literal as `E'<body>'`, escaping a backslash as two backslashes and a single quote as two single quotes, unconditionally rather than only for a value that needs it.
- **Alternatives:** Render a bare `'...'` literal and add a `standard_conforming_strings` precondition check at `CREATE VIRTUAL SCHEMA` — rejected, because the setting is a GUC that can change per role after creation, so a creation-time check does not bind at query time. Mirror MySQL's hex form as `convert_from(decode('<hex>','hex'),'UTF8')` — rejected on typing: that expression is typed `text`, and PostgreSQL applies no implicit coercion from `text` to a numeric or temporal column, so every non-character comparison would fail with an unknown-operator error. Choose the form per value, using bare quotes when the value holds no backslash — rejected, because it would let a literal change the shape of the generated statement, which the MySQL dialect deliberately paid a hex encoding to avoid.
- **Rationale:** The `E` prefix selects backslash-escape processing whatever `standard_conforming_strings` holds, and doubling the quote rather than backslash-escaping it also removes the dependency on `backslash_quote`. So one form is independent of both settings with no server check, and it yields an untyped literal PostgreSQL resolves from the other operand, which is what every numeric and temporal comparison needs.
- **Promotes to ADR:** no

### [8] PostgreSQL exposes the public schema only, with no new property

- **Decision:** A PostgreSQL virtual schema exposes the `public` schema of the addressed database. `adapterNotes` records `public` as the source namespace, which is both the SQL qualifier and the `information_schema` filter value. No fourth `CREATE VIRTUAL SCHEMA` property is added.
- **Alternatives:** Add a `SCHEMA_NAME` property — rejected for now: a property is a decision the adapter declined to make, and one added now becomes a supported input a later release cannot narrow. Auto-detect from the connection's `search_path` — rejected, because the exposed table set would then depend on invisible server state that the persisted metadata cannot track, so a role change would silently invalidate a created virtual schema.
- **Rationale:** MySQL's namespace comes from the address's path component because a MySQL database *is* its SQL qualifier; PostgreSQL's path component names a database, which is not a qualifier, so a namespace has to come from somewhere else. A virtual schema per source schema needs no new property, and adding `SCHEMA_NAME` later with `public` as its default stays compatible with everything created before it. The boundary is stated in the spec as this release's scope rather than left as an omission.
- **Promotes to ADR:** no

### [9] PostgreSQL boolean, character(n), text, and unconstrained numeric are unmapped

- **Decision:** Map seven PostgreSQL types — `integer`, `bigint`, `numeric(p,s)`, `character varying(n)`, `date`, `timestamp without time zone`, `double precision` — and leave every other type unmapped with a recorded reason.
- **Alternatives:** Map `boolean` to Exasol `BOOLEAN` — rejected: it would make `BOOLEAN` a type a source column produces, widening the mapped set that `pushdown-dialect`'s closure argument is built on, bringing a boolean operand into every predicate path, and requiring `LITERAL_BOOL`, which neither dialect advertises. Map `character(n)` to Exasol `VARCHAR` — rejected: PostgreSQL returns the value blank-padded and compares two of them ignoring trailing spaces, so `VARCHAR` matches neither the value nor the comparison and a delegated predicate would return wrong rows. Map `character(n)` to Exasol `CHAR`, which does match both — rejected as out of scope: four features state the invariant that every delegated character operand is Exasol `VARCHAR`, and reopening it is a larger change than this plan buys. Map `text` and unconstrained `numeric` by substituting a maximum size or precision — rejected, because Exasol compares a declared type for exact equality and a source value need not fit an invented bound.
- **Rationale:** The request asked to match MySQL's scope, and MySQL maps eight deliberately narrow types while omitting `TEXT`, `TINYINT`, `FLOAT`, `TIME`, and `JSON`. The PostgreSQL set is chosen to be the same shape rather than to exhaust PostgreSQL's type system, so the produced Exasol type set stays the same five for the release and no closure argument in `pushdown-dialect` has to be re-derived. `character(n)` is the one place the two scopes genuinely diverge, and the padding direction is why. The `character(n)` omission is bounded by adbc-vs's own invariant that every delegated character operand is Exasol `VARCHAR`, not by anything PostgreSQL cannot express: Exasol `CHAR` does match `character(n)`'s value and its comparison. Lifting it needs its own plan revisiting that invariant across the four features that state it — `vs-adapter/type-mapping`, `vs-adapter/pushdown-filter`, `vs-adapter/pushdown-aggregation`, and `vs-adapter/pushdown-join` — and adding the mapping here without that plan would leave three of them contradicting the fourth.
- **Promotes to ADR:** no

### [10] SUM and AVG stay withheld for PostgreSQL, despite its exact-numeric sum being exact

- **Decision:** Withhold `FN_AGG_SUM`, `FN_AGG_SUM_DISTINCT`, `FN_AGG_AVG`, and `FN_AGG_AVG_DISTINCT` from the PostgreSQL dialect as well as the MySQL one.
- **Alternatives:** Advertise `FN_AGG_SUM` for PostgreSQL and refuse a floating-point operand at render time — rejected. Advertise it and accept the divergence on `double precision` — rejected outright, since it returns a wrong number silently.
- **Rationale:** PostgreSQL's `sum` over `integer` returns `bigint` and over `numeric` returns `numeric`, both exact and order-independent, so a capability admitting only exact-numeric operands would be sound. None exists: a capability is advertised once per session and `FN_AGG_SUM` admits every numeric operand. PostgreSQL's `sum` over `double precision` is order-dependent because floating-point addition is not associative, and a parallel plan may combine partial aggregates differently between two runs of one query, so it is less stable than MySQL's measured left-to-right accumulation rather than more. ADR 002 settled that a capability which cannot be rendered safely for every operand type it admits is withheld whole rather than refused narrowly, because Exasol does not compute a delegated fragment itself after the adapter errors. Applying that existing principle, rather than reopening it, is the whole decision here.
- **Promotes to ADR:** no

### [11] JOIN_TYPE_FULL_OUTER is advertised by PostgreSQL only, gated on measurement

- **Decision:** The PostgreSQL dialect advertises `JOIN_TYPE_FULL_OUTER` and renders `FULL OUTER JOIN`; the MySQL dialect withholds it. Advertising is conditional on gate 2.3(a) measuring that PostgreSQL accepts a full join whose condition is an equality.
- **Alternatives:** Withhold it from both, keeping the two sets identical — rejected: it is the one capability the two targets genuinely disagree on, so it is what makes the per-dialect set observable rather than merely architectural, and it is a real delegation an operator gets. Advertise it without measuring — rejected: PostgreSQL restricts a full join to conditions that are merge- or hash-joinable, and an advertised capability the source refuses converts a query Exasol would have answered into a hard failure.
- **Rationale:** `pushdown-join`'s existing reason for withholding the capability is MySQL's lack of the feature, not a scope exclusion — mission.md scopes pushdown to equi and outer joins, and a full outer join is an outer join. So advertising it for a target that implements it follows the existing decision rather than revising it. An equality over one common type is both merge- and hash-joinable, which is why the restriction is expected not to bind; the gate is there because "expected" is not this repo's standard for a capability whose failure mode is a hard error. If the gate measures a rejection, the capability is withheld, the sets coincide in this release, and the plan says so rather than the architecture being wrong.
- **Promotes to ADR:** no

### [12] Type mapping moves behind MetadataSource rather than behind its own trait

- **Decision:** `MetadataSource::discover_tables` returns columns already mapped to `MappedType` with omissions recorded, so each driver's metadata source owns both its catalog SQL and its type mapping, and `create_schema` branches on no driver. The same trait carries each dialect's source precondition check.
- **Alternatives:** Add a separate `TypeMapper` trait keyed on `Driver` — rejected, because it needs a common source-column struct, and MySQL needs the unsigned flag and the column character set while PostgreSQL needs `udt_name` and the collation's determinism; a shared row would lose whichever fields one source has and the other does not, leaking each source's gaps into the caller. Keep the mapping in `create_schema` with a driver match — rejected, because it puts driver knowledge back in the module the identity was introduced to keep driver-neutral.
- **Rationale:** The reason to change a mapping and the reason to change a catalog query are the same reason: the source's own catalog and type system. Grouping by that, rather than by the technical role of "querying" versus "mapping", is what makes each driver's module deep enough that `create_schema` needs to know nothing. The precondition check joins the same trait because the requirement is stated by the dialect that renders it and executed by the module that speaks the source's SQL — which is the rule `create-virtual-schema` already states for MySQL's collations.
- **Promotes to ADR:** no

### [13] Pinned driver version strings are stored per driver, never derived

- **Decision:** Store each driver's pinned version string exactly as the registry index spells it — `v0.6.0` for MySQL and `1.12.0` for PostgreSQL — as a field of that driver's package row, and assert both resolve against the real index.
- **Alternatives:** Store a bare semantic version and add or strip a leading `v` when building the lookup — rejected: the index's spellings are not uniform across drivers, and the lookup matches the `version` scalar by exact string equality, so any single normalization rule fails for one of the two published versions.
- **Rationale:** This is a small decision worth recording because it is invisible until it fails, and it fails as a "version not published" error that reads like a registry problem rather than a formatting one. The relative package URL inside a matched block carries its own version segment and is read from the index rather than constructed, so nothing else depends on the spelling.
- **Promotes to ADR:** no

### [14] The PostgreSQL test container keeps its default locale

- **Decision:** Run `postgres:18.6-trixie` with the image's default `LANG=en_US.utf8` and set no `POSTGRES_INITDB_ARGS`, so the cluster is created with locale collation rather than code-point collation.
- **Alternatives:** Force `--locale-provider=builtin --builtin-locale=C.UTF-8` at initdb so the cluster sorts by code point — rejected, because the tests would then pass with the `COLLATE "C"` suffix missing from `MIN` and `MAX`, which is precisely the divergence the suffix exists to fix.
- **Rationale:** A test container configured to agree with Exasol cannot catch a dialect that fails to make the source agree with Exasol. The locale default is also the configuration a production cluster is likelier to have, so the fixture is honest as well as sensitive.
- **Promotes to ADR:** no

### [15] Three unknowns are deferred to measurement gates rather than assumed

- **Decision:** Gate 2.1 measures whether `getCapabilities` carries `schemaMetadataInfo.adapterNotes`; gates 2.2a and 2.2b measure whether the C++ PostgreSQL driver loads inside the UDF sandbox; gate 2.3 measures eight PostgreSQL semantic assumptions including the full-join condition restriction and the absence of a grouped-select-list rejection. Each gate precedes the tasks whose design it decides, and a contradicting result re-plans the affected spec bullets and scenarios before the rendering work starts.
- **Alternatives:** Assume each from documentation and correct during implementation — rejected: two of the three change the plan's architecture rather than an implementation detail. If the driver identity does not reach `getCapabilities`, per-dialect capability sets are illegal and the plan's central claim collapses to an intersection. If the driver does not load in the sandbox, the fix lands in `language-container-rs` and returns through the release chain, so the plan is blocked on another repo. Escalate all three to a human — rejected: none is a decision needing judgment, each is a fact needing a container.
- **Rationale:** Gating an unknown that decides an architecture is the pattern this repo's earlier plans used for exactly this class of question, and the gates that mattered most there were the ones that falsified a documented expectation. The driver-load gate is ordered first because it is the highest-consequence unknown and the most expensive one to discover late: a failure is fixed in `language-container-rs` and returns through the release chain. It is not cheap, and the plan says so rather than implying it: gate 2.2a needs HTTPS egress and a BucketFS upload, and gate 2.2b needs `make cross-udf-build`, `make stack-up`, the installed SLC, and a throwaway raw driver-load entry point. What it does not need is the dialect, the refactor, or a PostgreSQL container, which is why it can run before any of them.
- **Promotes to ADR:** no

### [16] Spec deltas keep each behavior with the feature that owns it, never per technology

- **Decision:** Add PostgreSQL scenarios to the existing `pushdown-*`, `type-mapping`, `create-virtual-schema`, `driver-self-install`, and `arrow-scan` features, and add exactly one new feature, `vs-adapter/driver-selection`, for the driver identity itself.
- **Alternatives:** Create a `postgres/` spec group or a `vs-adapter/postgres-dialect` feature holding PostgreSQL's rendering rules — rejected, because it organizes specs by technology rather than by behavior, so `pushdown-filter` would stop owning filter delegation. Parameterize the existing MySQL scenarios by dialect — rejected, because those scenarios carry measured MySQL specifics (collation names, backtick escaping, hex literals) that parameterizing would erase.
- **Rationale:** The repo's own spec governance already settled the analogous question for end-to-end tests: behavior verified through a live stack belongs to the feature that owns the behavior, never to a group organized by test file. The same logic makes PostgreSQL's filter rendering a scenario in `pushdown-filter`. `driver-selection` is a new feature rather than scenarios spread across three existing ones because "which drivers exist and how one is selected" is a single coherent responsibility that would otherwise leak into `create-virtual-schema`, `pushdown-dialect`, and `driver-self-install` at once — the information-leakage smell the identity exists to remove.
- **Promotes to ADR:** no

### [plan-review] The keystone precondition had a mapped test no task creates
