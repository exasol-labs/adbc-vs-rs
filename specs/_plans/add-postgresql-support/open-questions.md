- [ ] Task 8.5 is the plan's keystone gate: it must prove `getCapabilities`'s request actually carries `adapterNotes`, the precondition the entire per-dialect-capability architecture depends on. As written, it names no mechanism that can do this. The repo's only request-capture code, `tests/common/probe.rs`, is a throwaway Lua adapter whose `createVirtualSchema` handler returns empty `adapterNotes` and whose `getCapabilities` handler never echoes the request it received — it captures what its own scratch adapter sees, never what the shipped `ADBC_ADAPTER` receives. Two rounds of review could not settle this without a decision: (a) extend `probe.rs` so `createVirtualSchema` records a real `adapterNotes.driver` value and `getCapabilities` echoes the received request body through the existing marker-based error channel — test-only instrumentation, no change to the shipped adapter; or (b) instrument the production adapter directly to echo the request, which review flagged as an unreviewed disclosure surface nobody asked for. Which approach should task 8.5 specify — (a), (b), or something else?
