# Plan Review Findings: add-exasol-technology (round 1)

## Summary
- Axes checked: 6/6
- Total findings: 23 (Blockers: 8, Advisory: 15)
- Intent Fidelity blockers: 2

## Premortem

Three failure stories, each routed into the taxonomy below.

- **Six months on, the feature shipped and nobody uses it.** The built-in `EXA` adapter is faster for every bulk query, adbc-vs cannot return a result larger than the UDF's memory, and the two wins it does carry (ordering fidelity, `HASHTYPE`-in-join) both have documented one-line workarounds the plan itself cites. The plan decided this tradeoff was acceptable without asking. → I1, I2, D1.
- **`/speq:record` merges the plan and the spec library contradicts itself.** `specs/vs-adapter/create-virtual-schema/spec.md` still requires every driver to expose views while Exasol exposes none; `specs/vs-adapter/pushdown-dialect/spec.md` still says there are two dialects; `driver-path-override` still promises `DRIVER_PATH` works for every driver, untested for Exasol. → R1, R2, R3.
- **`/speq:implement` dispatches Group B in parallel and four sub-agents fight over one file.** `crates/adbc-vs-scan/tests/exasol_it_test.rs` does not exist until 2.3 creates it, and 2.2, 2.4, and 2.5 all write assertions into it. → T1.

## Intent Fidelity

#### [SCOPE_REDUCTION] BLOCKER
- Location: plan.md § Design > Context and § Non-Goals; decision-log.md decisions [2] and [3]
- Issue: the user's verbatim goal is to "outperform Exasol's own Lua-based Exasol-to-Exasol Virtual Schema ... on throughput/latency". The plan drops the whole of it — "**The throughput goal is not achievable and is dropped.**" — and substitutes a different value proposition. The research behind that call is sound and well cited, and a plan asserting a refuted performance claim would be worse. The defect is that the plan then decides unilaterally, in a headless run with no interview, that the feature ships anyway. plan.md carries no `## Open Questions` section and decision-log.md carries no escalation, so the one decision only a human can make never reaches one. That decision is load-bearing, because the plan's own evidence leaves the deliverable dominated by the incumbent on the axes the user named: `IMPORT ... FROM EXA` is "always parallelized" while adbc-vs moves rows through one UDF over one connection, and decision [9] concedes a result larger than the UDF's memory limit fails outright where the bulk loader handles any volume. The residual wins are also narrower than stated: the plan quotes the vendor's own prescribed `ORDER BY FALSE` sub-query workaround for the ordering defect, so the win is over a documented workaround rather than over an unremedied defect.
- Fix: Add an `## Open Questions` section to plan.md as the first section after `## Summary`. State in it: (a) the stated throughput goal is refuted, quoting the `IMPORT ... FROM EXA` evidence; (b) what remains — ORDER BY/LIMIT fidelity, `HASHTYPE`-in-join handling, one adapter with no JVM — and that both correctness wins have documented workarounds today; (c) that the technology cannot return a result exceeding the UDF's memory limit; (d) the two options for the human, namely ship as a correctness-and-uniformity feature accepting no performance claim, or hold this plan until the follow-up benchmark plan in § Dependencies has run. Mark the question as blocking plan approval so the orchestrator raises it as a PR comment rather than treating the plan as approved.

#### [SCOPE_REDUCTION] BLOCKER

- Issue: the user's goal names "cross-cluster **or** intra-Exasol federated queries". plan.md § Non-Goals declares "cross-cluster federation between two separate Exasol instances" out of scope, and decision [6]'s rationale is a test-infrastructure limit — "CI runners already exhaust disk with three containers". Nothing in the adapter distinguishes a remote Exasol source from a local one; the plan says so itself ("nothing in the adapter distinguishes a source that happens to be the same instance"). Add the question of whether untested-but-supported is acceptable, or whether a two-instance tier is required, to the `## Open Questions` section the previous finding creates.

## Feasibility

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: `scan-udf/exasol-scan/spec.md` § Background and its scenario "The address's query string reaches the driver, so certificate handling is operator-set"; decision-log.md decision [10]; plan.md § Impact
- Issue: the claim "the Script Language Container ships no CA bundle" is load-bearing for an operator-facing normative requirement — "One of the two parameters above MUST therefore appear in the address" and "the address carrying neither MUST fail". Decision [10] attributes the claim to CLAUDE.md: "`CLAUDE.md` records that the UDF sandbox guarantees no CA bundle." CLAUDE.md records no such statement; its only certificate line is "Every Exasol DSN carries `validateservercertificate=0` — the container serves a self-signed certificate", which is about a self-signed test certificate, not about a missing trust store. The claim is therefore unmeasured, and the only measurement the plan schedules (task 2.4, "Measure the certificate parameters ... in the integration tier") runs in `crates/adbc-vs-scan/tests/exasol_it_test.rs`, which links the crate as an rlib on the host and never executes inside the SLC. In the host tier the neither-parameter case fails for a different reason — the host trust store does not trust the container's self-signed certificate — so a green test would confirm nothing about the sandbox.
- Fix: In decision-log.md decision [10], delete the CLAUDE.md attribution and state the CA-bundle claim as unverified. Move the neither-parameter assertion out of the integration tier: add a task under § 5 that asserts, from inside the UDF sandbox in `crates/adbc-vs-adapter/tests/e2e_exasol_test.rs`, that an address carrying neither `validateservercertificate=0` nor `certificate_fingerprint` fails, and add that scenario row to plan.md § Verification. If the measurement shows the SLC does supply a trust store, weaken the `scan-udf/exasol-scan` clause from MUST-fail to a statement that the driver's default validates against the sandbox's trust store.

## Design Depth

#### [TACTICAL_SHORTCUT] ADVISORY
- Location: decision-log.md decision [9]; plan.md § Dependencies
- Issue: decision [9] accepts unbounded scan memory as permanent, weakening a framework guarantee to accommodate one driver: "no discipline in the scan can bound peak memory".
